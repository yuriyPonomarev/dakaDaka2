# U2B9-R1 — Common gear also has a chest-owned UID (code saved; no compile/gate/play/build/screenshot run executed here, so nothing is claimed passing)

- Changed only `Assets/Emberdelve/Runtime/Data/LootTable.cs` (+ this report). `ChestInteractable.cs` was read and left unchanged: its offer branch already routes on `LootDrop.IsRolled` (`Instance != null`), never on rarity, so Common instances route the same way with no edit and no `CollectLoot(ItemData)` fallback. No test, gate, asset, scene, meta, package, Inventory/Equipment/roller/instance/issuer/UI/builder edit.
- APIs added (additive only, nothing renamed or removed): `LootEntry.RequestsGearInstance` (`item != null && item.IsEquippable`) and `LootTable.RequestsGearInstances`; `LootEntry.RequestsRolledGear` / `LootTable.RequestsRolledGear` keep their old honest meaning — "declares a rarity above Common", i.e. the affix question, now documented as deliberately separate from the identity question so has-affix is never read as has-UID. `LootDrop`, both constructors, `Roll`, both `TryRoll` overloads, `affixRarity`, `affixCatalog`, `Validate`, `Contains`, `Describe` signatures unchanged.
- Pipeline fix: the profile pass now tracks `requestsRolledAffixes` and `requestsGearInstances` separately; the trusted item catalog is built whenever any entry is worn gear (Common included) instead of only when a rarity is above Common, while the "no affix catalog" refusal still fires only for a rarity that actually rolls affixes. `StageDrop` splits by `RequestsGearInstance`: carried entries stay one `ItemData`+drawn-amount drop on the counted U1C2H partial path; gear entries stage `amount` separate quantity-1 drops, each minted exactly once through the existing mint-free `LootRoller.TryRollAffixes` proof pass and then `LootRoller.TryRoll(definition, 1, rarity, authority, roller, issuer, …)` — so amount 2 Common boots is two qty-1 instances with two distinct UIDs, never one UID on an aggregated 2 and never a lost unit.
- Common gear semantics: `LootRoller`/`ItemInstance` already define Common as 0 expected affix records, so a Common gear unit needs no `affixCatalog` (null/empty is legal: `TryBuildAuthority` passes an empty affix list, `ItemInstanceAuthority.TryCreate` accepts it), consumes zero draws from the derived affix generator in both the proof and production passes, keeps the definition's fixed `statModifiers`/`attributeBonuses` untouched, and mints one UID at chest generation. Unknown rarity (`(AffixRarity)99`), a non-Common claim with no item, and Uncommon/Rare on carried gear remain refusals that mint nothing and publish nothing.
- Determinism/compatibility: the shape loop is byte-for-byte the same legacy loop on `new System.Random(seed)` (same `guaranteeFirstEntry` step, same `PickWeighted`/`RandomInRange` order and number consumption), so the same seed still selects the same entries and the same amounts; only what a selected gear unit becomes has changed. `DeriveAffixSeed` and the two-pass affix consumption are unchanged, and Common units draw nothing from that stream, so existing Uncommon/Rare records for the same seed are unchanged. The three authored tables (`Loot_SupplyChest`, `Loot_EmberChest`, `Loot_SealedChest`) are untouched assets: their carried coin/draught/arrow/relic drops keep definition+count behavior, and their Common boots/cuirass/fangblade/shield drops now arrive as one instance each — which is the same instance-backed bag state `Inventory.TryAdd` already produced for gear since U2B4, so equipment, UI, stats, death/stash and extraction see no new stack shape.
- Validate/Describe now match the real lifecycle: an equippable entry whose item id cannot be a catalog entry is reported, a gear-bearing table whose entries name two different definitions for one item id is reported (that is a roll-time refusal, mirrored so the builder sees it early), repeated references to the same object stay legal, and `Describe` shows the rarity for every gear entry. `Validate` gained no new failure for the three authored tables (all ids stable, all ids unique, all slots resolvable by `ItemCategoryRules`).
- Host contract: unchanged and unfallback-able. `RunDirector` is the only shipped host and implements `IInstanceLootHost`, so Common gear transfers through `Inventory.TryAddInstance` (which already requires `IsEquippable` + quantity 1 and refuses a duplicate UID); a hypothetical host without the instance contract now refuses Common gear too, with the existing explicit reason and the instance retained in `Remaining` — no shipped fixture does that, so no concrete fixture issue to report.
- Pending manager (not executed here): compile; the existing 17-check `EmberdelveChestInstanceGate` (its "Common gear also owns UID before pickup" case is the one that was failing and is what this patch targets — expected now `Instance != null`, `Rarity == Common`, `AffixCount == 0`, count 1); plus the requested Common full-bag→reopen-same-instance→transfer, amount-2 Common distinct-UID, legacy carried-partial (`EmberdelveChestPartialGate`), items/inventoryui/UI and live smoke-log reruns. Blockers: none inside the assigned scope; per-run server-owned loot seed and loose rolled-gear pickup remain out of scope as in U2B9.
