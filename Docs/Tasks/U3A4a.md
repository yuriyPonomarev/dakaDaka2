# U3A4a: server-simulated movement from client input frames (no prediction yet)

Status: written WITHOUT compiling or running anything (no Unity and no C# compiler in the implementer sandbox). Base: `9cfa1c6` (U3A2 + U3A3 + gate-exit fix; NetSeams 149/0, NetAdmission 108/0, NetProof 35/0 were verified in real Unity by the root agent). Scope: `Docs/Tasks/U3A_plan.md` section 2.3 and "U3A4", step 4a only. Option C of the plan: the server owns movement, the owning client renders what the server says. Client prediction, reconciliation and interpolation tuning are 4b.

## What changed

### Pure rules (`Emberdelve.NetRules`, unit tested)
- `InputSanitizer` (per sender). Order: finite numbers, flag whitelist (`MoveInputFrame.KnownFlags`), sequence, |move|, frame budget. Sequence: 0 is reserved, a frame at or behind the last accepted one is a replay (counted) only when it is the newest frame of a batch AND at least 4 behind (closer = reordering / redundancy, silently ignored); more than 64 ahead is invalid (the first frame must be <= 64). |move| up to 1.5 is scaled to length 1 (a diagonal of two full axes is 1.41; counted as `Clamped` only above 1.05), above 1.5 it is invalid. Yaw is wrapped to [-180,180), pitch clamped to +-85. Budget: token bucket, 2 x TickRate = 60 accepted frames per second per sender, burst 60. Rejected frames leave no state behind (the last accepted sequence only moves on accept) with one deliberate exception: a flood-dropped frame still consumes its sequence number, so an honest client that briefly exceeded the cap is not locked out behind the forward-jump window. Counters: `Accepted`, `DroppedReplay`, `DroppedFlood`, `DroppedInvalid` (+ per reason `InvalidNonFinite/Magnitude/SeqWindow/SeqZero/Flags`), `Clamped`, `Redundant`. Time is injected, the server feeds it from the tick counter.
- `ServerMoveInputBuffer`: per-player queue, hard capacity 6, trimmed to 4 (oldest dropped, its jump / crouch edges folded into the next frame). `Next` returns exactly one frame per call: queued, else the last move repeated for at most 3 ticks (edges cleared, sprint kept), else neutral (view kept).
- `MoveInputAggregator` (client): per render frame `Sample`, per tick `Flush` = one frame (move and sprint = last held, jump / crouch edges OR-ed, current yaw / pitch), stored quantized (`MoveInputFrame.Quantized`) so a predicting client will step with the numbers the server sees; `FillBatch` returns the last 3 frames, oldest first.
- `NetScriptSpec` / `NetScriptTimeline`: the client test script grammar (`name[:seconds][@yaw]`, comma chains, 0.8 s idle gap between steps) and the pure time line of every script.
- `NetLaunchArgs`: `-ember-net-script` now takes any of the scripts below or a chain (`forge-owner` keeps its exact old meaning and spelling); new `-ember-net-script-start-file PATH` (script starts when the file exists; default 1.5 s after spawn) and `-ember-net-script-yaw DEGREES` (negative values need the `=` form). `NetTuning.TickSeconds = 1 / TickRate` (`TickRate = 30` already existed).
- Tests (new files in `Tests/EditMode/NetRules`): `InputSanitizerTests`, `ServerMoveInputBufferTests`, `MoveInputAggregatorTests`, `NetScriptSpecTests` (parse, malformed input, launch args, every script's time line). Not run (no Unity here).

### Wire and RPCs (`Emberdelve.Net`)
- `MoveFrameWire` / `MoveBatchWire` (`INetworkSerializable`): `Count` + three fixed frame slots (no array support needed from the RPC layer). Frames carry FULL floats and the full flag byte on purpose: an honest client sends the quantized values, but the server does not trust the encoder, so NaN, absurd axes, unknown flags and big sequence jumps must be representable to be rejected and counted. No player, combat or party id anywhere.
- `NetPlayerRig`: `SubmitMoveRpc(MoveBatchWire, RpcParams)` = `[Rpc(SendTo.Server, Delivery = RpcDelivery.Unreliable)]`, RequireOwnership left ON; DEVELOPMENT_BUILD / Editor only `ForgeMoveTestRpc` = same payload and same server path with `RequireOwnership = false`. Both hand `this` and `rpcParams.Receive.SenderClientId` to `NetMovementServer.Receive`; nothing else identifies a sender. Owner role adds `NetInputSender` at spawn, removes it at despawn.

### Server (`NetMovementServer`, owned by `NetServer`)
- `Receive`: sender -> `NetIdentityTable` row -> movement state. No row (not admitted yet, already removed) => ignored and counted globally (`REJECT no-player`). Target object != the sender's own object => forged-owner movement: counted on the OFFENDER (`forge`), `REJECT forge-move count=n id=<offender> target=<victim id> ...`, nothing else happens. Otherwise each frame goes oldest to newest through the sanitizer (newest = primary) into the buffer.
- Simulation: subscribes to `NetworkManager.NetworkTickSystem.Tick` (not Update). On every tick each registered player gets exactly ONE step: frame from the buffer, `PlayerLook.ApplyAimPose(yaw, pitch)` (new, clamps pitch to the component's limits), `PlayerMovement.Step(frame, 1/30)`. Registered after `SpawnAsPlayerObject` (`ExternalDriven` was already set by `TrySpawnNetworkPlayer`), unregistered before the despawn. The host's own presenting player is not simulated here (it keeps its Update).
- Logs: `movement registered id=.. walk=.. sprint=.. crouch=.. jump=.. pos=..` (the resolved authority numbers), `move id=N pos=(x,y,z) acc=.. rep=.. flood=.. inv=.. tick=.. yaw=.. clamp=.. qdrop=.. forge=.. vmax=.. ymax=.. air=.. depth=..` (when the player moved or a counter changed, at most every 15 ticks, heartbeat every 120; `vmax` = fastest tick since the previous line), a last line with `final=1` and the per-reason counters at removal, `REJECT <kind> count=n id=N` (kinds: replay flood nan big-move seq-jump seq-zero flags bad-batch forge-move; logged at counts 1..3, powers of two and every 100th), `seg id=N kind=move ... dist disp mean peak from to` per finished stretch of movement (moving > 0.3 m/s until still for 6 ticks), `air id=N ticks rest ymax rise` per jump / fall of >= 4 airborne ticks.

### Client (`NetInputSender`, owner only)
- Per render frame: scripted driver if `-ember-net-script` is a movement script, else the real `EmberdelveInput` for a windowed owner (move, sprint, jump / crouch edges, mouse look integrated with PlayerLook's formula into a view yaw / pitch; own camera pitch via the new `PlayerLook.ApplyPitch`), else an idle stream. Per NGO tick: one `Flush`, one RPC with the last three frames. The owner's `PlayerMovement` stays `ExternalDriven`; its transform follows the server through the existing server-authority `NetworkTransform` (so the owner lags by the round trip: accepted for 4a).
- Scripts (development builds / Editor): `walk-forward:<sec>`, `walk-square:<sec per side>`, `sprint-forward:<sec>`, `jump`, and the hostile `flood-input` (10 batches per tick, neutral), `flood-run` (10 batches per tick, forward), `replay-seq` (an extra batch with sequences 30 behind), `nan-input` (NaN axes / infinite yaw + NaN pitch), `big-move` (|move| = 70), `seq-jump` (+100000), `forge-move` (frames on the highest-id other player's object through `ForgeMoveTestRpc`), plus the existing `forge-owner`. The honest idle stream continues during hostile steps; the hostile frames are extra. Logs `script <name> start/done pos=(..)` and `script chain done steps=N pos=(..)`.
- `NetClientProbe` also logs `[client] view id=<n> pos=(x,y,z)` for every other player every 0.5 s when it moved (> 2 mm) and as a 2 s heartbeat.

### Runtime change
- `PlayerLook`: `MinPitch`, `MaxPitch`, `ApplyAimPose(yaw, pitch)`, `ApplyPitch(pitch)`. Additive; `LateUpdate` untouched. Offline never calls them. `PlayerMovement` is unchanged; offline code paths, `NetRole` and the asmdef graph are unchanged (NetRules and Net only gained files).

## Gate: `EmberdelveNetMovementGate.Run()`
Process based, copied harness of NetAdmission (`-ember-proof-dir`, `-ember-proof-reuse-exe`, own PIDs only, exit only through `EmberdelveGateExit.Exit`, final line `[Emberdelve][NetMovement] PASS|FAIL checks=N failures=M`). Server `--ember-net-no-enemies --ember-net-max-players 4`; clients join in this order and take layout spawn slots 0..3 (checked against `movement registered ... pos`):
- B warrior (slot 0): `nan-input, big-move, seq-jump, replay-seq, flood-input, forge-move` (1.5 s each) and the observer.
- A archer (slot 1): `walk-forward:3, sprint-forward:1.5 (back), jump, flood-run:2`.
- W warrior (slot 2): `walk-forward:4` toward a wall. V warrior (slot 3): idle, the forgery victim.
Directions come from the layout asset (walkable grid): A's lane must be free for the longest legal walk, W's wall must be 3 to 9 m ahead; the gate fails with a message otherwise. All scripts start together via start files once every client reports `views=4`.
Checks (all from the server's own lines): A walk displacement and mean speed = logged resolved walk speed x 3 s +-20 %, along the sent yaw; sprint peak / mean faster than walk, peak <= class sprint x 1.15, displacement +-20 %; jump rise 0.6 to 1.3 x jump height, >= 8 airborne ticks, back at rest height; flood-run no farther than one honest stream (+20 %); W stops on the near side of the wall (travelled <= wall plane, >= plane - 1.3 m, closed segment, walkable cell); B's last `view id=` of A, W and V within 0.15 m of the server's last `move` position; owner A's own transform within 0.3 m of the server; per cheat a `REJECT <kind> count=1 id=B` line and counters (nan / big / seqj >= 15, replay >= 15, flood >= 100, forge >= 15); B and V do not move (XZ < 2 cm first to last line); honest clients A (except flood), W, V trip no replay / invalid / forge counter; for all four players no per-tick speed and no sampled interval above class sprint speed x 1.15; graceful exits, final `players=0 senders=0 registry=0`, forbidden-pattern scan, no PID left; static scan that no `[Rpc]` parameter list names a player / combat / party / sender / actor id and that the movement RPCs exist.

## Risks and notes
- **Step is not tick-deterministic yet (matters for 4b, not for 4a).** `PlayerMovement.Move` seeds its acceleration from `controller.velocity`, which Unity derives from the last Move and the (render) delta time, not from the tick dt passed to `Step`. The result is clamped to the resolved class speed, so speed bounds hold (the gate checks it), but the ramp shape depends on the server's frame rate. Owner prediction will need either a velocity kept inside PlayerMovement or a fixed-dt-independent ramp. Not changed here (hot path, seams gate parity).
- Tick event timing: NGO runs the tick in its own update stage; Step runs inside it. If the tick fires twice in one frame the server steps twice (correct) and two CharacterController.Move calls happen in one physics frame.
- The owner's view lags the server by the round trip (no prediction). The real-input windowed path (mouse look integration, `ApplyPitch`) could not be exercised headless; its sensitivity is PlayerLook's default (1.2), not the user's setting.
- Numbers in the gate (+-20 %, 0.15 m, the 1.15 bound) were chosen from the model (4.3 / 6.4 m/s, 30 Hz), not measured. If an assertion fails on first run read the logged values before changing a tolerance.
- Input before spawn / after despawn is handled (`REJECT no-player`, frames for a state-less sender ignored) but not provoked by the gate: a modified client cannot easily send between the approval and the spawn on loopback.
- The honest stream sends 3 frames per tick; a sender stalled for more than 3 ticks loses the older ones (by design: repeat 3 ticks, then neutral).
- Dead / extracted players are still stepped (4a ignores death); the combat slice (U3B) decides.
- Unity serialization: no new serialized field on existing components, so the generated `Emberdelve_NetPlayer.prefab` does not need a rebuild (`NetInputSender` is added at runtime).

## Fix: speed-bound failures (first Unity run, 138/142)
**Root cause: measurement/bound error in the gate, not a movement overshoot.** The gate bounded speed by the AUTHORED class `sprintSpeed` x 1.15 (archer 6.4 -> 7.36), but the legal speed is the server-RESOLVED one (`PlayerMovement.ResolveGroundSpeed`, DEX/gear folded in). The log line `movement registered id=2 ... walk=5.245 sprint=7.807` shows A's resolved sprint is 7.807 (authored 6.4, x1.22; its walk is likewise 5.245 vs 4.3, and the walk checks already used the resolved value). Every logged peak is exactly 7.807 (`vmax=7.807`, `seg ... mean=7.667 peak=7.807`, `vmaxAll=7.807`), i.e. the Move clamp to `[0, targetSpeed]` held and there is no overshoot: no tick exceeded the resolved cap, so the controller.velocity seeding, double Step, vertical/teleport and sprint-back hypotheses are not what failed (peak is the same value in all four failing checks and equals the cap to 3 decimals). Warriors (authored 5.2, resolved 4.888) were never over their bound.
**Fix:** the gate now bounds by the resolved sprint speed parsed from each player's `movement registered` line x 1.15 (sprint segment check, per-tick, sampled interval, whole-run VMaxAll). No tolerance widened; `PlayerMovement` and all runtime code untouched, so offline parity is unaffected.
The "Step is not tick-deterministic" risk above stays open for 4b (ramp shape depends on server frame rate), but it is not the cause of these failures.
