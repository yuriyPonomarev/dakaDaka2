# D1c3: ranged hit locations (projectiles use the melee location table)

Status (26 Oct 2026): DONE. User decision: ranged uses the melee location table (head x1.5). Evidence Logs/d1c3_20261026_160303 (19 groups PASS incl. ProjectileBlock 51, SkillAuthority 161, AttributeSkill 925, archer/realcombatarcher), reruns after fixture fixes (same-team targets, empty magazine, leftover fixtures catching arrows): CombatAuthority 51/0 (Logs/d1c3_rerun_20261026_163104), RangedLocation 99/0 (Logs/d1c3_rerun2_20261026_163449).

Scope: arrows and bolts take their damage multiplier from the same hit-location table as melee, decided by the authority from the target's analytic hit volumes. Nothing was compiled or run (no Unity here); every change was reasoned against the source. Nothing committed.

User decision (overrides the D1c plan where they differ): ranged projectiles use the SAME table (head 1.5, body 1.0, arms 0.8, hands 0.7, legs 0.6, feet 0.5; verified in `Runtime/Data/HitLocationTable.cs`) instead of the head-collider x1.8 rule. Melee impact zones never apply to projectiles. Targets without hit volumes (fixtures, objects, pose-less fakes) resolve Unspecified x1.0, which differs from the plan's "head collider contact = Head" fallback on purpose.

## Changes
1. `Runtime/Combat/LocalCombatAuthority.Projectiles.cs`: `IsProjectileHeadshot` (head collider within 5 cm) is deleted. New `ResolveProjectileLocation(flight, target, segmentStart, segmentLength, impactPoint)`: sweeps every `HitShape` of the target (radius + arrow radius, same `TrySweepCapsule` the contact search uses) along the step segment; smallest entry distance wins (first touched), entries within 0.1 mm go to the lower `HitLocation` value (same tie rule as `IsBetterContact` in the melee sweep). If the physics-collider branch won the contact and no volume is touched inside the step, the volume with the nearest surface to the impact point wins (same tie rule). Target is not an `IHitShapeProvider` or has no shapes: `Unspecified`. A blade contact (`bladeContact`) keeps `Unspecified`: the blade stops the arrow before any body location exists, and the interception/guard-reduction path is untouched. `StepProjectile` passes the segment start and length to `ApplyProjectileImpact`. The location multiplier is read from the authority's own `LocationTable` (GameConfig asset or code default); `HitCandidate.Headshot` is now derived (`location == Head`). Documented deviation from melee: first-touched, not deepest-in-window.
2. `Runtime/Combat/DamageAndScanning.cs`: `Resolve` and `ResolveSkill` gain trailing optional `projectileLocation` / `projectileLocationMultiplier`. With `rangedProjectile == true` the table factor replaces the binary x1.8; `DamageInfo.Location` is set and `DamageInfo.Headshot` is `location == Head` (a forged `HitCandidate.Headshot` is ignored on this path, `Finalize(locationAuthoritative)`). Flat-damage skills (BattleCry-style `UsesFlatDamage`) ignore location on the projectile path. Non-projectile calls (legacy hit-only melee/area) are bit-identical, so the CombatAuthority melee head-collider cases stay as they were. Dead `HitScanner.CollectRangedHits` (ray scan with the head-collider rule, no callers) removed; `CollectRadialHits` kept. `DamageResolver.HeadshotMultiplier = 1.8` stays for the legacy path.
3. Head bonus: no gear/affix headshot bonus exists in code today; the only hook is `HitLocationTable.Multiplier(Head, headBonus)` (default 0, head + bonus capped at `HeadCap` 1.8, never multiplied). Unchanged and now exercised by the new gate (1.5, +0.1 -> 1.6, +0.5 -> 1.8, +100 -> 1.8, bonus ignored for non-head). The projectile path currently passes no bonus.
4. Crouch (small, local, done): `PlayerLook.HitVolumeHeightRatio` (1 standing, `crouchEyeHeight / standEyeHeight` while `PlayerMovement.IsCrouched`, clamped 0.3..1); `PlayerRig.CollectHitShapes` compresses the collected shapes vertically toward the feet by that ratio (radii unchanged). Standing is an exact no-op (ratio 1, branch skipped), so every standing melee/ranged number is unchanged. The volumes step to the crouch ratio at once while the camera eases (about 0.3 s), a known small lead of the authority volumes over the view. Also fixes the D1a "volumes do not follow crouch" low for melee (melee reads the same `CollectHitShapes`). Telegraph lift of enemy bodies stays D1c4.
5. `Runtime/Core/GameContracts.cs`: doc comment of `DamageInfo.Location`; `Docs/Design/DND_PARITY.md` Hit locations row records the projectile rule.

## Risks
- Players feel it: ranged head 1.8 -> 1.5, and arms/legs/feet hits that were x1.0 now deal 0.8/0.6/0.5. Archer smoke tests that kill enemies by arrows could need more arrows; the smoke `archer` and `realcombatarcher` runs must be read, not just counted.
- Arrow radius (0.025 m) is added to volume radii, so ranged contacts are slightly more generous than melee.
- Collider branch (EnemyAgent has real colliders) can win the contact before any volume is touched; the nearest-surface fallback then decides. If an enemy's collider is much bigger than its volumes, locations skew toward the nearest volume.
- Crouch volumes step instantly while the camera eases; `HitVolumeHeightRatio` is derived from class eye heights, so a class with unusual values changes its crouch hitbox.
- `ResolveProjectileLocation` sweeps the whole step segment, so for a long step (up to 84 m per 2 s test advance) it is O(shapes x 64 iterations) per impact only, not per step.
- `ICombatEntity` fixtures that rely on `HeadCollider` for ranged headshots no longer get one (intended).
