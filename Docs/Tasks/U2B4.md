# U2B4 — actual gear instances survive bag/equipment transfers (code saved; every compile/behaviour check pending manager)

- Changed only `Runtime/Items/Inventory.cs` and `Runtime/Items/Equipment.cs`. No helper file was needed; no UI/PlayerRig/stats/builder/scene/asset/gate/package/meta touched, no new serialized fields (no scene-YAML change).
- New APIs (Inventory): `InventorySlot.Instance`/`IsInstanceBacked`/`UidText`, `InstanceAt(int)`, `IndexOfInstance(Guid)`, `HoldsInstanceUid(Guid)`, `MintedInstanceCount`, `TryAddInstance(ItemInstance,out reason)`, `TryAddInstanceAt(ItemInstance,Vector2Int,out reason)`; (Equipment) `EquippedInstance(EquipmentSlot)`, `HoldsUid(Guid)`; internal transfers are now instance-typed: `TryEquipTransfer(int,ItemInstance incoming,ItemInstance outgoing,out reason)`, `TryUnequipTransfer(ItemInstance,out reason)`.
- One authoritative instance per occupied gear stack/slot: `Stack.Instance` + `Stack.Definition` (definition reads derive from the instance), `Equipment._gear` is the store and `Equipment.Slots`/`Equipped`/`Describe`/stat rebuild read a `_slotViews` array rebuilt from it — never a parallel registry. Currency/consumables/relics stay definition-only (`Instance == null`) with unchanged behavior.
- Legacy path: `TryAdd`/`TryAddAt`/`GiveStartingItems`/`RunDirector.CollectLoot` still take `ItemData`; each accepted gear object becomes its own stack with exactly one explicitly minted Common instance (qty 1). Mint goes through `ItemIdentityIssuer.TryCreateInstance` against a per-definition local catalog (`ItemInstanceAuthority.TryCreate` with an empty affix list), so the accepted trusted-definition gate sees the exact object; two distinct objects sharing one item id each get their own catalog instead of making the lookup ambiguous. A mint failure refuses the whole add and rolls back every stack that call appended. `MintedInstanceCount` makes minting observable.
- `TryAddInstance` places the instance itself: same UID, same rarity, exact rolls, no mint/copy/reroll; refuses rolled non-equipment (metadata is not discarded), quantity≠1, a UID already in this bag, or a UID already worn by this player's equipment; a full bag leaves the instance untouched. It credits like any other loot add (starting-kit flag still suppresses credit).
- No reroll/mint on move/swap/equip/unequip/replace/grid-resize: `TryMove`/`TrySwap` exchange cells only, `ConfigureGrid` re-places the same instance object, `TryMergeStacks`/`TryAddToSlot` refuse instance-backed stacks (gear never merges by definition), `TryRemoveAt`/`Clear` drop the identity with the stack, and equip-by-index resolves the exact instance (`TryEquipTransfer` refuses if that slot's UID is not the one requested) instead of `IndexOfItem` ambiguity.
- Atomic ownership: the bag half commits the incoming unit's departure and the outgoing instance's arrival in one step (freed-footprint hole planning unchanged), then Equipment commits slot+hand+`RefreshStats` and raises the single `InventoryChanged` + one `EquipmentChanged` — refusals still touch and notify nothing, no `ItemCollected`, no RecoveredValue/LifetimeCollected credit, no momentary extra/duplicate/lost item. Class default hand stays the authored loadout (`RestoreClassHand`), never minted. Rolled affixes are still not applied to stats; a slot contributes only its definition's authored modifiers.
- Executed here: read/grep/find/ls and the edits only — no Unity, compile, import, test, gate, build or screenshot run, so nothing is claimed passing.
