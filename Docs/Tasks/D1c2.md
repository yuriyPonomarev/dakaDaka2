# D1c2: swing turn ceiling (authority only) and a sample grid that covers rotation

Status (26 Oct 2026): DONE. User decision: hard 720 deg/s ceiling only (no camera slowdown, no per-phase caps). Root fixes: two double literals in the new gate. Evidence: Logs/d1c2_20261026_154344 (TurnCeiling 116/0, CombatFlow 411/0, 17 groups PASS) and Logs/d1c2_rerun_20261026_155811 (SweptMelee 644/0 after the chest fixture used an armless dummy: the denser grid correctly finds the arm first).

Scope: review D1a H2 (turn rate) and M-b (per-probe sample spacing). Nothing was compiled or run (no Unity here); every change was reasoned against the source. Nothing committed.

User decision (overrides the D1c plan): only a hard ceiling of 720 deg/s. There are NO per-phase feel caps on `SwingPatternData`, NO `PlayerLook`/camera slowdown and NO `ITurnFlowSource`. The authority is the only place that limits turning.

## Changes
1. `Runtime/Data/CombatFlowTuning.cs`: new `swingTurnCeilingDegPerSec` (default 720, `DefaultSwingTurnCeilingDegPerSec`), plus `ResolvedSwingTurnCeiling` (what the authority enforces) and `GridSwingTurnCeiling` (what the sample grid is sized for).
2. `Runtime/Combat/LocalCombatAuthority.Swings.cs`: `SwingRecord.TurnCeiling` / `TurnClamped`. The ceiling is read from `FlowTuning` once, at the accepted begin (the grid and the follower of one swing always agree). In `StepSwing`, for every phase from begin to end: the reported yaw/pitch becomes a rate-limited follower. Per step, budget = ceiling x (ts - LastTs); yaw advances at most budget from `rec.LastYaw` (`Mathf.DeltaAngle`, shortest way round), pitch at most budget from `rec.LastPitch`; the excess is DISCARDED (never banked: only the follower state `LastYaw/LastPitch` carries on, it is not a hidden debt) and added to `TurnClamped`. A turn inside the budget is passed through unchanged, so honest play is bit-identical to D1c1. The per-sample Lerp between the last and the new pose is unchanged and now interpolates the follower pose. A non-finite reported yaw/pitch is treated like a missing pose (last pose kept; before, NaN would have flowed into the frame). Eye position is not limited (out of scope: movement authority).
3. `Runtime/Combat/CombatContracts.cs`: `MeleeSwingStatus.TurnClampedDegrees` (total yaw plus pitch degrees held back over the swing). Added as a trailing OPTIONAL constructor parameter (`float turnClampedDegrees = 0f`), so no constructor call site had to change; the only call site is `TryGetMeleeSwingStatus`, which passes it. Grep over Runtime/Editor shows no other `new MeleeSwingStatus` and no deconstruction.
4. `Runtime/Combat/SwingGeometry.cs`: `SampleCount(pattern, weapon, turnCeilingDegPerSec)`; the two-argument overload is the 720 grid and is what the smoke predictors (`PredictSwingContact`, `PredictSweepMargin`) keep calling. K = ceil(translation + rotation), clamp [8, 400]:
   - translation = (largest single-probe step of base or tip over the 128 probes) x 128 / spacing (M-b: the fastest segment decides, not the average);
   - rotation = ceilingRad x activeTime x EffectiveReach / spacing (H2).
   spacing is unchanged: clamp(sweepRadius/2, 0.02, 0.06). A ceiling <= 0 or infinite is sized as 720.
5. `Editor/EmberdelveAssetLibrary.cs` (`BuildConfig`): authors `Config.flow` if missing and sets the ceiling to 720 only when the stored value is 0 (an asset saved before D1c2); a tuned positive value or a negative (unlimited) value is left alone. Run `BuildDataOnly` once.
6. Gates: new `Editor/EmberdelveTurnCeilingGate.cs` (+ `.meta`, guid fe6cf309769040e7ae56043f01d06a70); `EmberdelveSweptMeleeGate` +6 checks; `EmberdelveRuntimeSmokeTest` realcombat matrix +1 check per combo step.

## Convention for the ceiling value (`CombatFlowTuning.swingTurnCeilingDegPerSec`)
- positive: used as is (deg/s);
- 0: unset, an asset serialized before this field existed, resolves to the default 720 (Unity gives old assets no initializer value for a missing field in every path, so 0 is deliberately NOT "unlimited");
- negative (for example -1): UNLIMITED. This is the test seam for mutation checks. The sample grid is still sized for 720 in that case, so the mutation changes only the follower, nothing else;
- NaN or +Infinity: treated as unset (720).
No separate flag was needed.

## Sample counts and literals
Computed outside Unity with a Python port of the formula and the authored keys (sword reach 2.3+0.6, rapier 2.7+0.45, `ApplySwingPatterns` numbers):

| pattern | spacing | old K | translation | rotation term | new K |
|---|---|---|---|---|---|
| sword slash L->R / R->L (active 0.30) | 0.06 | 66 | 66 | 143.9 | 210 |
| sword overhead (active 0.32) | 0.06 | 57 | 59 | 153.5 | 213 |
| rapier thrust (active 0.12) | 0.05 | 16 | 16 | 70.3 | 87 |

All stay below 400, so the guarantee holds at 720 deg/s for the shipped patterns. The old values 66/57/16 match the D1a doc.
Literals: no gate hard-codes a sample index or K. All quote K as a fraction or a relation, and the time of a sample does not depend on K (samples are time-equal), so they hold: SweptMelee "wall contact < K/3", "> K/2 and < 0.95 K", "wall sample == 0", probe "first >= u - 0.13 and <= u + 0.01" (a finer grid only tightens it), thin pattern K > sword K (thin sword is clamped to 400, sword is 210), CombatFlow `stopTime` (fraction), smoke predictors (use the same two-argument grid as the default-config authority). No literal had to be changed. Cost: about 3x more segment/capsule tests per swing (210 samples x targets x one linecast per sample), still tiny.
Thin test pattern (r 0.02, spacing 0.02) now clamps at 400 in a static pose: the translation spacing is then 0.0095 m, still fine; the rotation part of the guarantee is not claimed for that clamped synthetic case (the new gate uses a thin RAPIER, K about 216, for the turning case).

## New checks (`EmberdelveTurnCeilingGate`, expected about 116; the gate prints the real count)

- Yaw flick (27): rapier thrust, target directly behind at 1.8 m, a 180 degree flick inside one 20 ms tick at three moments (early active, last 20 ms of the active phase, during the windup). Plus: a 14 degree step in 20 ms (700 deg/s) is not clamped; a pose-less swing (pose removed after the begin) completes on its last pose, hits the target in front, 0 clamped.

- Legal turns (51): 100 deg/s toward a target 40 degrees off (sword slash), 5 tick plans (1, 5, 20, 16/17/18, 50 ms): hit, 0 clamped, same location and damage, first touched within 2 samples of the 1 ms plan; 600 deg/s turn never clamped at any of the 5 plans; 900 deg/s clamped (> 30 degrees); a yaw+pitch wobble is not clamped; a thin target (r 0.01) on the path of a 600 deg/s turning attacker found with 5 ms and 20 ms ticks at u = 0.3 and 0.6.

- SweptMelee: +4 (K below the clamp per shipped pattern) +2 (real rig first and second swing report 0 clamped) -> expected 638 -> 644.
- Smoke realcombat (and realcombatarcher/archer matrices that share the combo-step loop at `EmberdelveRuntimeSmokeTest` ~2020): +1 per combo step ("real input is never held back").
Tick plans exclude the 2.5 s plan for turning cases on purpose: with a pose that changes inside a tick the authority interpolates linearly between tick poses, which is exact for constant-rate input only when the tick is short; static-pose tick independence (all six plans) stays pinned by the SweptMelee gate.

Mutations to run when Unity is available (each should fail the named checks): disable the follower (`TurnCeiling = Infinity` always) -> flick checks; drop the rotation term -> "consecutive samples within spacing" and the thin turning target; replace the per-probe maximum by the average -> the fast-segment check; ceiling 0 mapped to unlimited -> convention check.

## Risks
- Not compiled. Watch: tuple-named foreach in the new gate (C# 7), `IHitShapeProvider`/`HitLocation` namespaces (the gate uses Combat, Core, Data like the SweptMelee gate), `ComboTiming` being public (it is).
- The follower keeps chasing a held reported pose: a flick to 180 is reached after 0.25 s, so a legal 720 deg/s spin can still reach a target behind late in a long active phase (sword active 0.30 s). That is the ceiling by definition (user decision), not a leak; the gate uses the 0.12 s thrust and flick moments that make the difference decisive.
- Honest players CAN exceed 720 deg/s with a fast mouse flick (about 2 turns per second); that swing pose then lags the camera and the visual/damage agreement (2 mm) breaks until it catches up, because the camera is intentionally not slowed. Raise the tunable or use -1 if that feels wrong.
- Update vs FixedUpdate: the budget uses the authority clock between steps, so a long frame gives a proportionally larger budget; no slack constant is needed.
- Timings: `TurnClamped` accumulates per step; with many tiny ticks and a persistently held far pose it grows large (it is a diagnostic, not a limit).
- Reversing input is not exactly tick independent (follower state depends on step boundaries); constant-rate input is.
- Smoke predictors assume the default ceiling grid; if the ceiling is tuned, their sample index changes slightly (they only predict location/margin).
- Enemies (no pose provider) untouched; D1c4 gets the same follower through `IAimPoseProvider`.

## Note: SweptMelee run 1 (2 failures, "overhead versus horizontal")
Cause confirmed by a Python port of the sweep and the contact rule (sword slash L->R, humanoid at 1.5 m, aim at the chest): the left arm (x -0.43, r 0.10) is the FIRST volume touched, at u = 0.24 on both grids (sample 16/66 and 51/210). The contact window is 0.02 s; the old grid rounded it up to 5 samples = 22.7 ms, long enough for the torso (depth 0.1045) to overtake the arm (0.1022) at the last window sample. At 210 samples the window is 14 samples = 20 ms and the arm is still deepest (0.1022 vs the torso not yet deeper), so the location is Arms. The old Body result was a 2 mm knife-edge artifact of window rounding; the new grid is the more accurate one. The grid and the selection rule are unchanged. Fix: the chest fixture in `OverheadVersusHorizontal` uses a humanoid with the arm volumes disabled (`AddHumanoid(..., withArms: false)`), so the section still pins what it means to (slash on body = 1.0, overhead on head = 1.5 x pattern multiplier, ratio check strict at 1e-3). Check count unchanged (644). Not re-run here.
