## Problem
`InstigatorCombatId` (SubmitAttack, swings, projectiles, skill hits) and `casterCombatId` (TryBeginSkillCast, CompleteSkillCast) were caller-supplied and unauthenticated. Any code with the authority could attack, cast, spend another player's mana/ammo, stamp their cooldowns, burn their command sequence or occupy their swing slot.

## Changes
- `Runtime/Combat/CombatSenders.cs` (new): `CombatSenderId` (none / `TrustedHost` / `ForPlayer(playerId)`, one int, value type) and static `CombatSenders` (combat id -> owning sender). Setters (`Bind`, `Unbind`, `Reset`) are internal: only the Runtime assembly (RunDirector, CombatRegistry) and the Editor gates can write. `Bind` requires the entity to be registered and to BE that player's body (`IPlayerOwned.PlayerId == sender`), never re-binds an owned entity, and is idempotent for the same pair. `Authorize(sender, combatId)`: owned id accepts only its owner; unowned id (enemy, fixture rig) accepts only the trusted host; no sender is always refused. Reason text always contains "sender".
- `LocalCombatAuthority.Senders.cs` (new partial): sender-bound overloads `SubmitAttack`, `TryBeginMeleeSwing`, `LaunchProjectile`, `TryBeginSkillCast`, `CompleteSkillCast`, `SubmitSkill`, `LaunchSkillProjectile`. Each calls `AuthorizeSender` FIRST (before registry lookup, sequence, cooldown, mana, ammo, swing or activation state) and then delegates to the existing method, so a refusal changes nothing except `RejectedCount`, `SenderRefusalCount`, the reject-reason strings and `LastCommandSender` (observability). The existing sender-less overloads are not modified.
- `CombatContracts.cs`: the 7 overloads added to `ICombatAuthority` (the only implementer is LocalCombatAuthority); `CombatRegistry.Unregister` unbinds, `ResetForRun` resets the table.
- `RunDirector.TryJoin`: binds `ForPlayer(rig.PlayerId)` to `rig.CombatId` after party resolution and before the rig changes; SpawnPlayer inherits it. A bind failure refuses the join.
- `PlayerRig.CombatSender`: the bound player sender, or `TrustedHost` for a rig no run admitted (fixture/tool rigs are unowned entities; their sender-less calls keep working exactly as before).
- Call sites switched to the sender-bound overloads: `MeleeCombat` (swing), `RangedCombat.Fire`, `SkillCaster` (begin and complete), `BattleCryBehavior` (hit), `RangedSkillUtility.FireOne` (skill arrows). `EnemyAgent` and all Editor gates still use the sender-less path (enemy = unowned entity, trusted local path).
- Line endings kept per file (PlayerRig.cs CRLF edited with CRLF; new files LF; metas without trailing newline like their neighbours).

## Risks and limits
- The sender-less overloads stay open: any in-process code can still pass a rig's id without a sender. R1c1 binds identity and moves every shipped player call site onto it; closing the old path needs the ~15 fixture gates migrated (R1c3, user decision 1).
- `PlayerRig.CombatSender` is derived from the rig itself, so this is local-process hardening, not network security: a client that owns the rig can still send as it. The sender source must become the connection in U3A.
- The owner table is process-wide static like `CombatRegistry` (same reset points).
- `ICombatAuthority` grew by 7 members; any out-of-tree implementer (none in the repo) would break.
- Entities not bound by a RunDirector (fixture rigs) are unowned: the trusted host may act for them, a player sender may not.
- Blind-written C#: lambdas with `out` parameters in the gate, `in` parameter forwarding and the reason substrings ("sender", "sequence", "activation") are the first things to check when compiling. The P2 projectile checks assume a spawned remote rig has a usable aim pose. Gate runtime is dominated by real cooldown waits (about 40 s).
- Does not touch kit epoch/mana/ammo authority (R1c2), dash movement or CompleteSkillCast being caller-driven (R1c3).
