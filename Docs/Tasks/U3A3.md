# U3A3: admission, ownership and cleanup over the wire (spawn, no movement)

Status: written WITHOUT compiling or running anything (no Unity in the implementer sandbox). Base: U3A2 (`39c1260`, compiles with NGO 2.7.0 / UTP 2.6.0). Scope: `Docs/Tasks/U3A_plan.md` section 2.2 and "U3A3". Binding user decisions kept: NGO server authority, auto parties of 3, late join while Running, disconnect removes the actor immediately, rejoin = new actor, loopback only, offline path identical.

## What changed

### Pure rules (`Emberdelve.NetRules`, unit tested)
- `NetApproval.Evaluate(payload, serverProtocol, connectedCount, maxPlayers, isSlotInUse, isClassApproved)` (the U3A1 four-argument overload stays and checks neither slot nor class). Order: payload, protocol, class, duplicate slot, capacity. Request-level faults therefore win over "server full".
- Reasons (stable): `bad payload` (missing, empty, over 256 bytes, malformed, slot empty / over 32 chars / non-printable-ASCII anywhere in slot or class: the last blocks log injection), `protocol mismatch client=X server=Y` (U3A1 wording unchanged; the NetProof gate only needs the prefix), `unknown class`, `duplicate slot`, `server full`. Constants `NetApproval.Reason*`.
- `NetLaunchArgs`: `-ember-net-no-enemies [true|false]` (bare flag = true; also `--ember-net-no-enemies=false`), `-ember-net-script NAME` (`forge-owner` only; anything else is an arg error, exit 2). `-ember-net-class` / `-ember-net-slot` already existed. `NetTuning.DefaultClassId = "warrior"`: a client with no class asks for it (so plain `-ember-net client` still joins).
- Tests: new `Tests/EditMode/NetRules/NetApprovalTests.cs` (16 tests: every reason, precedence, hostile fields, max-length slot, stable strings, both new flags).

### Net layer (`Emberdelve.Net`)
- `NetIdentityTable` (server only): clientId <-> slot <-> server PlayerId (+rig, NetworkObject); `ResolveSender(clientId)` returns `CombatSenderId.ForPlayer(id)` or `None`. This is the only place a sender could come from; nothing sends one.
- `NetServer` (plain class driven by `NetBootstrap`): see "Server flow".
- `NetPlayerRig`: new `ServerClassId` (`NetworkVariable<FixedString32Bytes>`, server write / everyone read), static `Spawned` list, client log `view despawned id=<n> owned=<bool> views=<k>`, and the dev-only `ForgeOwnerTestRpc`.
- `NetClientProbe` (client process only): logs the settled view picture and runs the optional test script.
- `NetBootstrap`: `EnableSceneManagement = true`, creates `NetServer` / `NetClientProbe`, class default, quit-file polling for clients too (same `-ember-net-quit-file`), `shutdown players=P senders=S registry=R` line before `shutdown complete`. The old `Approve` moved into `NetServer`.
- Runtime (still no NGO type): `NetRole.EnemiesDisabled` (set only by the launcher, only true when a role is networked) and `NetSceneRoles` uses it to deactivate the scene's `Enemies` root before its Awake on a simulating process (found by name in the existing client list, else `GameObject.Find`; the saved scene is not re-authored).

### Server flow (`NetServer`)
1. `NetBootstrap` logs `listening` exactly as before (OnServerStarted). In the first `Update` after the server listens, `NetworkManager.SceneManager.LoadScene("Emberdelve_Level01", LoadSceneMode.Single)` is requested (from Update, not from the OnServerStarted callback, to avoid calling the scene manager from inside StartServer). NetBoot -> Level01 is the "how does the dedicated server get into Level01" answer; clients follow through NGO scene synchronisation.
2. Readiness is polled, not event driven: `GameServices.TryGet<RunDirector>` and `State == Running`. Then `ready scene=Emberdelve_Level01 players=0 senders=0 registry=B maxPlayers=N enemies=on|off` is logged. 60 s without it = server logs an error and refuses everybody with `server not ready`.
3. `ConnectionApprovalCallback`: the class list lives in the RunDirector (scene), so an approval that arrives before `ready` is HELD with `response.Pending = true` and decided (then `Pending = false`) when ready. That is what keeps the U3A1 flow (client launched right after `listening`) working. The host's own approval is never held. Seats count approved connections (`_approved`), reserved at approval; a seat that never reaches `OnClientConnected` within 20 s is released (`reservation expired`) so a client killed during scene sync cannot leak a seat. Log: `approval id=.. approved=.. slot=.. class=.. reason=..` (U3A1 format kept).
4. `OnClientConnected`: `RunDirector.TrySpawnNetworkPlayer(prefab, classId, locallyControlled: clientId == host, ...)` first, then `NetworkObject.SpawnAsPlayerObject(clientId, true)`. Any refusal destroys the half-made rig and disconnects the client with the reason. Log: `admitted client=<c> id=<playerId> party=<p> slot=.. class=.. netId=.. players=P senders=S registry=R`.
5. `OnClientDisconnect`: `RunDirector.RemovePlayer(id, "disconnect")` then despawn (destroy if still spawned). Log `removed client=<c> id=<p> slot=.. reason=disconnect players=.. senders=.. registry=..`. The row is removed from the table first, so the call is idempotent.
6. Status line every 2 s: `status players=N senders=N registry=N clients=N ready=bool`. On shutdown every remaining actor is removed before NGO stops, then `shutdown players=0 senders=0 registry=0` (real counts, not constants) precedes `shutdown complete clean=True ...`.

### Client logs
- `owner id=<n> views=<k> owned=1 class=<c> party=<p> ids=a,b` is written when the view picture has been stable for 0.75 s and again whenever the settled picture changes (a player joins or leaves), so views=2 and the later drop are both visible. `<n>` is the owned rig's replicated server id (`PlayerRig.SetNetworkPlayerId`, already applied by `NetPlayerRig`).
- `view despawned id=<n> ...` when any view disappears (also during the client's own shutdown).
- Refusal: `rejected reason='<reason>'` from `NetworkManager.DisconnectReason` (U3A1 code), exit 11.

### Forged-owner test RPC
`NetPlayerRig.ForgeOwnerTestRpc(int probe, RpcParams rpcParams = default)`, `[Rpc(SendTo.Server, RequireOwnership = false)]`, compiled only under `DEVELOPMENT_BUILD || UNITY_EDITOR`. The handler compares `rpcParams.Receive.SenderClientId` with `OwnerClientId`: a mismatch logs `REJECT forge-owner count=<n> target=<id> owner=.. sender=.. senderPlayer=player#<id> probe=<target's probe>` and returns without touching anything; the owner's own call writes `TestProbe` and logs `forge-owner self-call accepted`. `--ember-net-script=forge-owner` makes the client (once it sees another player's view) call it twice on that player's object and once on its own. The parameter is a free number, no identity. The gate also scans `Net/*.cs` and fails if any `[Rpc]` parameter list names a player/combat/party/sender/actor id. There is no RPC that reaches combat authority, so "a sender-bound authority command from the forged path" is unreachable by construction (no combat RPC exists yet; U3B's first one must resolve the sender with `NetIdentityTable.ResolveSender`).

### Build and gate
- `EmberdelveWindowsBuild.BuildNetProofPlayer`: scenes are now `[Emberdelve_NetBoot, Emberdelve_Level01]` (NetBoot stays index 0 = start scene), and it calls `EmberdelveNetBuilder.EnsureNetPlayerPrefab` (prefab + catalog must be in `Resources` for the player build) and fails clearly when Level01 is missing. Lobby builds and `BuildReview` untouched.
- `EmberdelveNetAdmissionGate.Run()` (`Emberdelve.EditorTools`): process based, same harness as the NetProof gate (`-ember-proof-dir`, `-ember-proof-reuse-exe`, only own PIDs, a timeout kill or surviving PID is a failure, `EditorApplication.Exit` only in batch mode). Final line `[Emberdelve][NetAdmission] PASS|FAIL checks=N failures=M`. Child logs in `<runDir>/logs/{server,client_a,client_b,client_c,client_dup,client_badclass,client_d}.log`.
  Scenario: server `--ember-net-max-players 2 --ember-net-no-enemies --ember-net-disconnect-timeout-ms 4000`, wait `ready` (players=0 senders=0 registry=0); A warrior admitted (counts 1/1/1); B archer + forge-owner admitted (2/2/2), distinct ids and client ids, each client `owner id=<its server id> views=2 owned=1`, ids lists equal, classes right, neither claims the other's id; forged calls rejected (count=2, target=A, sender=B, A's probe 0), B's own call accepted, nothing removed; C refused `server full`, duplicate slot (`adm-a`) `duplicate slot`, class `necromancer` `unknown class` (each: client exit 11, `rejected reason='..'`, server refusal line, never `connected`), totals 2 approvals / 3 refusals / 2 admissions; B hard-killed with `Process.Kill`: server `removed ...` within 20 s with counts 1/1/1, A logs `view despawned id=<B>` and settles on views=1; D (new slot) admitted with a new id and counts 2/2/2 (cap freed), D and A see each other; A and D leave by quit file (exit 0, clean), server removals end at 0/0/0; server quit file: exit 0, `shutdown players=0 senders=0 registry=0`; forbidden patterns absent in every log; all PIDs gone; source scan for identity RPC parameters.
- `EmberdelveNetProofGate` (U3A1): checks unchanged; only the connect windows were widened (client connect timeout 20 -> 40 s, wait for A's `connected` 40 -> 60 s) because a client now synchronises the dungeon scene before it counts as connected.

## Decisions
1. Approvals before the dungeon exists are held (Pending), not refused: keeps the U3A1 gate valid and needs no "not ready" retry in clients.
2. Seats are reserved at approval time (in `NetServer`, not derived from NGO's connected list) so two simultaneous joiners cannot both take the last seat or the same slot; stale reservations expire.
3. Request faults (class, slot) are reported before "server full" so a full server still tells a bad client what is wrong, and the gate can test duplicate / class refusal while the cap is reached.
4. Readiness by polling `RunDirector` state instead of NGO's `OnLoadEventCompleted` (less signature risk).
5. `SpawnAsPlayerObject(clientId, destroyWithScene: true)`.
6. Class id on the wire is a `FixedString32Bytes` NetworkVariable (24 chars max); the string is only a label on clients.
7. No-enemies is a process switch (`NetRole.EnemiesDisabled`) applied by `NetSceneRoles` before Awake, so enemies never register (registry == players in the proof).

## Verify first when compiling / uncertainties (nothing here was compiled)
1. `NetworkVariable<FixedString32Bytes>` (NGO should serialise FixedString types; if the ILPP complains, switch `ServerClassId` to a `NetworkVariable<int>` index into the approved list or an `INetworkSerializable` wrapper). Used members: `new FixedString32Bytes(string)`, `.ToString()`.
2. `[Rpc(SendTo.Server, RequireOwnership = false)]`, `RpcParams rpcParams = default`, `rpcParams.Receive.SenderClientId` (first use of the 2.x Rpc API in the project; the method name must end in `Rpc`).
3. `NetworkManager.ConnectionApprovalResponse.Pending` held and released later (`response.Pending = false` after setting `Approved/Reason`). If NGO 2.7 does not poll held responses, the first clients would hang until their connect timeout; the fallback is to refuse with a retryable `server not ready`.
4. `NetworkManager.DisconnectClient(ulong, string)` (reason overload), `NetworkManager.SceneManager.LoadScene(string, LoadSceneMode)` returning `SceneEventProgressStatus`, `NetworkObject.SpawnAsPlayerObject(ulong, bool)`, `NetworkObject.Despawn(bool)`, `NetworkObject.IsSpawned`.
5. Scene management: server `OnClientConnectedCallback` is expected after the client finished synchronising; `ConnectionApproval` + `EnableSceneManagement` + a player spawned after connect (not by `CreatePlayerObject`). If the player spawn races the client's scene sync, the symptom is a client without its own view; move spawn into `SceneManager.OnSynchronizeComplete`.
6. Ordering on disconnect: NGO may destroy the player object before or after our `OnClientDisconnectCallback`. `NetServer` handles both (RemovePlayer first, despawn only if still spawned), and `PlayerRig.OnDestroy` unregisters anyway.
7. `NetworkManager.DisconnectReason` content for a refusal (U3A1 relied on it already; it must now equal the exact reason string, e.g. `server full`).
8. Level01 must be re-built with this tree's slice (`Net_SceneRoles` is not in the saved scene in git): the server needs it to deactivate the scene rig and `Enemies`.
9. Host in the Editor is still deferred (no Editor launch switch); the host path in `NetServer` (own player via `locallyControlled`) is untested.
10. The gate's absolute `registry=0` relies on enemies being the only non-player combat entities (true in the current code: only `EnemyAgent` and `PlayerRig` register).
