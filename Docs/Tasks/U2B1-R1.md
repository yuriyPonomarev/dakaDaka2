# U2B1-R1 — scale-independent grid alignment (code saved; all Unity/compile checks pending manager)

- Changed file (only): `Assets/Emberdelve/Runtime/Data/AffixDefinition.cs` — `AffixBandRules` alignment/integrality internals. No test, gate, asset, scene, consumer or API signature touched; `Epsilon`, `IsFinite`, `NearlyEqual`, `IsIntegral`, `TryValidateBand`, `TryValidateValue` and the `AffixDefinition` Inspector/validation surface are unchanged.
- New policy: grid alignment is decided in **fractions of one step**, never as a relative tolerance on the index. `TryGridIndex` computes `n = Round((upper-base)/step)` and requires `|(upper-base) - n*step| / step <= AlignmentAllowanceInSteps(base,upper,step)`, where the allowance is the representation budget of the inputs actually supplied (`1e-6` relative for a value that is exactly a float, i.e. Inspector-authored float widened to double — 2^-24 = 5.96e-8 plus headroom; `8e-15` for a full double input, 2^-53 plus arithmetic headroom), times `|base|+|upper|+|upper-base|`, divided by the step. Acceptance therefore implies residual <= allowance <= `MaxAlignmentSteps` = 1e-2 of a step, for **any** index size.
- Unvalidatable grids are refused, not waved through: if the endpoints' own representation error already exceeds 1e-2 of a step (e.g. float-authored 0.03f..0.12f with step 1e-5f, budget 0.024 steps), or `|span/step| > MaxValidGridIndex` 4.5e15 (2^52, past exact double integers), the reason says the grid cannot be validated at that precision. No rounding, clamping or mutation of any input.
- Reproducer now rejected: pure doubles `min=.03, max=.12, step=1e-7, value=.08000005` — band still validates (residual 0 steps, budget 1.9e-8 steps), value alignment gives index 500000.5 -> n=500001, residual **0.5 steps** vs budget `8e-15*0.16/1e-7 = 1.28e-8` steps -> rejected as off-step. A legitimate fine-grid point `value=.08` (residual 6.7e-11 steps) is still accepted, so tiny steps are validated, not excused.
- Legitimate float bands keep passing by the same rule: 0.03f..0.12f step 0.01f band residual 6/10737418 = 5.59e-7 steps vs budget 2.4e-5 steps (43x margin); rolled 0.08f residual 1.86e-7; 0.1f..0.4f step 0.1f residual 0; integer attribute/HP/mana/armor/damage bands residual 0. Half-step off-step values (gate's `low + step*0.5`) residual ~0.5 steps -> rejected.
- `IsIntegral` made scale-consistent with the same budget (residual to nearest whole <= that value's own representation error, `>= 1e-6*max(1,|v|)`): float-authored whole numbers unchanged, `1e9+0.5` no longer passes as whole. Range, prototype-containment, non-finite, integrality-of-attributes, category and catalog rules untouched.
- Actual checks performed: none executed (file tools only, no Unity/tests run). Verification here is hand arithmetic on IEEE-754 values of the gate's 13 authored bands and the reported reproducer; **all 163 gate checks and the focused re-run remain pending manager**.
- Remaining limitations: the float-vs-double budget is inferred from whether each input is exactly a float value, so a double that is exactly a float gets the looser float budget; a designer wanting a step finer than ~1e-2-of-a-step's representation floor on a given band must author it as full-precision doubles (or the band is refused); no gameplay/roll consumer exists yet, so no runtime evidence of these rules.
