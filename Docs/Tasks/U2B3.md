# U2B3 — seeded weighted loot roller (code saved; every compile/behaviour check pending manager)

- Added only `Assets/Emberdelve/Runtime/Items/LootRoller.cs` (`public static class LootRoller` + private nested `Candidate` grid record). No existing runtime consumer, inventory/equipment/UI, builder, scene, asset, gate, package or `.meta` touched; no `.meta` written (Unity import creates it).
- APIs: `LootRoller.TryRoll(ItemData definition, int quantity, AffixRarity rarity, ItemInstanceAuthority authority, System.Random random, ItemIdentityIssuer issuer, out ItemInstance instance, out string reason)` and the mint-free core `LootRoller.TryRollAffixes(ItemData definition, AffixRarity rarity, ItemInstanceAuthority authority, System.Random random, out AffixRecord[] records, out string reason)` (same consumption order, so a roll and this helper report identical records; nothing is minted or built).
- Pre-RNG gates, in order: null random/issuer/authority/definition → stable item id → `authority.TryResolveItem` **and** `ReferenceEquals(trusted, definition)` (same trusted-definition gate as the accepted creation boundary) → `AffixRarities.TryExpectedAffixCount` (Common 0 / Uncommon 1 / Rare 2, `(AffixRarity)3` refused) → carrying/quantity rule (worn gear exactly 1, carried 1..`ItemData.StackLimitForFootprint`; mirrors `ItemInstance`'s private rule, and the issuer re-checks it as final authority) → for rarity>0: `IsEquippable`, `authority.TryCategory` and `AffixCategories.IsSingle`. Common consults no affix pool and consumes no randomness.
- Eligibility/sampling: pool is built from `authority.AffixDefinitions` only (no caller candidate list, no caller-named stat key); every entry is re-validated at the use boundary with `AffixDefinition.TryValidate` plus an explicit finite-positive-weight check, so a weight/band/category edited after the authority was built is a refusal naming that entry rather than a stale value or a silently shrunk pool; category mismatch is the only legitimate exclusion; duplicate id or two eligible definitions for one stat key is refused. The pool is a **copy** sorted by `string.Compare(..., Ordinal)` id (catalog order/asset order never changed), so re-ordering the catalog cannot alter a seeded result. `pool.Count < expected` → false, count is never lowered, and the draw loop runs exactly `expected` times (an exhausted pool is a refusal, never a retry or infinite loop).
- Weighted pick without replacement: one `random.NextDouble() * total` ticket per affix, `total` and the cumulative sums accumulated as doubles in identical order over the still-unused entries (so the running sum ends exactly at `total`); picked entries are marked used, and distinct stat keys are guaranteed because the pool holds one entry per key. Grid draw: whole index in `[0, kMax]` inclusive of both authored endpoints — `kMax` recomputed with the accepted `AffixBandRules` alignment method (residual in fractions of one step vs `AlignmentAllowanceInSteps`, bounded by `MaxValidGridIndex`/`MaxAlignmentSteps`), an unrepresentable or off-grid band is refused before RNG; `random.Next((int)gridCount)` when the grid fits an int, a clamped `NextDouble`-scaled index only for an absurdly fine grid, no draw at all for a single-value band; value = `min + index*step` in double, widened to `float`, then re-checked by `AffixDefinition.TryValidateRolledValue(value, category)` before it becomes an `AffixRecord`, so nothing the instance path would refuse leaves the roller.
- Failure/mint behavior: any failure returns false + one reason + null `instance` (and null `records`) and mints nothing; final construction is only `issuer.TryCreateInstance(trusted, quantity, rarity, records, authority, …)`, which re-validates everything and mints exactly one UID after that, so `MintedCount` is unchanged by a refused roll. Same seed + same catalog + same request ⇒ identical affix ids, order and values; UIDs intentionally differ per created item. No `UnityEngine.Random`, no global seed, no clock reseeding, no fallback generator, no clamping/reroll; definitions and catalog lists are only ever read (fixed item properties untouched). Copy/restore/export were not modified and do not call the roller.
