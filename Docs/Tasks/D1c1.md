## Per item

1. `IsSwingInProgress` lag. It no longer reads the record's `Phase` alone: a swing that has a record is in progress while `Now - StartTime < end`, where end = `Timing.Total`, or `StopTs + WallRecoil` after a wall stop. It flips at the swing's end time with no step in between (the record's `Phase == Finished` still means over). Death and weapon change are still noticed by the next step (events, not time). `LocalCombatAuthority.Swings.cs`.
2. A-B-A swap. New optional contract `IWeaponChangeSource { int WeaponChangeCount }` (`Core/GameContracts.cs`). `ClassLoadout.WeaponChangeCount` goes up in every `Equip`; `PlayerRig` implements the interface and forwards it. The authority stores the counter in `ChainState.WeaponEpoch` and `SwingRecord.WeaponEpoch` at the accepted begin and compares in `ChainIsLive`, `ChainAllows` (new reason "the weapon changed since combo step N..."), `ForgetDeadChains` and `StepSwing` (swing ends as `WeaponChanged`). Entities that do not implement the interface report 0, so every existing fake keeps the old identity comparison.
3. Held factor vs the walk clamp: NOT changed (reason below).
4. Pruning. `PruneEntityState()` runs at the top of `StepSwings()` (every FixedUpdate and every gate step). It removes `_lastSwingFloor` and `_chains` entries whose id is no longer in `CombatRegistry`, and `_guardBrokenUntil` entries that are expired, belong to a dead entity or an unregistered id. Live entities are untouched. Deliberately NOT pruned: `_lastAttackTime`, `_lastSequence`, `_skillStamps` (main file; they are the cooldown / replay memory, and `PlayerRig`/`EnemyAgent` unregister in OnDisable, so pruning would reset the cooldown on a disable/enable). `_swingsById` was already bounded (FinishedSwingMemory). Internal observability: `SwingFloorEntryCount`, `ChainEntryCount`, `GuardBrokenEntryCount`. Note: there is no unregister hook in the authority (the registry is a static table), so pruning is "on step"; it takes effect at the next step after the unregister.
5. `EmberdelveInput` overrides (`MoveOverride`, `SprintHeldOverride`, `SecondaryHeldOverride`, `PrimaryPressed/Held/ReleasedOverride`, and the older `InteractHeldOverride`) are now `internal`. All users (grep over Runtime, UI, Review, Editor) are Editor gates (CombatFlow, MultiPlayer, ProjectileBlock, RuntimeSmokeTest); none in UI/Review. The Editor assembly sees them through `InternalsVisibleTo("Emberdelve.Editor")` declared in `LocalCombatAuthority.cs` (Emberdelve.Runtime). Risk: if any Editor code outside these four files or a reflection call used them, it would fail to compile; the grep found none.

## Item 3 analysis (why unchanged)
The walk clamp `[2, 8]` lives inside the attribute rule (`AttributeRules.ResolveMoveSpeed`, or the precomputed `EffectiveStatsSnapshot.WalkSpeed`), i.e. inside `ResolveWalkSpeed`, which D1b says must stay untouched; sprint/crouch have no clamp at all ("authored base retained"). `ResolveGroundSpeed` multiplies the result by guard, speed penalty, status and the flow factor (held x authority), all `<= 1`. The max cap of 8 therefore cannot be exceeded by the later multiplication; what "after the clamp" changes is only the lower bound (walk can end below 2 with penalties). Moving the held factor before the clamp would (a) need the factor injected into the attribute rule and the snapshot path, changing `ResolveWalkSpeed`/`BaseMoveSpeed` (used for dash/sprint ratios), (b) turn the floor 2 into a raise above rule x held for low-speed builds, and (c) change literals asserted in AttributeAction/AttributeVitals/NumericAffix/CombatFlow gates for any case near the floor. Unclear intent, so left as is. One check documents the cap (`ground speed <= rule speed <= 8`). If the owner wants the floor applied after the held factor, say so and the listed gates need review.
