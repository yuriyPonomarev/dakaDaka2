## Root cause (read from the real runtime, not assumed)
`PlayerRig.Awake` → `WireRig` Ensures `ManaComponent`, `StaminaComponent`, `StatusComponent`, `Equipment` and adds the
`SkillCaster`; `SkillCaster.Awake` then `ManaComponent.Ensure(gameObject)` finds that same pool. The old gate then ran
`AddComponent<ManaComponent>` and `AddComponent<StatusComponent>` on top of them — neither type has
`DisallowMultipleComponent`, so a second pool and a second status set existed for certain — and wrote them into
`rig.mana` / `rig.status` with `SetReference`. `AddComponent<SkillCaster>` / `AddComponent<Equipment>` (both
`DisallowMultipleComponent`) cannot add a second instance, so those locals were null and `rig.skills` / `rig.equipment`
were only rescued by the explicit `rig.WireRig()` re-resolve afterwards. Result: `SkillCaster.mana` spent the rig's real
configured pool while `rig.Mana` pointed at the duplicate whose `Awake` left it unconfigured (default 100, `_configured`
false so its `Update` regen never runs) → the observed mana delta 0 vs 24, later "not enough mana" rejections, and
`PlayerMovement._status = GetComponent<StatusComponent>()` reading the first status set while `rig.Status` reported the
second → the cascade.

## Dash distance vs the 24 m/s cap — inspected, no fixture change proposed or made
`DashBehavior.Cast` → `TryStartDash(dashDistance * scale, dashDuration * scale)`; `TryStartDash` clamps duration to
[0.05, 2], distance to [0.5, 20], then `_dashSpeed = min(meters / seconds, 24f)`. Authored 4.6 / 0.22 = **20.909 m/s at
every scale** (scale 1.16 → 5.336 m / 0.2552 s; scale 1.40 → 6.44 m / 0.308 s — both still 20.909 m/s), so the cap and
both clamps are not reached and the existing distance expectation is arithmetically consistent with the runtime.
`MoveDash` asks `controller.Move(_dashDirection * _dashSpeed * dt + gravity)` per frame and ends the dash on a side
collision, so covered ground = speed × asked duration ± at most one frame of overshoot (≈0.35 m at 60 Hz, ≈0.70 m at
30 Hz), which is inside the existing 0.9 m `DistanceTolerance`. No runtime movement code was changed and no tolerance
was widened. If the manager's run still misses a distance assertion after this ownership fix, the honest next question is
the real frame rate / a blocked `controller.Move`, not the authored numbers.
