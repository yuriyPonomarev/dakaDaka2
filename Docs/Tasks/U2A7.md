# U2A7 — builder uses the rig-owned vitals and kit

## Files changed
- `Assets/Emberdelve/Editor/EmberdelveLevelBuilder.cs` — `BuildPlayer` only (component block + the `SetReference` block). No runtime, gate, scene, asset, package or other builder change; no scene regenerated.
- This report.

## What changed
Ownership of the five rig-owned vitals/kit components moved from "the builder adds its own copies" to "the builder resolves them the way `PlayerRig.WireRig` does":

Before (`EmberdelveLevelBuilder.cs` 343..350):
`rigGo.AddComponent<ManaComponent>()`, `AddComponent<StatusComponent>()`, `AddComponent<SkillCaster>()`, `AddComponent<Equipment>()` — unconditional adds, no stamina at all, and none of the five was ever handed to the rig.

After:
- `ManaComponent.Ensure(rigGo)`, `StaminaComponent.Ensure(rigGo)`, `StatusComponent.Ensure(rigGo)`, `Equipment.Ensure(rigGo)` — the same static Ensure APIs `PlayerRig.WireRig` (lines 120..127) uses: `GetComponent` first, `AddComponent` only when nothing exists. `SkillCaster` uses the exact `WireRig` shape (`GetComponent`, then `AddComponent` if null) because `SkillCaster` has no `Ensure`.
- The five locals are kept and now feed `SetReference`: `rig.mana`, `rig.stamina`, `rig.status`, `rig.skills`, `rig.equipment` are serialized on the saved scene rig, in the same order the accepted U2A5 fixture wires them (`mana, stamina, status, skills, inventory, equipment, loadout` after `health`). Existing wiring for `input/movement/look/health/inventory/loadout`, `loadout.*`, `melee/ranged/interactor/hotbar` is untouched.
- Component display names preserved (`Mana`, `Status`, `SkillCaster`, `Equipment`) plus `Stamina` for the newly serialized pool.
- `rig.WireRig()` is **not** called from the builder: camera/combat/look wiring is still incomplete at the point the components are created, and `WireRig` would allocate a `CombatRegistry` id and subscribe health/mana events in edit mode.

## Why this is the correct fix
`PlayerRig` already owns these components: `WireRig` Ensures mana, stamina, status, equipment and the caster, and `SkillCaster.Awake` Ensures the same `ManaComponent`. Unconditional `AddComponent` in the builder therefore produced a second pool / second status set / second caster whenever Awake had already run — the exact failure mode U2A5-R5/R6 had to fix in the gate fixture (`EmberdelveAttributeSkillGate.BuildRig` now uses the identical Ensure pattern, and `CheckRigComponentOwnership` counts `GetComponents<T>() == 1` and compares rig/caster/melee/ranged references by identity). The builder now matches that pattern instead of contradicting it.

Stamina is included because `PlayerRig` already has `[SerializeField] private StaminaComponent stamina`, `StaminaComponent.Ensure` and `WireRig` wiring for it; previously the scene rig had **no** serialized `StaminaComponent` at all — it only appeared at runtime when `WireRig` added one.

## Edit-mode vs play-mode initialization
- Edit-mode build (the normal path, `EmberdelveLevelBuilder.Build` → `NewScene` + `AddComponent`): Awake does not run for these components (the U2A3-R2 finding), so `Ensure` is what puts all five on `Player_Rig`, and the new `SetReference` calls write the rig's serialized references into the saved scene. The scene rig is therefore fully wired before play mode, with exactly one instance of each.
- Play mode after that scene loads: `PlayerRig.Awake → WireRig` finds every serialized reference non-null, adds nothing, and only then registers the combat id and subscribes health/mana events — unchanged runtime behaviour.
- If the builder ever runs where Awake already ran, `Ensure`/`GetComponent` resolve the components `WireRig` created instead of adding duplicates.
- Authored values unchanged: `StaminaComponent`'s serialized defaults (100 / 5 / 0) are the same field initializers `WireRig`'s runtime `AddComponent` used, `Awake` still fills the pool once, and `ClassLoadout`/`InitializeVitals` still configure the pools from the class + attribute derivation. No pool, skill, stat-rule, HUD or scene-YAML edit.
