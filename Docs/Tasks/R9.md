# R9: versioned, validated, atomic container snapshot for bag + equipment (F9)

## Verified starting point (HEAD 88e7fa63)
- `ItemSnapshot` (JsonUtility DTO) and `ItemInstance.TryRestore/TryValidateSnapshot` were already strict and all-or-nothing for one item. `ItemCatalog.TryRestore/TryRestoreAll` resolved by id; `Inventory.TryAddSnapshot` placed one restored instance. Nothing described a whole container.
- Gaps (F9): no schema version, no container format (cells, carried stacks without a uid, equipment slots), no duplicate-uid check across a set or across containers, fractional affix values (move_speed 0.01 step, mana_regen 0.1 step) never went through JSON, and JsonUtility silently defaults a missing `rarity` to Common and ignores unknown fields.
- Item/affix validation (uid shape, rarity vs affix count, ids, keys, bands, steps, category, gear quantity 1) lives in `ItemInstance`; it is reused, not copied.

## Schema (schemaVersion 1)
`ContainerSnapshot` (`Runtime/Items/ContainerSnapshot.cs`), canonical compact JSON, fixed member order:

```
{"schemaVersion":1,"kind":"bag","containerId":"bag","width":10,"height":6,
 "entries":[
   {"slot":"","x":2,"y":0,"item":{"uid":"<32 hex>","itemId":"footpad_boots","quantity":1,"rarity":2,
      "affixes":[{"id":"affix_move_speed","key":"move_speed","value":0.09}, ...]}},
   {"slot":"","x":0,"y":3,"item":{"uid":"","itemId":"ember_coin","quantity":8,"rarity":0,"affixes":[]}}],
 "checksum":"sha256:<64 lowercase hex>"}
```
- `kind`: `bag`, `equipment`, `stash` (stash is reserved for U4C, validated like the bag). `containerId`: stable id (`bag`, `equipment`; container ids must be unique per profile).
- Grid kinds: width/height 1..64, each entry has an origin cell `x,y` and `slot:""`. Equipment: width=height=0, each entry has `slot` = exact `EquipmentSlot` name (`Weapon`, `OffHand`, `Head`, `Chest`, `Legs`, `Back`) and `x=y=0`.
- Entries are the whole `ItemSnapshot` shape: gear = uid + itemId + quantity 1 + rarity + rolled affixes `{id,key,value}`; carried stacks (coins, potions, arrows, relics) = itemId + quantity with `uid:""`, rarity 0, no affixes. Affix order is the instance's own order.
- Canonical order: grid entries by (row, column), equipment entries by slot number. `Seal()` sorts and writes the checksum, and the validator REFUSES entries that are not in canonical order. Input must also be canonical text: `TryFromJson` (container and loadout) refuses any current-version document whose re-serialization differs byte for byte from the input (extra whitespace, `` escapes, member order, `9e-2` or `0.120` for `0.12`, `-0`, a BOM), so an accepted current-version document has exactly one byte form. A writer on another runtime that spells a float differently is refused as non-canonical (U4C: the server writes through this same code).
- Cap: `MaxEntries` = 512 per container, document size 2 MiB, JSON nesting 12, affix array 8 at parse level (the rarity rule 0..2 is enforced by validation).

`LoadoutSnapshot` (`LoadoutSnapshot.cs`): `{"schemaVersion":1,"bag":<container>,"equipment":<container>,"checksum":...}`; the checksum covers both container documents including their own checksums.

### Versioning
`CurrentSchemaVersion = 1`, `MinSupportedSchemaVersion = 1`. A newer version (2, 99, int.MaxValue) is always refused; an older one (0, negative) is refused unless a migration chain is registered (none is). In-memory snapshots must be exactly the current version. Migration chain (`ContainerSchema`, order enforced and tested with a registered dummy v0 step): (1) the ORIGINAL document is verified under the OLD version's own checksum rule (`MigrationStep.VerifyIntegrity`; `TreeChecksum` = SHA-256 of the compact tree without its checksum member), (2) the tree is rewritten one version at a time (`MigrationStep.Upgrade`), (3) the migrated tree is read by the current strict reader and RE-SEALED with a fresh current-version checksum; the canonical-bytes rule applies only to documents that were already current. The loadout wrapper and its containers share one version number, so they migrate together; a current wrapper around an older container is refused. Migration only changes in-memory data, never a file.

### Checksum scope and its limits (honest)
Unkeyed SHA-256 over the canonical JSON of everything except the checksum field (`sha256:` + 64 lowercase hex). It is TAMPER EVIDENCE, not security: it catches corruption and casual edits (a changed value, a swapped uid, a duplicated entry, a stale checksum, wrong order). Anyone who can edit the file can recompute it, so it proves nothing about authorship. The real defence is that the profile/stash is server-owned storage written only by server code, and every restore re-validates content against the trusted catalog (ids, keys, bands, steps, categories, counts, quantities, placement, uid uniqueness). Authenticating a profile (signing with a server key, binding to an account) is not done here.

### Unknown-fields policy: REJECT
Unknown, missing and repeated members, wrong types (a string for a number, `1.5`/`1e0` for an int), `null` where a number belongs, NaN/Infinity/overflow, leading zeros, trailing commas/garbage, raw control characters, bad escapes are all refused (`StrictJson`). A missing `rarity` is a refusal, not Common.

### JSON and floats
`StrictJson.cs` is a small RFC 8259 reader and writer, not JsonUtility. Every number uses the invariant culture; a float is written as round-trip text (`"R"`, with a `"G9"` fallback and an explicit `-0`): bit-exact, but the exact spelling is runtime-dependent, so nothing relies on it: the checksum hashes exact float BIT PATTERNS (`bits:xxxxxxxx`), not the text (tested with a different formatter: text changes, checksum does not). `0.09` is `0.09` under ru-RU and de-DE, where `0.09f.ToString()` really is `0,09` (the gate asserts that, so the culture is proven to be in effect). Non-finite values have no spelling; the writer emits `null`, which every reader refuses.

## Validation (all-or-nothing)
`ContainerSnapshotValidator.TryValidate(snapshot, catalog, others, expectedKind, out ValidatedContainer, out reason)`: the result is either a fully resolved container (catalog definitions, restored `ItemInstance`s) or null + ONE reason; nothing is mutated. Order: null, schema version, kind (and expected kind), container id, grid shape, entries present and under the cap, checksum present/shaped/matching, then per entry: unknown item id (catalog), position vs slot rules, gear through `ItemCatalog.TryRestore` (uid, rarity/affix count, unknown/foreign affix, wrong id/key pair, non-canonical key, non-finite/out-of-band/off-step value, disallowed category, duplicate affix, quantity 1), carried stacks (no uid/rarity/affixes, quantity 1..stack cap via the now-internal `ItemInstance.TryValidateQuantity`), duplicate uid inside the snapshot, equipment slot rules (item belongs in that slot, one item per slot, no stacks, no cell), grid rules (inside the grid, no overlap, footprint from the definition), canonical order, finally uid collisions against `others`.

`ItemUidRegistry` (`ItemUidRegistry.cs`): the per-profile ledger the future stash uses. `CanHold(owner, uids)`, atomic `TryReplaceOwner`, `ReleaseOwner`, `Contains/TryGetOwner`, and `TryRegisterSnapshot(snapshot, catalog)` = validate with the ledger as the "held elsewhere" set, then register. A uid held by a different container is refused; the same owner may re-register.

## Inventory / Equipment / Loadout integration
- `Inventory.ToContainerSnapshot()` (bag, id `bag`, kind bag), `Inventory.TryRestore(snapshot[, registry], out reason)`. Needs a catalog (a bag without one refuses), the snapshot grid must equal the bag's grid, a uid the player's equipment wears is refused. Commit replaces the stacks with the exact restored instances (same uid, rarity, rolled values, cells; no mint, no reroll), recomputes `TotalUnits`/`CarriedValue`; the run statistics (`LifetimeCollected`, `RecoveredValue`) are left alone.
- `Equipment.ToContainerSnapshot()` (id `equipment`, kind equipment), `Equipment.TryRestore(snapshot[, registry], out reason)`: catalog comes from its bag; refuses a uid the bag carries and a weapon item with no granted weapon. Commit hands every previously worn weapon back to the class, places the restored instances, applies weapon/shield hands like equipping, then `RefreshStats()` (the existing path: equipment stat source replaced wholesale, attribute rebuild from worn instances, `SetMax` only moves ceilings), so no free healing and no stat accumulation; events are raised after commit.
- `LoadoutSnapshot.Capture(bag, equipment)`, `LoadoutSnapshot.TryRestore(snapshot, bag, equipment, registry, out reason)` and `TryRestoreJson`. Validates the loadout checksum, then BOTH sections (each against the catalog and the ledger), then that the two sections share no uid, then commits both. A bad bag or equipment section, a shared uid, a stale checksum or an unsupported version changes neither container.
- Internal two-phase API (`TryPrepareRestore` validate, `CommitRestore` cannot fail) is what gives the atomicity.

## New gate: `Emberdelve.EditorTools.EmberdelveContainerSnapshotGate.Run` (954 checks)

Fixture: 5 worn pieces (Rare boots with 0.09 move_speed + 0.3 mana_regen, Uncommon cloak 0.07, Rare cuirass, Rare blade, Common shield) and a 10x6 bag with 3 more gear instances (a 0.12 move_speed boots, two Rare multi-cell items) and 5 carried stacks.
- Floats: 4017 floats (every move_speed/mana_regen grid point computed two ways, extremes, denormal, -0, 4000 pseudo-random bit patterns) write and parse back bit-exact with no comma under en-US, ru-RU, de-DE and the default; `0.09f` writes `0.09`.
- Rich loadout under en-US/ru-RU/de-DE: capture bytes identical, parse + re-serialize string-equal, wipe, restore, then bag + equipment are instance-equal (uid, rarity, float bits, cells), stats, totals and run statistics as expected; restore over a different state replaces it.

- Cross-container uid: ledger registers bag (3 uids) and equipment (8 total), refuses an equipment snapshot reusing a bag uid with the ledger unchanged, `CanHold`/atomic `TryReplaceOwner`/`ReleaseOwner`, stash-held uid refused by bag restore and loadout restore, worn uid refused by bag restore, carried uid refused by equipment restore, same uid in both loadout sections refused.

## Review fixes (Docs/Reviews/R9.md, ACCEPT-WITH-FOLLOWUPS)
- **M1 (placement overflow)**: the validator's bounds check is now `entry.x > width - size.x || entry.y > height - size.y` (width <= 64, size >= 1: cannot overflow, negatives refused first), and `Inventory.CanPlace` (pre-existing `origin.x + width > gridWidth`) uses the same form. Gate: `x`/`y` = int.MaxValue, MaxValue-1, MinValue, -1, width/height, width+1, and (for the 2-wide gear) width - sizeX + 1, for a 1x1 stack and for multi-cell gear; six gear entries parked at `x=int.MaxValue`; equipment entries with x/y = MaxValue/MinValue/-1; `CanPlace`, `TryAddInstanceAt`, `TryAddAt`, `TryMove` with overflow origins. Every case is refused with the live state unchanged. With the old comparison restored the gate fails (checked, see the mutation run).
- **M2a (one byte form)**: made true. `ContainerSnapshot.TryFromJson` and `LoadoutSnapshot.TryFromJson` refuse a current-version document whose re-serialization is not byte-equal to the input. Gate: `\u` escape, whitespace (everywhere, leading, trailing newline), member order, `1.2e-1`, `0.120`, `0.119999997` (same bits), `-0` integer, BOM, `+10`, integers above/below int range, loadout whitespace; the exact canonical text is accepted.
- **M2b (migration vs checksum)**: order fixed and documented above (verify original under the old rule, migrate, re-seal). Gate registers a dummy v0 -> v1 step: an intact v0 container and v0 loadout migrate to the original canonical bytes and restore; a v0 document edited after writing, or with a wrong checksum, is refused on the integrity check; version 2 stays refused; a current wrapper around a v0 container is refused; with the registry cleared v0 is refused again.
- **M2c (float spelling)**: the checksum now hashes exact float bit patterns, so it does not depend on how a runtime spells a float. The text claim is reworded (bit-exact round trip, runtime-dependent spelling). Gate: a different formatter (`G9`) changes the document text but not the checksum, and the re-spelled document is refused as non-canonical.
- **S1 (observers)**: restore is split into apply (no event) and notify. Loadout restore applies the bag, then the equipment (slots replaced before any hand or pool change can run a subscriber), and only then raises `InventoryChanged` once and the equipment events (removed items `false`, restored items `true`). Each raise is guarded, so a throwing subscriber is logged and cannot undo or abort an applied restore. Gate: a loadout in which two uids swap between bag and equipment, with a consistency observer on `InventoryChanged`/`EquipmentChanged` (never sees a uid both worn and carried or an old half state) followed by throwing subscribers: the restore still succeeds and the state is the restored one.
- **S2 (ledger)**: `Inventory/Equipment.TryRestore(snapshot, ledger, ...)` now also updates the ledger (atomic `TryReplaceOwner`) after a successful validation. `LoadoutSnapshot.TryRestore(..., ledger, ...)` validates against `ledger.WithoutOwners("bag","equipment")` and moves both owners with the new atomic `ItemUidRegistry.TryReplaceOwners`, so one ledger per profile (bag + equipment + stash) works when a uid moved between bag and equipment. Gate: ledger holding the old state accepts the swapped loadout and follows it, a refused loadout leaves the ledger untouched, a single-container restore that would contradict the ledger is refused, `TryReplaceOwners` refuses a uid in two owners or held by a non-replaced owner, `WithoutOwners` is a copy.
- **S3**: capture -> JSON -> wipe -> restore -> byte equality on the real production grid (10x4) with the real starting kit (`Inventory.GiveStartingItems(rig.Class.startingItems)`, the call `ClassLoadout.Apply` makes) before the fixture reconfigures the bag; the vacuous "parse touched nothing" checks were removed (the count is 954 independent checks; refusal cases that call a restore still assert unchanged state); BOM, `-0` integer, integer overflow cases added. `TryPrepareRestore` no longer calls `EnsureGrid()` (validation does not resize the cell array; `EquipmentPartner()` still caches the partner reference, which is benign).
- Also from the review's notes: `ValidatedContainer/ValidatedEntry` have internal constructors and internal setters (no hand-built "validated" container from outside); `ContainerSnapshot`, `ContainerEntry`, `LoadoutSnapshot` are no longer `[Serializable]`, so `JsonUtility` cannot silently bypass the strict format.

## Decisions worth knowing
- Plain `bag` restore requires the snapshot grid to equal the live grid instead of resizing the bag (a resize is a side effect that could drop items); the class config owns the grid size.
- `Inventory.RecoveredValue/LifetimeCollected` are run statistics, not content; a restore does not reset them.
- Restore does not check that the rig is alive: loading a profile is not a gear change by the player. If the server wants that rule, it belongs in the caller.
- `ContainerSnapshot.TryFromJson` is structural (strict parse + version); legality is `TryValidate`, run by every restore. A caller that only parses learns nothing about the checksum.

## Open follow-ups
- U4C: on-disk server stash/profile store, atomic file replace (write temp, flush, rename), per-profile file naming, backup of the previous version, recovery after a crash; it should serialize these snapshots and keep one `ItemUidRegistry` per profile (stash container id e.g. `stash`).
- Server authentication of a profile (signed container, account binding); the checksum is not that.
- Per-run issuer/authority (R4/H2): the bag still mints starting-kit and pickup Common instances through its own issuer; restoring does not change that, and a restored profile's uids are not yet registered with a run-level ledger.
- Stash restore into a stash container type (kind `stash` validates but no runtime class consumes it yet).
- A uid ledger is in-memory per process; cross-process uniqueness (two sessions) is the server's job.
- `ItemSnapshot.ToJson/TryFromJson` (JsonUtility) stays for single-item transfer and still has its documented weaknesses; nothing persisted should use it.
- A real v2 migration when the schema changes (chain, integrity-first order and re-seal exist and are tested with a dummy step; nothing registered).
- Not covered: dead-rig behaviour, weapons whose `grantedWeapon` is cleared after save (refused by `TryRestore`, tested by code path only), the UI refresh after restore (events are raised, no UI test).

### Later items from Docs/Reviews/R9.md (for U4C / U3)
1. U4C minimum: atomic file replace (temp, flush, rename), backup of the previous version, crash recovery, safe fixed per-profile file names; validate before writing (parse and `TryValidate` the exact text about to be written: `Capture` does not self-validate, so an unrestorable capture would otherwise be saved); read with an encoding that strips the BOM (the reader refuses a BOM); one ledger per profile with locking; stash container class consuming kind `stash`; extraction/death integration (what is banked, exactly once, alive/range/time) stays with the caller; server authentication and account binding (the checksum is not that).
2. Float spelling across runtimes (L1): the checksum hashes bit patterns, but canonical-only input means a document spelled by a different formatter is refused as non-canonical; the server must write through this same code, or the canonical spelling must be pinned by an own formatter.
3. Grid policy (L2): restore requires the snapshot grid to equal the live grid; a changed class bag size refuses every saved bag. Needs migrate / relocate / grid-in-profile policy.
4. Entry cap (L3): `MaxEntries` = 512 but `MaxGridDimension` = 64; a 64x64 stash can hold 4096 1x1 stacks. Size the cap for the stash.
5. Ledger (L4): per process and per profile, not thread-safe, no cross-profile uid index, no record of issued uids (a fabricated Rare with a fresh uid is accepted wherever the file is writable). Acceptable only because the store is server-owned; U3/U4 need a global uid ownership index, locking and issuance tracking.
6. Affix tolerance (L5, pre-existing): `AffixBandRules.TryGridIndex` allows about 1e-6 relative residual, so a tampered near-value (for example `0.0900001`) is accepted and stored verbatim; the bits of a valid roll are not unique. Consider exact-grid validation.
7. Run state (L6): `LifetimeCollected`/`RecoveredValue` are not restored and restore ignores whether the rig is alive; U4C/U3 callers must enforce "only in the lobby or at raid start".
8. The loadout and container schema versions share one constant (a container-only change bumps both). Slot names are persisted as text (`EquipmentSlot.ToString()`), so enum member names must stay frozen like the stored ints. `StrictJson` builds the whole tree before any per-array cap applies (a 2 MiB `[0,0,...]` allocates about 1M nodes before refusal): irrelevant while the store is server-written, relevant if clients ever upload. There is no asmdef split, so `internal` still means "whole Assembly-CSharp".
