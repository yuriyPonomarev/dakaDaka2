# U4B two-client extraction proof

> Historical implementation note. Current acceptance and remaining work: [CURRENT_WORK](../CURRENT_WORK.md) and [raid acceptance](RAID_UI_ACCEPTANCE_20261108.md). Status statements below describe the original slice.


This process gate starts a dedicated NGO server and two independent client processes. A development-only server fixture seeds recovered loot into A's inventory and places A at the real extraction point only after `ExtractionPoint.CanInteract` succeeds.

The gate then exercises the production owner hold bridge and server RPCs. A completes the hold, receives one server-authored `RunResult`, and replays completion after the lease is sealed. B invokes begin, heartbeat, complete and cancel on A's player object; sender identity must reject those calls. The gate compares every displayed result field with the server result and checks A's inventory revision and contents are identical before and after result presentation. The result cache is display state; this gate does not grant loot or persist a bank balance.

After success, the same gate starts separate two-client sessions for movement, nonlethal damage and lethal damage. Movement is sent through the regular owner movement stream and must exceed the server hold's 5 cm tolerance. Damage stimuli are development-only server fixtures that call `PlayerRig.ApplyDamage` with server-created `DamageInfo`; they exercise the normal `HealthComponent` event path, not the PvP damage RPC validation. Nonlethal damage must cancel the hold without creating a terminal result. Lethal damage must cancel the hold before `HealthComponent.Died`, then produce exactly one authentic `RunDirector` `Dead` result for A, never `Extracted`. After real death custody, A's owner snapshot is expected to become empty because the server clears the source only after transferring its loadout to the corpse; the gate checks that the corpse commit precedes the Dead result. Successful extraction keeps its separate unchanged-inventory assertion.

The gate now also runs a timeout session after the extraction/interruption scenarios. Its server-only `-ember-net-timeout-proof-server` fixture mints a distinct gear UID for each owner and applies a five-second process-local deadline after both join; it does not edit the shared GameConfig or enable the production countdown. Both owners must first receive an enabled server clock sample with the warning active, then receive its expired state. Both must receive `Dead` only after their exact UID is found in their own distinct in-memory corpse, and each UID must be absent from the other corpse. `ExtractionAllowed` must refuse both for the expired timer, and a third client attempting to join afterward must be refused by `RunDirector`. Because the connection is approved before the run scene can reject its player spawn, the client exits with `NetExitCodes.UnexpectedDisconnect` (13); the gate requires the exact timer-refusal log, `shutdown complete clean=True`, process termination, and exit code 13. It does not accept arbitrary nonzero exits. The gate asserts the production countdown asset setting remains false.

Run through `Tools/Run-EmberdelveGates.ps1` with `Emberdelve.EditorTools.EmberdelveNetExtractionGate.Run`, or add `NetExtraction` to a run set. Use a unique output directory; the gate builds a development proof player unless `-ember-proof-reuse-exe` points to a proof player built from the same source.

The gate covers success exactly once, foreign RPC rejection, owner-only result delivery, no client inventory payout, server-observed movement/damage/death interruption, and timeout finalization/corpse custody/late-join rejection. The timeout case also checks replicated owner countdown warning and expiry, not just the server deadline. NetExtraction passed **136/0** at `DakaDaka_ci/Logs/focused-net-extraction-r5-20261106/summary.json`. This proves runtime delivery and server deadline behavior, not visual HUD usability. It does not cover persistent stash banking or opponent attack RPC validation as the source of interruption damage.
