## Binding model
`HotbarBindings` (plain C# class, one per Inventory, lazy via `Inventory.Hotbar`, `[NonSerialized]` so a cloned rig gets its own) holds `ulong[4]`, 0 = empty. Reads validate against the live bag (`StackIdAt` returns 0 when the stack retired), so a retired binding is empty immediately even before pruning. Because StackIds are monotonic and never reused (Inventory.AllocateStackId; Clear does not reset the counter; restore allocates fresh IDs), a retired ID can never come back or be inherited. API: `StackIdAt`, `TryGetStack`, `SlotOf`, `TryAssign(slot, stackId, out reason)`, `TryUse(slot, out reason)`, static `IsUsableDefinition(ItemData)` (healAmount > 0 or ammoGrant > 0, the same two things `LocalInventoryAuthority.UseStack` applies), `HasSeeded`; internal `RetireAll`, `SeedDefaults`.

- Key use: `TryUse` -> `Inventory.TryUseStack(stackId)` -> same Use command as TryUseSlot (TryCreateLocalCommand with SourceStackId, ExpectedSourceGearUid = instance uid or Empty, then Submit(_rig, ...)). Retired/empty slot: returns false, nothing submitted, no fall-through. Partial use keeps the StackId, so the binding stays.
- Default rule: `SeedDefaults` (first <=4 usable stacks in bag order) runs at the end of `Inventory.GiveStartingItems` (before the final InventoryChanged) and in `Inventory.ApplyRestore` (covers `Inventory.TryRestore` and `LoadoutSnapshot.TryRestore`; no event raised there, NotifyRestore's InventoryChanged refreshes the HUD). `Clear()` retires all.
- Refill rule (documented in class doc): NO auto-refill mid-raid. A newly appearing stack is a different identity from what the player last saw on that key; only explicit `TryAssign` binds. One safety net: `HotbarController.Update` seeds once if `!HasSeeded` (a bag whose loadout hook never ran); Clear/restore/GiveStartingItems/TryAssign all mark it seeded.
- `TryAssign`: refuses unknown/retired stack and unusable definitions (reason string "<name> cannot be used from the hotbar"), prunes retired ids, removes the stack from any other slot, replaces the slot's previous binding, raises `GameEvents.HotbarChanged(ownerId)` only when something changed.

## Input gating decision
Today the run layer (`HudController.UpdateInventoryScreen` -> `RunDirector.SetInventoryOpen(true)` -> `rig.SetInputEnabled(false)` -> player action map disabled) already makes `EmberdelveInput.SlotPressed` false while the satchel is open. I kept that and added an explicit guard in `HotbarController.Update` (return when `director.InventoryOpen` and `director.Player == rig`). The screen reads 1-4 from `Keyboard.current` directly (same style as its `Mouse.current` use in `HandlePointer`), because the player map is disabled then. Assignment target: stack under the pointer if any, else the selected stack (hover wins over selection); ignored on the Character tab, when closed, or when the run is not Running. Refusals and success use `GameEvents.RaiseToast(ToastOwner, ...)`, the screen's existing feedback.

## New checks (all in EmberdelveInventoryUiChecks.Run, same Check(...) counting; scenario names)
- `InitialLoadoutBindsDefaults` (run at entry, before any reset: real class-apply loadout vs expected first usable stacks)
- `HotbarDefaultsAtLoadoutAndRestore`: Clear retires; GiveStartingItems binds draught/arrows skipping coin/blade; no auto-bind of a later stack; restore retires old binding and binds defaults for fresh StackIds; IsUsableDefinition for draught/arrows/coin/blade.
- `HotbarKeyUsesBoundStackIdentity`: exact StackId consumed, heal from definition, one revision + one InventoryChanged, partial use keeps binding, compaction (earlier coin removed) keeps binding, last unit retires slot.
- `HotbarRetiredBindingDoesNothing`: lookalike at the freed index untouched (count, TotalUnits, revision, events, HP), never inherits binding; legacy `TryUseSlot(0)` still works.
- `HotbarAssignFromOpenScreen`: selection path, hover path (hover beats selection), reassignment moves with no duplicate, replacement, idempotent re-bind (no event), coin and blade refused with toasts naming the item and no change, nothing-selected refusal, shared inventory revision unchanged, closed screen ignored.
- `HotbarHudMatchesBindings`: HUD chip Label texts ("Arrow Bundle x3", "Blood Draught x2"), empty chips, after compaction, after partial use, after a binding move (HotbarChanged refresh), after retirement, after Clear.

Key input is NOT simulated: batch mode has no Keyboard device (the existing archer smoke notes the same). HotbarController calls exactly `inventory.Hotbar.TryUse(i, out _)` and the screen's key handler calls exactly `TryAssignHotbarSlot(i, pointer)`; the checks call those two public methods. Gating of "1-4 while screen open" is therefore verified by reading, not by test.
