# D2: complete simulated projectiles (authored gravity, deterministic stepping, flight-time tuning)

Status: IMPLEMENTED, pending Unity run. Nothing here was compiled or run (no Unity in this environment); every change was reasoned against the source. Base commit dcc0114.

## Step 1: what already existed at dcc0114 (the plan docs were stale)

Arrows and bolts were NOT hitscan. `DND_PARITY.md` still said "hitscan ray ... projectileSpeed is visual", and `RangedCombat.Fire` is only an intent builder. What the code actually did:

- `LocalCombatAuthority.Projectiles.cs` (PROJECTILE_WEAPON_BLOCK work) already owned every ordinary arrow/bolt and every MultiShot/PiercingShot arrow as a `ProjectileFlight`: launch validation (weapon, muzzle attachment, 1 degree aim match, range claim, sequence, cooldown, ammo, skill activation and spread slot), a per-frame `AdvanceProjectiles(Time.deltaTime)` from `LateUpdate`, and `SubmitAttack` refuses ranged weapons outright ("must launch an authority-stepped projectile").
- Per-step segment casts already existed: `TryFindProjectileContact` sphere-casts the segment against level + hit masks, sweeps analytic `HitShape` capsules and body spheres, and sweeps the defender's guard blade; the nearest contact wins. A level collider ends the flight (`wall`), a body applies damage, a blade contact blocks (PROJECTILE_WEAPON_BLOCK), piercing continues past a body with per-cast target/budget dedup.
- First-touch hit location (D1c3 `ResolveProjectileLocation`) and the hit-location multiplier were in.
- `ProjectileVisual` was already authority-driven (`MoveAuthoritative` / `FinishAuthoritative`); `WeaponData.projectileSpeed` was the simulated speed, not a visual one.

What was missing (and is what D2 adds):

| Missing at dcc0114 | Effect |
|---|---|
| No gravity: the flight was a straight line along the aim (`Position += Direction * step`) | no drop at all |
| Step length was `speed * Time.deltaTime`: the segment length (and so tunnelling margin, the order of hits inside a call) depended on the frame rate | not rerunnable by a server |
| No flight-time cap (only the path-length `Range`) and no recorded end reason or impact point | nothing to assert "impact on the wall" |
| Falloff was by RANGE: `WeaponData.DamageAtRange(|origin - hit point|)` inside `DamageResolver`, applied to the base before location/guard | not the design rule (air time, after location and DR) |
| No pure (engine-free) projectile math, no NUnit tests, no gate for ballistics | nothing a server or a test could reuse |

## Step 2: what was built

### Data (all authored, all defaulting to the old behavior)
`WeaponData` (Ranged header, new "Ballistics (D2)" group; `projectileSpeed` and `rangedRange` are unchanged and remain the muzzle speed and the path-length cap):

| Field | Meaning | Default on a fresh/old asset |
|---|---|---|
| `projectileGravity` | m/s^2 straight down (0 = flat) | 0 |
| `projectileMaxFlightTime` | seconds in the air before removal (0 = only the range cap) | 0 |
| `projectileFalloff` | `ProjectileFalloffKey[]` (seconds, scale), ascending, linear between keys, held at the first/last key outside; empty = none | empty |

`SkillData` (Effect tuning): `projectileSpeedMultiplier` (default 1) and `projectileGravityMultiplier` (default 1), applied to that skill's projectiles. No drag, by design.

Because the defaults are "no gravity, no table", every weapon asset or test-made `WeaponData` without these fields flies exactly the legacy way. The two ranged library weapons get the numbers through the idempotent `EmberdelveAssetLibrary.ApplyProjectileBallistics()` (called from `BuildAll` after `ApplyCombatFlow`; `LoadOrCreate` only configures new assets). The committed `.asset` files carry the same values, so a gate run does not need `BuildAll` first.

| Asset | Gravity | Max flight | Air-time falloff (seconds -> scale) |
|---|---|---|---|
| Hollow Bow (42 m/s, range 46) | 6.0 | 1.6 s | 0 -> 1.00, 0.30 -> 1.00, 0.50 -> 0.70, 1.10 -> 0.45 |
| Ember Crossbow (54 m/s, range 34) | 3.0 | 1.2 s | 0 -> 1.00, 0.30 -> 1.00, 0.50 -> 0.90, 0.90 -> 0.75 |
| Multi-shot skill | speed x1.0, gravity x1.0 (flies like the weapon) | | |
| Piercing Shot skill | speed x1.0, gravity x0.75 (heavier, flatter arrow) | | |

The bow's 0.7 at 0.5 s is the DnD recurve reference and its floor 0.45 is the old range-falloff floor; the crossbow is faster, has half the gravity and loses less. A 40 m bow shot drops 2.72 m below the aim line (0.5 * 6 * (40/42)^2).

### Pure rules (`Runtime/Rules/ProjectileBallistics.cs`, assembly `Emberdelve.Rules`, namespace `Emberdelve.Ballistics`, no engine types)
- `StepSeconds = 1/60`; `Advance(state, gravity, dt)`: the EXACT constant-acceleration update `p' = p + v dt - g dt^2/2 (y), v' = v + a dt`. Not explicit or semi-implicit Euler (they drift g*dt*t/2 from the true parabola and so would change the drop with the step size); exact means the sampled path is the same parabola at any step size and `PositionAt` (closed form) predicts it to float rounding. No drag.
- Determinism: a fixed step and a fixed sequence of float operations, so the same launch state and step count give bit-identical states in the same process. Frame rate cannot matter because `ConsumeSteps(ref accumulator)` splits accumulated frame time into whole steps (epsilon 1e-5 s, at most 600 steps per call, remainder carried).
- `DropBelowAimLine`, `TimeAlongAimLine`, `TimeToHorizontalDistance`, `SolveLowPitch` (low-arc, drop-compensated aim), `FalloffScale` (table), `IsValidTable`.
- `ProjectileFalloffKey` (serializable struct) lives here so the weapon asset and a server share one type.

### Authority (`LocalCombatAuthority.Projectiles.cs`)
- `AdvanceProjectiles(delta)` adds `delta` to each flight's accumulator and runs `StepProjectile` once per whole 1/60 s step (flights processed one after another, as before).
- `StepProjectile`: integrate the step; the straight chord of the step (<= 0.9 m for the crossbow, within 0.1 mm of the true arc) is cast exactly as the old segment was (`TryFindProjectileContact` unchanged): wall/ground ends the flight at the contact (no hit through a wall, thin walls are swept, not tunnelled), bodies use D1c3 first-touch location, blades and piercing/skill budgets unchanged, the friendly/self/inactive rules unchanged. Path length is still capped by `rangedRange`; `projectileMaxFlightTime` is new.
- Air time of a contact = whole steps flown + the fraction of the step's chord covered, times 1/60.
- `SimulateBallistics` (public, default true) is read at launch: false gives gravity 0, no time cap and the legacy range falloff (still fixed-stepped). Used by gates that assert straight-line geometry.
- Observability for gates and a future server rerun: `internal event ProjectileStepped(serial, instigator, step, position, velocity)`, `internal event ProjectileEnded(ProjectileEndReport)` (reason RangeExhausted/TimeExpired/Wall/Body/Blade, last position, impact point, steps, air time, path length) and `ActiveProjectileCount`.
- Visual follows the sim: `ProjectileVisual` is placed each frame between the previous and the current simulated position (interpolated by the carried remainder) and finishes at the final position. It has no ballistics of its own.

### Damage (`DamageResolver`)
`Resolve` and `ResolveSkill` gain a trailing optional `airTimeFalloff` (default -1 = legacy). When a projectile flight passes a scale >= 0: the base is `BoostedBaseDamage` (no range attenuation) and the finished hit (after charge, power, location, the defender's guard reduction and armor) is multiplied by the scale by `DamageResolver.ApplyProjectileFalloff` with a final 1.0 floor. Every earlier step is a multiplication, so the order only matters for the floor. A flat-damage skill still takes no falloff; a non-projectile resolution ignores the scale. This is the DND_PARITY formula position ("x location, x DR, x projectile reduction and falloff").

## Literal changes (old -> new, why)

No expected number inside an existing gate changed value. What changed is which mode those gates run in:

| Gate | Change | Why |
|---|---|---|
| ProjectileBlock (both authorities: the main one and the live-capture one) | `SimulateBallistics = false` | blade/body literals are narrow straight-line geometry at 8 m; a 0.11 m bow drop would move the arrow off the blade |
| RangedLocation | `SimulateBallistics = false` | head/arm/hand/feet volumes are hit by horizontal arrows at exact heights; its `DamageAtRange(distance)` expectations are the legacy range rule |
| SkillAuthority, AttributeSkill, CombatAuthority, AttributeAction, FlatDamageAffix | `SimulateBallistics = false` | their damage literals are `DamageAtRange(distance)` at 15 to 31.5 m on straight lanes (the 30 m bow shot would otherwise drop 1.5 m off the target and fall under the new 0.7 air-time curve) |
| RuntimeSmokeTest (archer modes) | `_localAuthority.SimulateBallistics = false` right after the authority is resolved | enemies are placed on precomputed straight rays and the volley/pierce damage uses `bow.DamageAtRange` |
| CombatFlow (1.8 m), MultiPlayer (8 m crossbow), SenderOwnership, KitState, MovementLifecycle | unchanged, run with ballistics ON | short lanes or launch-only checks: drop <= 0.04 m, air time < 0.2 s (factor 1.0) |

Other behavior differences that gates can see (no literal changed):
- `AdvanceProjectiles(x)` now runs `floor(x / (1/60))` whole steps and carries the remainder, instead of moving exactly `speed * x`. Distance moved by one call is quantized to one step (0.7 m bow, 0.9 m crossbow). The existing calls are safe: `AdvanceProjectiles(0.12f)` = 7 steps = 4.9 m of an 8 m lane (ProjectileBlock "not yet reached"); `range / speed + 0.01..0.02` still covers the whole range (46.2 m of 46 for the bow, 34.2 m of 34 for the crossbow).
- A bow or crossbow shot in a ballistic authority now drops and uses the air-time table: old bow range falloff 1.0 -> 0.45 over 18 -> 46 m, new 1.0 / 0.7 / 0.45 at 0.3 / 0.5 / 1.1 s (about 12.6 / 21 / 46 m); old crossbow 1.0 -> 0.5 over 12 -> 34 m, new 1.0 / 0.9 / 0.75 at 0.3 / 0.5 / 0.9 s.

## Risks and limits

- Not compiled. Most likely compile-level misses: a name collision on `Trace`/`Pump` in the gate, `System.MathF` availability in the Rules assembly (should be fine on Unity 6 / .NET Standard 2.1), and the `[Serializable]` struct arrays on a ScriptableObject.
- The `.asset` files were edited by hand in Unity's YAML layout (array of structs as `- time:/scale:`). If Unity rewrites them on import that is only formatting; `BuildAll` reproduces the same values.
- Gameplay: live arrows now drop (6 m/s^2 is a 2.7 m drop at 40 m, about 3.9 degrees of lead) and the real game has no aim assist or reticle compensation yet; tune `projectileGravity` per weapon if that feels too heavy. The player-facing reticle does not show the drop.
- The gate and the old gates use 3000,0,3000 fixtures with `hitMask = 0`; the wall section uses the `Emv_Level` layer (falls back to layer 0 if the layer name is missing).
- Flights are advanced one after another per call, so with several flights in the air the order in which two arrows reach a shared per-cast budget or kill the same target can differ from a lock-step server loop; per-flight trajectories are independent of that order.
- Piercing Shot and Multi-shot ballistic flights are covered by the resolver checks and the data check, not by a skill-activation flight in the new gate (their launch needs a full activation); their flights share `StepProjectile` with ordinary arrows.
- U3A networking is untouched; a server rerun is possible (`ProjectileBallistics` is engine-free and `AdvanceProjectiles` takes any delta), but nothing replicates projectiles yet.
