# R6b1: shared inventory/loadout revision

## Scope

This draft adds a monotonic runtime `Inventory.Revision` for the bag and its paired equipment. The counter is owned by the inventory so a bag operation, equipment transfer, equipment restore, and atomic loadout restore all advance the same value. The revision is not serialized: JSON schema 1, snapshots, UIDs, rolled values, and R6a runtime stack IDs keep their existing formats and meanings.

Revision preflight and commit are centralized in `Inventory.CanCommitRevision` and `Inventory.CommitRevision`. A mutating public path preflights before touching live state, commits once after its final state is installed, and commits before `InventoryChanged` or `EquipmentChanged` callbacks run. At `ulong.MaxValue`, paths that could mutate fail closed; they do not wrap. No test sets the counter to that boundary through reflection.

## Mutation coverage

- Direct definition adds, exact-cell adds, and instance adds commit once when at least one unit is accepted. A partial add is still a committed change and advances once even when its legacy result is `false`. Refused adds do not advance.
- Grid size changes that reseat the bag commit once. Reapplying the same dimensions does not advance. Same-cell moves keep their existing successful return and notification, but do not advance.
- Swaps, merges, removals, additions into an existing slot, and `Clear` commit once on a real change. Empty `Clear` remains an event-compatible no-op. `TryUseSlot` relies on its existing nested removal for the single commit, with a revision preflight before healing or granting ammo.
- Equip, replacement, unequip, nonempty equipment clear, standalone bag restore, and standalone equipment restore commit once after the full operation. The silent bag transfer helpers do not commit independently.
- Combined loadout restore preflights once, silently applies both validated halves, commits once, and then notifies. Failed validation or UID-ledger refusal occurs before either half changes.

## Gate

`Emberdelve.EditorTools.EmberdelveLoadoutRevisionGate.Run` checks direct loot addition, a refused placement, same-cell and same-grid no-ops, empty clears, standalone bag restore/refusal, equip, standalone equipment restore, and an atomic combined restore/refusal. The callback assertions compare revision and canonical bag/equipment snapshots so listeners must see the final state at the notification boundary. The combined restore checks exact-once revision advancement while both the bag and worn boots return to their saved state.

Integrated into the project checkout. Unity compilation and gate execution remain pending the root's focused gate and batch run. The gate uses the production catalog and level fixture, following the existing R6a editor-gate pattern.

## Limits

The revision identifies runtime state changes for future command replay checks; this slice does not add commands or migrate UI/consumable effects. `GiveStartingItems` continues to use its existing per-item `TryAdd` path, so each accepted item addition advances once and the existing final notification remains. The terminal fail-closed policy may reject any potentially mutating call at counter exhaustion rather than risk a partial state update.

`Equipment.Clear` resolves the shared revision owner through `BagPartner()`, just like equipment restore. This preserves clearing behavior for editor-created component pairs before `Awake` initializes the cached inventory reference.
