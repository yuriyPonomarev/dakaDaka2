# U4B corpse loot custody

> Historical implementation note. Current acceptance and remaining work: [CURRENT_WORK](../CURRENT_WORK.md) and [raid acceptance](RAID_UI_ACCEPTANCE_20261108.md). Status statements below describe the original slice.


## Foundation registry and network runtime
- `CorpseLootRegistry` provides a server/offline-only custody and transfer primitive based on `CorpseLootManifest`.
- `TryCommitDeath` stages the manifest and reserves its gear UIDs before atomically restoring an empty loadout to the source. If capture, source revision matching, or empty-loadout restore fails, staged custody and UID reservations are rolled back and the source is left intact.
- Per-run corpse IDs are monotonic. Repeated death commits for the same player are refused, and a UID already assigned to another corpse is refused.
- `TryLootAll` is a server/offline-only whole-loadout transfer primitive. It requires an empty paired recipient bag/equipment, uses `LoadoutSnapshot.TryRestore` to validate and atomically apply the original stacks, gear UIDs and affixes, prevents re-entrant transfers, and removes corpse custody only after the recipient commit succeeds.
- The recipient profile's `ItemUidRegistry` is required for loot transfer and is updated by that same atomic loadout restore. Existing runtime admission does not yet create profile UID registries, so a future RPC caller must supply the recipient's live registry.
- `CorpseContainerModel` is a per-entry looting model. It assigns server-side row IDs and a corpse revision; a caller specifies an expected corpse revision, bag revision, row ID and quantity. Ordinary stacks merge into existing matching capacity before requiring a free grid footprint, and gear moves as one exact UID-backed item. The target bag's atomic snapshot restore updates the profile UID registry; only after success is the corpse row reduced or removed.
- Capacity, catalog resolution, profile UID conflicts, stale revisions, and synchronous re-entry are refused before the corpse row changes. A busy latch stays held through deferred inventory notifications, preventing a callback from collecting the same row twice.
- Added a bounded owner RPC protocol in `NetPlayerRig` / `NetInventoryServer`: request state and transfer intents carry corpse/entry IDs, amount, per-connection sequence, expected corpse revision and expected bag revision. Server derives the actor from the sender and owned player object, checks admitted/alive state, reach and level line of sight against the stored corpse position, reconstructs the current bag/equipment UID registry, then commits through `CorpseContainerModel`.
- Server presence (ID, world position, revision) is broadcast to every connected owner/client; client owners and the listen-host owner present it as a local interactable capsule marker. Full contents are sent only to the requester and nearby admitted owners. Owner results carry current revisions, stale/failing requests receive the current state, and empty models are removed after their final row transfer. Full state is bounded to 16,000 UTF-8 bytes; the server accepts at most 128 live corpses. Per-client corpse state requests are limited to one per 0.25 seconds and transfers to one per 0.1 seconds. `RegisterCorpse` remains available for dev fixtures; real death now uses the atomic custody path.
- The client marker requires the owning live player and ready inventory session; the host marker uses its existing server-owned rig and direct server handler, without adding the client inventory authority. Both check range and line of sight before sending the state request, and the server repeats sender/admission/alive/range/LOS checks. Presence replicas reject stale revisions and retain removal tombstones so a delayed packet cannot move or resurrect a removed marker.

## Runtime state
- Networked deaths enter `ICorpseDeathCustodian` before publishing a result. `NetInventoryServer.TryCommitDeath` captures and validates the manifest/model/wire and registry capacity first, then atomically clears the source loadout and publishes the prevalidated corpse. It guards re-entry by player ID, refuses duplicate UIDs already held by another corpse, and treats immediate network notification failure as committed custody recoverable by later presence snapshots.
- If preflight/source commit refuses, the dead session remains pending, its rig stays disabled with the original loadout, and the result is withheld. `RunDirector` retries once per second until the server custodian accepts. Offline deaths retain the existing result path; no offline corpse UI is wired.
- On owner disconnect, the server attempts the same custody transaction before despawning the player object. A refusal unregisters gameplay/admission but retains the original rig on the server (`DontDestroyWithOwner`) and retries. Shutdown logs any retained loadout that could not be committed. Bodies and loot are intentionally session-only and are discarded when this server process stops; durable stash banking is a later feature.

## Limits
- Models are intentionally in-memory for the current-session game loop; server shutdown discards bodies and their loot. Durable stash banking is a later, separate U4C feature. Network deaths register through the atomic custody service, while `RegisterCorpse` remains for development fixtures. The capsule marker is an interim locator, not a corpse body asset. The new second-container UI is a minimal paged uGUI panel (six rows/page, Take 1/Take all, refresh and close); it sends intents only and renders server snapshots, with one transfer in flight, stale/refusal refresh, bounded wait timeouts, and closure on death, extraction, corpse removal, or owner despawn. It does not create corpse custody or change inventory locally.
- The listen-host uses the same UI backed by the direct server handler. Its development process proof has passed 104/0, covering the host request route, range/LOS/stale refusal and exact UID custody/removal. Batch proof does not render or click uGUI; live interactive host-panel usability remains unverified. Persistent stash transfer and offline corpse UI are future scope; current-session corpse loot is intentionally volatile.
- `TryLootAll` expects its caller to validate the admitted living recipient, distance and line of sight. No caller is wired yet.
- The RPC checks sender ownership/admission, alive state, range, LOS, request sequence and revisions. The real-death hook now uses a separate atomic server custody transaction; the UI still consumes the same registered corpse model.
- Disconnect refusal retains the source rig server-side and retries. When the server process ends, current-session bodies and loot are discarded by design.

## Checks
- Focused EditMode cases cover exact custody and UID round-trip, source-clear rollback, profile UID conflict/refusal and retry, partial stack merge, stale corpse/bag revisions, full-bag rollback, UID-ledger rollback, re-entrant duplicate refusal, wire state round-trip/bounds, request-sequence replay/skip rejection, burst/backwards-clock rate-limit behavior, presence revision/tombstone rules, local-live-owner request eligibility, and UI-session corpse/revision/sequence/re-entry behavior. Profiled UI EditMode verification passed 8/8 in an earlier run.
- The network death hook withholds the result until custody succeeds. Dedicated-server and listen-host synthetic corpse proofs passed 83/0 and 104/0. The real-death process proof passed NetInventory 121/0 in `Logs/runs/20261106-061410`: it applies lethal damage through `PlayerRig.ApplyDamage`, verifies an injected preflight refusal preserves the source UID and withholds corpse/result, then retries and verifies the same UID in corpse custody before result publication. It also kills the second client process (without calling an internal callback), checks NGO disconnect refusal retains the exact UID on a spawned server rig, then checks retry registers that UID in a corpse before despawn.
- A corpse proof run exposed a fixture-only grid initialization issue: a newly added empty `Inventory` with the same dimensions as its defaults skips `ConfigureGrid`'s rebuild, leaving its zero-filled cell map appearing occupied while `FreeCells` reports full capacity. The fixture now calls `Clear()` after sizing to recompute the empty grid before adding the minted test gear. The prior run remains failed evidence; rerun the proof to verify this setup correction.
- Follow-up audit found the same occupancy initialization defect affected real offline rigs: when `ClassLoadout` requested the default 10x4 dimensions, the no-op sizing path left the initial zero-filled cell map occupied, refusing starting items. `Inventory.Awake` rebuilds the map when it runs, and `EnsureGrid` now lazily rebuilds it from existing stacks on first access, covering inactive/deserialized components queried before `Awake` without clearing contents. The first test draft used arbitrary equippable gear; `GiveStartingItems` discarded `TryAdd`'s refusal reason, so its empty-slot assertion alone could not distinguish placement failure from gear-mint refusal. The test now uses the shipped Archer class's real starting-item list, exercises the no-`Awake` default 10x4 path, and verifies lazy rebuilding preserves the exact container snapshot. `GiveStartingItems` also logs a concrete refusal reason when a starter cannot be placed. EditMode verification is pending; Unity was not launched for this fix.
- The dedicated-server and two-client corpse proof passed 83/0 in `Logs/runs/20261106-045438/gates`; the listen-host proof passed 104/0; the real-death + disconnect proof passed 121/0 in `Logs/runs/20261106-061410`. Remaining verification: rendered client/listen-host UI usability and close-on-death/disconnect behavior. Corpse custody remains volatile in-memory by design; stash persistence is deferred to U4C.
