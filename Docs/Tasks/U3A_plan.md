# U3A plan: first real network proof (dedicated process + two clients, walking / ownership / late join, offline retained)

Status: PLAN ONLY. Nothing was compiled, installed or run. Written from a read of Docs (ROADMAP, OPUS_COMPLETION_PLAN, PLAN_CLAUDE, Design/NETWORK_SPIKE.md, R1c_plan, R1c1, R2R7) and the runtime (RunDirector, PlayerRig, PlayerMovement, PlayerLook, EmberdelveInput, CombatSenders/CombatRegistry, LocalCombatAuthority, GameServices, EmberdelveWindowsBuild, gate runners).
Acceptance row: "Real independent process connection/input/cleanup evidence". NETWORK_SPIKE.md already fixes the boundaries (sender from the authenticated connection, never from the payload; client transform / client-finished dash is not an authoritative position; per-player view separate from simulation; profile != peer connection; no hosting/matchmaking dependency; a one-process two-object harness is NOT the proof). This plan implements those, it does not reopen them.

## 0. Facts in the code that shape the plan

1. The project is code-only in this tree (no Packages/, scenes, prefabs). The scene rig is scene-authored: `RunDirector.playerRig` is a serialized scene reference, and `SpawnPlayer` clones that rig. There is NO player prefab yet. U3A must generate one (Editor builder, same style as `EmberdelveLevelBuilder`).
2. Everything gameplay-authoritative lives in process-wide statics: `CombatRegistry`, `CombatSenders` (owner table), `GameServices`, `GameEvents`, `RunContext`, `CombatTeams`. One match per process is a documented assumption. This is fine for a dedicated process (one match) and for a client process (one view). It is NOT fine to put two logical worlds (server + client) in one process. Consequence: the two real clients are separate processes, and "in-editor loopback" means Editor = host/server + a built client process, never two NetworkManagers in the Editor.
3. `PlayerRig.PlayerId` == process-local combat id (R7 comment: "until the session layer hands out account ids (U3A)"). `CombatSenderId.ForPlayer(rig.PlayerId)` is bound in `RunDirector.TryJoin`. U3A makes the SERVER the only allocator: server PlayerId = server combat id, replicated to clients as a read-only value; clients never register their views as combat entities.
4. `PlayerMovement.Update` reads `EmberdelveInput` and `Time.deltaTime` directly (variable dt, CharacterController). Its own comments name `DesiredMoveIntent`, `ResolveGroundSpeed` and static `ViewRelativeDirection` as "the numbers a future server compares/applies". The input layer comment says a networked build swaps the input source. R1c3 already made the dash "client moves, authority validates" (user decision) with `IMovementRollback`.
5. `RunDirector`: `Start()` joins the scene rig as local player; `TryJoin(rig, party, locallyControlled, class, out reason)` and `SpawnPlayer(..., class, ...)` already take a trusted-host class (R2R7 says network class ids must be validated against the approved catalog at the network boundary). Missing for network: no `RemovePlayer/Leave`, `_local == null` (dedicated) paths are untested, `TogglePause` sets `Time.timeScale = 0` (must be local UI only online), `RestartRun/ReturnToLobby/LobbyController` call `SceneManager.LoadScene` (would unload an NGO-synced scene), no player spawn points in `DungeonLayoutData` (MultiPlayer gate uses ad-hoc origins).
6. Existing evidence machinery to reuse: `Tools/Run-EmberdelveGates.ps1` (log regex `] PASS ... checks=N ... failures=0`, scans for `error CS`/`FAIL`/`Exception:`), `Tools/Run-EmberdelveEditModeTests.ps1`, `EmberdelveWindowsBuild.BuildReview` (headless Development player build, output outside Assets), `EmberdelveReviewBridge` (opt-in `--ember-review-dir`, real virtual-device input + screenshots, DEVELOPMENT_BUILD only), `[InitializeOnLoad]` + SessionState play-mode gate pattern (`EmberdelveMultiPlayerGate`).
7. `Emberdelve.Runtime` currently references only Emberdelve.Rules and Unity.InputSystem. Keep it free of `Unity.Netcode` so the offline code path and all 45 existing gate groups stay package-independent; put NGO code in a new `Emberdelve.Net` assembly that references Runtime (never the reverse).

## 1. Stack decision

Recommendation: Netcode for GameObjects (NGO) 2.x on Unity Transport (UTP) 2.x, ClientServer topology, DIRECT transport (UnityTransport, IP:port). No Unity Gaming Services, Relay, Lobby, Matchmaker or Sessions in U3A (NETWORK_SPIKE: first proof must not depend on paid hosting or a cloud deployment). `Unity.Services.Multiplayer` sessions are a later layer (internet discovery), not U3A.

Why: matches the existing GameObject/MonoBehaviour game; official; the only official option that fits without a DOTS rewrite; server-authoritative by default; headless/dedicated supported; first-party Multiplayer Center is already in the manifest and points at it.

Versions (VERIFY BEFORE INSTALL, I have no package registry access here):
- NETWORK_SPIKE.md records "NGO 2.7 supports Unity 6.0 and later". Target `com.unity.netcode.gameobjects` 2.7.x if the Package Manager in 6000.2.5f1 offers it and does not flag it incompatible; otherwise the newest 2.x that the resolver lists for 6000.2 (U3A1 step 1 records the exact resolved version in Docs/Tasks/U3A1.md).
- `com.unity.transport` 2.x arrives as an NGO dependency; do not add it explicitly unless the resolver omits it. Pin the exact versions the resolver chose in manifest.json (no ranges, no "latest"). Expect transitive additions: com.unity.collections 2.x, com.unity.nuget.mono-cecil, possibly Burst/Mathematics (check the dependency delta against the current manifest; the project is URP and must stay unchanged, 6000.2.5f1 unchanged).
- Install through the UPM Client API (`UnityEditor.PackageManager.Client.Add` via Editor eval) per NETWORK_SPIKE slice 1; then force a compile and read the Editor log for new warnings (record delta).
- Optional dev tools (not required): `com.unity.multiplayer.tools` (runtime net stats), `com.unity.multiplayer.playmode` (see section 8: not usable in batch).

Alternatives (brief, not recommended now):
- Netcode for Entities: requires moving gameplay to DOTS. No.
- Mirror / FishNet / Photon Fusion 2: workable on GameObjects; Fusion has built-in tick prediction but is a third-party service/licence; Mirror/FishNet are non-official. Revisit only if NGO prediction work (U3A4) proves unworkable.
- Unity Transport only + hand-written messaging: most control, most code; kept as the fallback for the movement stream only (NGO custom named messages ride on the same connection anyway).
- Distributed Authority topology (NGO 2.x): rejected, needs a cloud service and is not server-authoritative.

## 2. Architecture

### 2.1 Roles
Static `NetRole` (Runtime assembly, tiny, no NGO dependency): `Offline | DedicatedServer | Host | Client`, set once by the launcher before the dungeon scene loads, default `Offline`. Helpers: `RunsSimulation` (Offline/Server/Host), `PresentsLocalPlayer` (Offline/Host/Client), `IsClientOnly`. Gameplay code asks these instead of asking NGO. Offline never touches NGO: no NetworkManager in the scene, no NetworkObject on the scene rig, no package types on any offline code path (this is the "offline retained" guarantee, and it is cheap).

- Offline: today's path exactly. `RunDirector.Start` joins the scene rig; lobby -> dungeon via SceneManager as now.
- DedicatedServer: server process owns `RunDirector`, `LocalCombatAuthority` (ICombatAuthority registered in GameServices), `CombatRegistry`, `CombatSenders`, enemies, chests. No local player, no camera, no HUD, `RunDirector.Start` does not join the scene rig (new `serverMode`), pause does not touch `Time.timeScale`.
- Host (listen server): same as server plus one locally presented player (this is the "local host path": same code as dedicated + `IsLocal` session). Used for the Editor-as-server dev loop and a future "Host game" button. Offline does NOT use it in U3A.
- Client: scene geometry + replicated views only. `LocalCombatAuthority`, `RunDirector`, enemies, chests, `HudController`, `LobbyController` are not active (see 2.5). Rigs on a client are views: not registered in `CombatRegistry`, no combat components running.

### 2.2 Identity, ownership, admission (the part NETWORK_SPIKE cares most about)
- `NetworkManager.NetworkConfig.ConnectionApproval = true`, `PlayerPrefab = null` (no auto player), spawn manually after admission.
- Client connection payload (`ConnectionData`, bounded size, versioned): `{ protocolVersion:int, buildHash/id:string, classId:string, devSlotId:string }`.
- Server approval callback (pure rules in `Emberdelve.NetRules`, testable without Unity): reject on payload parse failure / oversize, protocol mismatch, `classId` not in the server's approved class catalog (resolved from the server's `GameConfig`/class list, the client only sends an id string), connected count >= `maxPlayers` (default 9, overridable `--ember-net-max-players`), duplicate `devSlotId` already connected, run ended. Response carries a machine reason string that the client logs.
- `devSlotId` is a DEV-SCOPED loopback identity (command line `--ember-net-slot`), explicitly not production authentication (NETWORK_SPIKE). It is the seed of the durable profile key for U4C; the peer connection id is never a profile key.
- On `OnClientConnectedCallback` the server: instantiates the net player prefab, calls `RunDirector.TryJoin(rig, requestedParty(-1 auto), locallyControlled:false, approvedClass, out reason)` BEFORE `NetworkObject.SpawnAsPlayerObject(clientId)`. If TryJoin refuses (party/run state), destroy the instance and disconnect the client with the reason. Nothing is ever half-spawned.
- Table `NetIdentityTable` (server only): `clientId -> {playerId, rig, slotId}`. `ResolveSender(RpcParams p)` returns `CombatSenderId.ForPlayer(table[p.Receive.SenderClientId].playerId)` - the ONLY source of a sender. No RPC parameter ever carries a player id, combat id, class, weapon, stats or position. Unknown/disconnected clientId -> `CombatSenderId.None` (every sender-bound authority command is already refused for None). This is the `IAuthorityConnection` hook R1c_plan deferred to U3A; keep it a plain function on the table, not a new interface family.
- Ownership: the player NetworkObject is owned by the connecting client (`SpawnAsPlayerObject`). Every server RPC handler re-checks `rpcParams.Receive.SenderClientId == OwnerClientId` itself. Do not rely on the RPC attribute's RequireOwnership alone (a modified client bypasses client-side checks; check the NGO attribute surface in the resolved version, the name/semantics changed between 1.x ServerRpc and 2.x `[Rpc(SendTo.Server)]`).
- Disconnect: `OnClientDisconnectCallback` (server) -> new `RunDirector.RemovePlayer(playerId, reason)`: unsubscribe `Died`, `CombatRegistry.Unregister` (also unbinds the sender), remove session / free party seat, despawn + destroy the rig, remove identity-table row, log counts. Removal is immediate in U3A (no corpse, no linger; those are U4B).

### 2.3 Movement: server-simulated from client input, owner-predicted (RECOMMENDED)
Options considered:
- A (recommended): server runs the real `PlayerMovement` (CharacterController, class/stat speeds, flow factor, status slows) driven by input frames; owning client predicts with the same code and reconciles; other clients interpolate server state. A client can send only intent (move axes, yaw/pitch, sprint/crouch/jump bits); the server derives speed, collision and position. Speed hacks and teleports are impossible by construction, not merely detected. It is the only option consistent with NETWORK_SPIKE ("a client transform ... is not an authoritative position") and with swept-melee/hit-location combat that needs trustworthy positions (U3B) and with dash (U3B runs the dash on the server; R1c3's report-and-rollback becomes the offline-only path).
- B (fallback, cheaper): owner-authoritative `ClientNetworkTransform` plus server validation (speed cap using `ResolveGroundSpeed`, wall sphere cast, as R1c3 does for dash). Zero latency for the owner, but positions are client-claimed, rollback is visible, and it contradicts the NETWORK_SPIKE boundary. Keep as an escape hatch only if CharacterController replay proves too noisy, and only with a user decision.
- C: no prediction at all (server-sim, owner renders server state). Used as the deliberate intermediate step inside U3A4 to prove authority before adding prediction.

Design for A:
- Refactor (offline-preserving, U3A2): `PlayerMovement.Step(in MoveInputFrame f, float dt)` holds the body of today's `Update` (crouch toggle edge, capsule height, grounded check, jump/gravity, Move/MoveDash). `Update()` builds a frame from `EmberdelveInput` + `Time.deltaTime` and calls Step unless `ExternalDriven` is set (then Update does nothing). Add `ViewRelativeDirection(Vector2, float yawDegrees)` next to the existing Transform overload (keep the old one, gates call it). `MoveInputFrame` (plain struct in Runtime): `seq, moveX, moveY (sbyte-quantized), yaw, pitch, flags(sprint, jumpEdge, crouchEdge, guardHeld reserved)`. Yaw/pitch are the client view (absolute), applied on the server to body yaw and pitch pivot so the server rig has a real aim pose for U3B (`IAimPoseProvider`), pitch clamped to PlayerLook limits. Turn-rate validation is U3B (D1 "H2 turn-rate cap during swings"), but the field is carried now.
- Tick: NGO tick rate 30 Hz for U3A (config constant `NetTuning.TickRate`; user decision 60 vs 30). Input is sampled per render frame on the client, aggregated into one frame per tick (move = last held value, edges OR-ed), sent every tick as `[Rpc(SendTo.Server, Delivery = Unreliable)]` carrying the last 3 frames (loss redundancy; server dedupes by seq). Server steps ONE frame per player per tick with fixed dt = 1/TickRate from a per-player queue (cap 6; jitter buffer 1-2). Missing frame: repeat last move for <= 3 ticks then neutral input (no extrapolated runaway).
- Server sanitization (pure, unit tested): finite check on every float, |move| clamped to 1, seq must be > lastSeq (replay/old dropped and counted), forward jump window (seq - last <= 64 else flagged), at most 2*TickRate frames/s accepted per sender (flood -> drop + count), flag mask whitelist, pitch clamp, yaw wrapped. Counters per player exposed in a debug string for the gate: accepted, dropped-replay, dropped-flood, dropped-invalid.
- Replication back: owner gets `[Rpc(SendTo.Owner, Unreliable)] Ack(uint lastProcessedSeq, Vector3 pos, float verticalVelocity, float speedScale)` every 2nd tick; also a `NetworkVariable<MoveParams>` (owner-read) with the authoritative walk/sprint/crouch speeds because the client does not have the server's gear/attributes in U3A (inventory replication is U3B+). Non-owners see the player through a server-authority `NetworkTransform` (position + yaw, interpolation ON, no scale) and a `NetworkVariable<short>` pitch for the head/weapon visual. Owner's `NetworkTransform` does not drive its own transform (`OnIsOwnerChanged` / authority mode so prediction is not fought).
- Owner prediction (U3A4 step 2): client runs `PlayerMovement.Step` locally for every frame it sends, stores `(seq, pos, vy)` in a ring; on Ack compare with the stored entry for `lastProcessedSeq`: error <= 0.10 m ignore, <= 1.0 m blend over ~100 ms, > 1.0 m snap (`TeleportTo`, which exists) and replay unacked frames. Official alternative to evaluate first for the blend part: NGO `AnticipatedNetworkTransform` (client anticipation with server override); if it fits the CharacterController flow it replaces the hand-written blend, otherwise keep the small custom loop. Decision point is recorded in U3A4's report, not guessed here.
- Headless server rig: keeps all components (so the same prefab works for U3B), but Camera/AudioListener/Light are disabled/destroyed (existing `SpawnPlayer` already does this for remote clones), `EmberdelveInput` gameplay map off (`SetInputEnabled(false)`), `PlayerMovement.ExternalDriven = true`.

### 2.4 Prefab and scene wiring
- Editor builder `EmberdelveNetBuilder` (menu + `-executeMethod`): derives `Assets/Emberdelve/Prefabs/Net/Emberdelve_NetPlayer.prefab` from the Level01 scene rig (all current components) and adds `NetworkObject`, `NetworkTransform`, `NetPlayerRig` (NetworkBehaviour in `Emberdelve.Net`). SINGLE prefab for all roles; role-specific behavior is applied in `NetPlayerRig.OnNetworkSpawn` from `NetRole`/`IsOwner`: server (full rig, headless), owner client (camera + input + movement prediction), observer client (view only: camera/input/combat components disabled, CharacterController disabled so transform follows interpolation). Prefab overrides (per-role prefabs) are the alternative; not chosen because they double the generated assets and the hash-matching rules add failure modes.
- Because Awake runs before OnNetworkSpawn, `PlayerRig.WireRig` consults `NetRole.IsClientOnly` (static, set before scene load) to skip `CombatRegistry.Register` and combat event wiring on client processes. This is the single behavioral change to PlayerRig besides `SetNetworkPlayerId(int)` (client sets the replicated server id).
- Level01 gets one new scene object `NetSceneRoles` (execution order very early) that, per role, deactivates listed roots: Client: RunDirector, LocalCombatAuthority, enemy/chest roots, HudController, lobby bits; DedicatedServer: HudController/camera roots; Offline: nothing (and the component is a no-op). Scene edits go through the existing builders (LevelBuilder), not hand edits. A dedicated `Emberdelve_NetBoot` scene (NetworkManager + UnityTransport + `NetBootstrap`) is added to the Windows build as scene index 2; a `[RuntimeInitializeOnLoadMethod(AfterSceneLoad)]` hook loads it only when `--ember-net=` is on the command line. Without that flag the shipped flow (lobby first) is byte-for-byte as today.
- Spawn points: add `playerSpawns` (list of walkable cells) to `DungeonLayoutData` (validated by its existing Validate) or derive from NavGrid; 9 slots minimum, spread so spawns are not stacked. Needs a data asset rebuild (user decision 10).
- Net client scene flow: server loads Level01 with NGO scene management, clients follow. `RunDirector.RestartRun/ReturnToLobby` and `LobbyController` start are disabled for non-Offline roles in U3A.

### 2.5 What the client does NOT do in U3A
No combat, inventory, chests, enemies, loot, extraction, HUD beyond a dev-build overlay (role, id, ping, players, reconcile error). These are hidden/inactive on clients, not replicated (U3B/U4). Enemies exist only on the server and are visible to nobody in U3A (consequence to state in the report; acceptable, they do not exist for the walking proof). Server running enemy AI against walking test players is allowed but the proof scenario can turn enemy spawns off via a launch flag to avoid flake (`--ember-net-no-enemies`).

## 3. Launch contract (command line, one executable for all roles)
Standard Unity flags: `-batchmode -nographics -logFile <path>` for headless; `-screen-width/-height -popupwindow` for windowed clients.
Project flags (all `--ember-net-*`, parsed by a pure `NetLaunchArgs` in Emberdelve.NetRules):
- `--ember-net=server|client|host` (absence = Offline; nothing else changes).
- `--ember-net-port=<n>`; `--ember-net-address=<ip>` (client); `--ember-net-listen=loopback|any` (default loopback, see risks: Windows Firewall prompt blocks unattended runs).
- `--ember-net-max-players=<n>` (default 9), `--ember-net-class=<classId>`, `--ember-net-slot=<devSlotId>`.
- `--ember-net-ready-file=<path>` (server writes `port=..;pid=..` when listening and the scene is loaded), `--ember-net-quit-file=<path>` (server polls; graceful shutdown), `--ember-net-max-seconds=<n>` (watchdog self-exit on every role), `--ember-net-no-enemies`.
- Client test driver (DEVELOPMENT_BUILD only): `--ember-net-script=<name>` e.g. `walk-forward:3.0`, `walk-square`, `forge-owner`, `flood-input`, `replay-seq`, `quit-after:<s>`. The driver feeds `MoveInputFrame` into the same send path (not the Input System), so it works in `-nographics` and unfocused. A real-input pass uses the existing review bridge in windowed mode (section 6).
- Dedicated build: U3A uses the standard Windows Development player run with `-batchmode -nographics` (no extra module). Optional later: `StandaloneBuildSubtarget.Server` (Dedicated Server) profile, which needs the "Windows Dedicated Server Build Support" module; check with `list_platforms` before promising it. Server loop must set `Application.targetFrameRate = 60` (headless is uncapped otherwise) and `Application.runInBackground = true` on every role (an unfocused client otherwise stalls and trips NGO timeouts).
- Transport timeouts for tests: `DisconnectTimeoutMS`/`HeartbeatTimeoutMS` lowered (about 3000-5000 ms) via launch flag so a killed client is detected within the gate budget; the 30 s default is too slow. Property names depend on the resolved UTP version.

### U3A4: movement (input frames, server simulation, interpolation, prediction)
Goal: walking is real, server-authoritative and visible on the other client; cheat inputs cannot move a player faster or elsewhere.
Steps (each ends green; this slice may split into 4a/4b if review demands):
- 4a server-sim, no prediction (option C): input frames, sanitizer, per-tick step, `NetworkTransform` for observers, owner renders from Ack. Prove authority and agreement first.
- 4b observer interpolation tuning + owner prediction/reconciliation (section 2.3). Record reconcile error stats from the owner (max/mean, snaps count).
Gate `EmberdelveNetMovementGate` (processes, scripted client driver): A runs `walk-forward` for 3 s at walk speed: server position delta equals expected `ResolveGroundSpeed` x time within tolerance (accounting for acceleration ramp, tolerance derived from a reference offline run of the same frames in the seams gate); B (observer) logs A's final view position within 0.15 m of the server's authoritative end position; B walks a square, ends within tolerance of its start; sprint/crouch change the measured speed; jump leaves the ground then lands; wall run-in does not pass the wall (server position stays on the near side).
Negatives (each = counters in the server log + unchanged position): `flood-input` (10x frames per tick), `replay-seq` (resent old seq), NaN/Infinity axes and yaw, |move| > 1, giant seq jump, input before spawn/after despawn, forged-owner (from U3A3) now with a movement RPC, frames sent for a destroyed actor. Speed bound: no sampled interval exceeds class run speed x 1.15.
Risks: CharacterController replay accuracy; Update-vs-tick ordering (server steps in the NGO tick event, not Update); `Physics.SyncTransforms` and controller enable/disable on teleport; Unity physics step is not involved (CharacterController.Move is immediate) which helps determinism but means gravity/grounded checks must run inside Step with the tick dt.

## 5. Verification strategy (what the root agent can actually drive)

### 5.1 Layers
1. Pure logic, EditMode NUnit (cheapest, run first): `NetLaunchArgs`, approval rules (cap/duplicate/class/protocol/oversize), `MoveInputFrame` quantization round trip, input sanitizer (NaN, flood, replay, clamp), reconcile thresholds. Existing runner `Run-EmberdelveEditModeTests.ps1` with a new test filter/asmdef.
2. In-Editor play-mode gates (existing pattern, no transport): seams parity, RunDirector server-mode join/remove, offline retention. Batch via `-executeMethod` or live Editor via eval.
3. Editor-as-host dev loop (not acceptance): live Editor play mode as `Host` + one built client process launched by eval; fastest iteration, and the only "loopback host + client" that is honest because the client is a separate process. Never two NetworkManagers in one process (statics, section 0.2).
4. Independent-process gate (the acceptance evidence): 1 server + 2 (then 3) client player processes. See 5.2.
5. Windowed evidence pass: same build, server headless, two clients windowed, review bridge driving real input and taking PNG snapshots (NETWORK_SPIKE: actual moving client screenshots per slice; a connected status or a frozen frame does not count). Needs an unlocked desktop session; do after the headless gate is green.

### 5.2 Process gate harness (C# in the Editor, so no shell is needed)
`EmberdelveNetProofGate` (Editor assembly) does, using only BuildPipeline and System.Diagnostics.Process:
1. Build once with `BuildNet` into a fresh run directory outside Assets (e.g. `<repo>/Builds/net/<runId>/Emberdelve.exe`), or reuse a prior build when `--ember-net-reuse-build <dir>` is given. Fail on any build error.
2. Pick a free UDP port (bind port 0, read it, release), create the run dir `logs/` and the ready/quit file paths.
3. Start the server with `-batchmode -nographics -logFile server.log --ember-net=server ...`; wait (poll, timeout 60 s) for the ready file; record PID.
4. Start clients with their scripts and slots, each with its own log; poll their logs for the expected markers with a per-step timeout; scenario steps run from the Editor side (e.g. "wait for A: WALK-DONE").
5. Kill only PIDs it started (never by process name); in `finally` kill survivors, then verify `Process.HasExited`; any survivor that had to be force-killed during the graceful phase is a FAILURE.
6. Parse all child logs: required markers present with sane values, forbidden patterns absent (`error CS`, `Exception`, `NullReferenceException`, `[Netcode]` errors, `FAIL`), expected rejection lines only in the expected quantity. Emit one summary in the existing format: `[Emberdelve][NetProof] PASS checks=N failures=0` (so `Run-EmberdelveGates.ps1` accepts it) and copy the child logs next to the Editor log as evidence.
Run modes: batch `-executeMethod ...Run` (blocking, calls `EditorApplication.Exit`), or from a live Editor via eval `RunFromEditor()` (non-blocking, polls on `EditorApplication.update`, writes the same summary). Operational constraint to settle with the user: the existing runners refuse to start while a GUI Editor holds the project lock, so either the Editor session is used for the whole gate (eval route, builds a player from the live Editor like `BuildReview`) or it must be closed for batch runs.

### 5.3 Scenario (U3A5 final), with expected evidence lines
1. Server up (ready file, scene loaded, `players=0`).
2. A (Warrior) and B (Archer) connect: `admitted id=<n> party=<p>`; each client logs `owner id=<n> views=2`.
3. A walks forward 3 s: server delta matches expected; B's view of A converges to server position (<= 0.15 m) and B's reconcile stats show no snaps for A's own walk.
4. B runs forge-owner, flood-input, replay-seq, NaN: server logs `REJECT <kind> count=<n>`; A and B positions unchanged by the cheats; speed bound holds.
5. Cap block (server max-players=3 in this scenario): late join C is admitted and sees A and B at current positions with unique ids; D is refused `server full`.
6. B is hard-killed: within timeout server logs `removed id=.. players=2 senders=2 registry=2`; A and C log the view despawn; D (retry) is now admitted.
7. A quits gracefully, C quits, D quits; quit file; server logs `shutdown players=0 senders=0 registry=0` and exits 0.
8. Gate checks: all PIDs gone, port reusable (a second server start on the same port succeeds in the handshake gate), no forbidden log patterns.

### 5.4 Multiplayer Play Mode (MPPM)
Not usable for acceptance: virtual players are extra GUI Editor instances created from the interactive Editor window; they cannot be launched or asserted from `-batchmode`, share licensing/UI state, and would still be separate processes only inside an interactive session. Optional for the human developer's manual loop; the plan neither needs nor installs it.

## 6. Risks and mitigations
1. Process-wide statics (CombatRegistry, CombatSenders, GameEvents, GameServices, RunContext): one world per process. Mitigation: server process owns the world, client rigs are views (not registered), never two logical worlds in the Editor, `RunDirector.OnDestroy` already resets the tables.
2. Hot-path refactor (PlayerMovement.Step, RunDirector server mode): regression in offline play. Mitigation: parity gate, full 45-group regression after U3A2 and U3A4, each slice commits only when counts match the recorded baselines (MultiPlayer 134, SkillAuthority, SenderOwnership, etc.).
3. NGO package/transitive churn (collections, burst, mono-cecil) altering build time or warnings; NGO RPC IL post-processing needs the asmdef to reference `Unity.Netcode.Runtime`, and attribute names differ 1.x vs 2.x. Mitigation: U3A1 isolates install + compile; verify the attribute surface (`[Rpc(SendTo...)]`, delivery, ownership option) in the resolved version before writing handlers; keep Mono scripting backend (IL2CPP needs the C++ toolchain, not part of this proof).
4. Firewall: binding UDP on 0.0.0.0 pops a Windows Defender Firewall dialog that blocks an unattended run. Default `--ember-net-listen=loopback`; LAN bind only with explicit user consent.
5. Headless focus/background and framerate: clients stall unfocused (`runInBackground`), headless server spins at max FPS (`targetFrameRate`), Input System devices missing (scripted driver bypasses devices).
6. Timing flake: timeouts, startup order and the 30 s default disconnect timeout. Mitigation: lowered test timeouts via flags, marker-based waits (not sleeps), generous per-step budgets, one retry only for process start (never for assertions).
7. CharacterController prediction mismatch: error spikes on slopes/steps/contacts. Mitigation: option C intermediate, thresholds, replay with the same tick dt, fallback B only by user decision.
8. Scene management: server and clients must load the same scene via NGO; existing `SceneManager.LoadScene` calls (lobby, restart) must be inert online. Mitigation: role guards, covered in the seams gate.
9. Half-spawned actors: spawn only after TryJoin succeeds; disconnect during spawn must still clean (test: client quits between approval and spawn).
10. Identity confusion: `PlayerId` semantics change (server-issued). Mitigation: single setter, assertion in gate that events/HUD keyed ids match; no payload carries an id.
11. Evidence false-greens: connected-only, frozen frame, or single-process claims. Mitigation: all positions are compared against independently computed expectations, cheat tests assert both the rejection counters AND unchanged state, process liveness/exit codes checked, forbidden-pattern scan on every child log.
12. Windows specifics: path/quoting of `-logFile`, antivirus delaying new exes, port reuse (TIME_WAIT is irrelevant for UDP), leftover processes from a crashed gate (track PIDs in a file; cleanup step at the start of the next run kills only PIDs recorded by the previous run).
13. Distinct from U3B: no combat/inventory over the wire here. Do not let U3A add sender-bound command RPCs beyond the test RPC; U3B owns that surface.
