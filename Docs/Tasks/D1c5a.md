## Changes
1. M-c guard exclusion (authority half).
   - `Runtime/Core/GameContracts.cs`: new optional `IGuardStateSource { bool IsGuarding }`. `PlayerRig` implements it with its existing `IsGuarding` property (no new state).
   - `LocalCombatAuthority.Swings.cs` `TryBeginMeleeSwing`: right after the dead check, an instigator that is an `IGuardStateSource` reporting `IsGuarding` is refused with "instigator is guarding: lower the guard before swinging". It runs before the sequence stamp, the cooldown stamp and the chain bookkeeping, so a refusal changes only `RejectedCount` / `LastAttackRejectReason` (the same intent is accepted once the guard is down).
   - `PlayerRig.IsGuardingWithDefense` (the one place the damage path reads the guard: `TryResolveGuard`, `TryGetArcReduction`, `TryGetProjectileGuardBlade`) now also requires that the authority does not report the rig's own swing in progress (`ICombatFlowState.IsSwingInProgress`, windup + active + recovery). The raw `IsGuarding` read stays the client flag. Entities that are not `IGuardStateSource` (enemies, fakes) are never refused. Guard ownership itself is still U3B.
2. Data / health gate: new `Editor/EmberdelveCombatDataGate.cs` + `.meta` (guid `3138a2a85f524b2990bba7702c2c0800`, unique in the tree; the `.meta` is two lines with no trailing newline like its siblings).
3. Swing blocker mask. `LocalCombatAuthority.Swings.cs`: `SwingLevelMask` replaced by `internal SwingBlockerMask` = (config level mask, or the level layer without a config) minus the interact layer, the loot layer and the config's `interactMask`. The wall test (`Linecast` eye->hand, `CheckSphere` at the hand, `Linecast` along the blade, all `QueryTriggerInteraction.Ignore`) is unchanged and now reads this mask. Before this change props were already off the mask only because the shipped level mask is the level layer alone; the derivation makes it independent of config edits. Decision (per the review default): chests, Ember Gate pillars (built and parented on `Emv_Interact`), loot and any trigger collider are walk-through for a blade; only level geometry stops a swing. Projectiles are untouched.
4. Item 6: no lobby card / HUD / tooltip reads `WeaponData.windupTime` / `activeWindow` / `recoveryTime` in this tree (grep over Runtime: the only readers are `AuthorPattern`, the asset library seed, and gates). The authoring seed in `EmberdelveAssetLibrary.AuthorPattern` (weapon fields copied into the pattern at build time) is left as it is. To make the pattern the single display source, `WeaponData` gets `DisplayTiming` / `DisplayWindup` / `DisplayActive` / `DisplayRecovery`: the first swing pattern's `Timing` when `UsesSweptMelee`, else the weapon's own fields (ranged, legacy). No serialized field removed or renamed. Any future card must read these.
5. Item 7: `Docs/Design/DND_PARITY.md` new section 1.5a "Recorded combat rules": deepest-volume-in-window melee location (ties: lower enum value, head first), projectile first-touch, enemy swept attacks, 720 deg/s turn ceiling, plus the three D1c5 rules.
6. Item 8: smoke melee assertion tightened (literal location table and sword zone bands, location and headshot checked, tolerance 0.15 for the literal damage); SweptMelee production-configuration section; real-time buffered-press edges; CombatFlow display-timing and guard sections.

## Risks
- Not compiled. Likeliest compile points: tuple deconstruction in the new gate loops (`foreach ((string label, string layer, bool trigger, bool blocks) c in cases)` with a `null` layer element), `internal SwingBlockerMask` read from the Editor assembly (relies on the existing `InternalsVisibleTo("Emberdelve.Editor")`), `IGuardStateSource` on `PlayerRig` (CRLF file).
- Physics: the prop and wall fixtures stand at 3000,3000 with a wall/prop 8 x 4 x 0.3 m at z = 1.0; the slash starts pointing sideways, so the level-wall control relies on the blade moving into the surface (it did in the existing wall gate at z = 1.6; z = 1.0 is closer to the hand, a "buried base" also counts as a stop).
- `OwnSwingRunning` reads the authority from `GameServices` on every guard resolution (a dictionary lookup + a cast, only while `_guardHeld`); no allocation.
- A rig whose swing is in progress cannot block even in the recovery phase of a swing the player has already finished visually (authority recovery is 0.3 s for the sword). This is the intended "block and attack are exclusive" rule; MeleeCombat already drops the guard for the whole swing, so the visuals agree.
- Level01 data gate assumes enemies are spawned and registered within three frames of play mode (the CombatFlow gate relies on the same).
- Smoke literal-damage check could flake only when the test's sampler and the authority's grid disagree about the zone side; the within-0.01 edge guard covers the known case.
- The DND_PARITY contact window numbers (0.016 to 0.020 s) are taken from `AuthorPattern` calls; enemy patterns use 0.02.
