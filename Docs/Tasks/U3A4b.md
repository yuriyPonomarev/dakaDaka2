Status: written WITHOUT compiling or running anything (no Unity and no C# compiler in the implementer sandbox). Base: `e8214bd` (verified in real Unity by the root agent: NetMovement 142/0, NetAdmission 108/0, NetSeams 149/0, NetProof 35/0). Scope: `Docs/Tasks/U3A_plan.md` section 2.3 (owner prediction paragraph), section 4 "U3A4 4b", risk 7. Observer interpolation is unchanged (server-authority `NetworkTransform`, `Interpolate = true`).

## What changed

### 1. Determinism of the Step path (`PlayerMovement`)
Problem (the open item of 4a): `Move` seeded the acceleration ramp from `CharacterController.velocity`, which Unity derives from the RENDER delta time, so `Step(state, frame, dt)` was not a function of its arguments (the ramp shape depended on the server frame rate; a client at another frame rate would never match).

Design: the **Update path is untouched** (it still seeds from `controller.velocity`; `StepCore` is called with `relativeToViewTransform = true` and the new code is skipped by that flag). The **Step path** keeps `_stepVelocity` (planar, xz) = the transform's actual displacement over the dt that was passed in, measured around the whole `StepCore` (so a dash step is covered too), and seeds `currentHorizontal` from `_stepVelocity.magnitude`. It is the same quantity the controller velocity expressed (planar actual displacement over dt) but with the right dt. `TeleportTo` resets it. The offline parity gate (Update vs Step with the recorded render dt, tolerance 1e-4) should be unaffected because with dt == the render dt both seeds are the same number up to float rounding; the gate is NOT changed. If it ever differs by more than the tolerance that is the signal that `CharacterController.velocity` is not plain displacement/deltaTime in this Unity version (see risks); do not widen the tolerance, change the Step seed instead.
New (additive) public surface on `PlayerMovement`: `GroundMask`, `ApplyPredictionParams(in MoveParamsData)`, `CapturePredictionState(out PredictedState)`, `RestorePredictionState(in PredictedState)`, `NudgeBy(Vector3)`, `PlaceAt(Vector3)`. `ResolveGroundSpeed` / `ResolveWalkSpeed` return the server numbers when `ApplyPredictionParams` was called (never on a component that already has a class: refused).

### 2. Server Ack and resolved movement numbers (`NetMovementServer`, `NetPlayerRig`, `NetMoveWire`)
- `[Rpc(SendTo.Owner, Delivery = RpcDelivery.Unreliable)] AckRpc(MoveAckWire)` every 2nd network tick (`ReconcileRules.AckEveryTicks`). The wire struct carries `LastProcessedSeq, ServerTick, X Y Z, VerticalVelocity, PlanarVx, PlanarVz` (the spec) plus `JumpCooldown, CapsuleHeight, StateFlags(crouched)` so a snap can replay exactly. No identity parameter. The state is captured right after a QUEUED frame (a real client frame), under that frame's sequence number; repeated / neutral fill steps do not overwrite it, so the owner always compares like with like.
- `NetworkVariable<MoveParamsWire> MoveParams` (owner-read, server-write): resolved walk / sprint / crouch speeds (DEX, gear, status, flow already folded in), stand / crouch height, jump height, ground layer mask. Written at registration, re-checked every 15 ticks, republished on change (log `params id=..`). The owner applies it through `ApplyPredictionParams`; the client has no class data of its own in U3A.
- Server log additions: `params id=N walk=.. sprint=.. crouch=.. stand=.. crouchH=.. jump=.. mask=..`, final line also `acks=N shoves=N`, and (development builds) `dev-shove applied ...`.

### 3. Owner prediction (`NetOwnerPrediction`, new, client only; fed by `NetInputSender`)
- Starts when `MoveParams` is valid (first tick after that). Until then the owner behaves as in 4a. On start: `NetworkTransform.enabled = false`, `CharacterController.enabled = true`, `ApplyPredictionParams`, `TeleportTo(current transform position)`.
- Per network tick, for the first (honest) frame of the tick: `PredictionRules.ServerView(frame)` (quantized as on the wire and `|move|` scaled exactly like the server's `InputSanitizer`; unit-tested against it) -> `PlayerLook.ApplyAimPose` -> `PlayerMovement.Step(frame, TickSeconds)` -> ring entry `(seq, frame, state)`. The extra frames of a flood step and the hostile frames are not predicted.
- On Ack (`PredictionReconciler.OnAck`, pure): compare the stored entry for `LastProcessedSeq` with the server state (3D distance). `<= 0.10 m` ignore; `<= 1.0 m` **blend**: the unacked entries are translated by the correction (same trajectory) and the body is nudged by linear shares over 100 ms (3 ticks) through `controller.Move` (walls still stop it); `> 1.0 m` (or non-finite) **snap**: `TeleportTo(server)`, `RestorePredictionState(server)`, then every entry still in the ring (the frames the server has not processed) is stepped again and its stored state rewritten. Unknown sequence (before prediction started, flood extras) = `missing`, older-or-equal = `stale`, neither is an error.
- Fight guard: at the start of every predicted tick the body must still be where the predictor left it; if not (the transform sync wrote to it) it is counted (`fights`) and put back (`PlaceAt`, state kept).
- Real-input owner: the view (yaw and pitch) is applied locally every render frame once prediction runs (no round trip for looking).
- Logs: `[client] prediction started walk=.. sprint=.. crouch=.. jump=.. pos=..`; `[client] reconcile acks=N maxErr=.. meanErr=.. blends=N snaps=N replays=N replayFrames=N missing=N stale=N fights=N at=<tag>` (every 5 s when changed, after every script step with `at=step:<name>`, `at=script-end`, `at=final` at despawn); `[client] reconcile SNAP error=.. seq=.. to=(..) replayed=N`; `[client] predict pos=(x,y,z) seq=.. ack=..` (the owner's own position, when it moved or every 2 s).

### 4. Decision: AnticipatedNetworkTransform vs custom loop
Evaluated, NOT used. (a) It writes the transform itself, which an enabled `CharacterController` resists / overrides (the same reason `TeleportTo` toggles the controller); (b) it has no notion of an input sequence to compare and replay, which is what a CharacterController needs; (c) switching the component means rebuilding the generated prefab and re-verifying a new API surface without being able to compile here. The custom loop is ~150 lines of engine glue around a pure, tested core. The plain `NetworkTransform` stays on the prefab (observers keep interpolating it); the owner switches its own copy off at runtime (UNCERTAIN, below) and guards against it anyway.

### 5. Pure parts (`Emberdelve.NetRules`, NUnit)
`PredictedState` / `PredictionEntry`, `PredictionRing` (capacity 128, overwrite counted, `IndexOf / DiscardThrough / TranslateAfter / Set`), `ReconcileRules` (`Decide`, thresholds), `BlendCorrector`, `ReconcileStats` (+ the log line), `PredictionReconciler`, `PredictionRules.ServerView`, `MoveParamsData`, `NetDevShove` (+ `NetLaunchArgs.DevShove / DevShoveFile`). Tests (new files in `Tests/EditMode/NetRules`): `ReconcileRulesTests`, `PredictionRingTests`, `PredictionReconcilerTests` (includes ServerView == InputSanitizer output over a grid of axes), `PredictionStateTests`, `NetDevShoveTests`.

### 6. Dev switch for the forced correction
`-ember-net-dev-shove SLOT:YAW[:METERS]` + `-ember-net-dev-shove-file PATH` (server, development builds / Editor only, parsed everywhere): when the file exists the player admitted with that dev slot is teleported once METERS (default 2) along world yaw YAW between two ticks; the speed tracker is told so it is not read as speed. The owner cannot predict it, so it must snap.

## Gates
### `EmberdelveNetSeamsGate` (play mode, +14 checks, expected 163)
New `StepDeterminism`: the same 150 frames stepped with the same tick dt inside ONE render frame vs one per render frame at a 4x longer captured render dt give the same positions (<= 1e-5); capture -> step -> `TeleportTo` + restore -> step reproduces the span (covers vertical velocity, ramp velocity, jump cooldown, capsule height, crouch bit); `ApplyPredictionParams` refused on a movement that has a class, refused for NaN, honoured on a bare one (speeds, crouch-over-sprint precedence, replacement, ground mask). Existing checks untouched (StepParity still compares Update with Step).

## UNCERTAIN: new NGO API usage (cannot be compiled or run here)
1. `[Rpc(SendTo.Owner, Delivery = RpcDelivery.Unreliable)]` (`SendTo.Owner` is new; `SendTo.Server` + `Delivery` was already verified).
2. `NetworkVariable<MoveParamsWire>` with a hand-written `INetworkSerializable, IEquatable<>` struct and `NetworkVariableReadPermission.Owner` (the project's other variables are ints and `FixedString32Bytes`).
3. **`networkTransform.enabled = false` on the owner stops the sync from writing to the body.** This is an assumption about NGO 2.7. If it is wrong, the fight guard puts the body back every tick (so prediction still works), the `fights` counter climbs and the gate's `fights == 0` check fails with exactly that label; the remedy would be a `NetworkTransform` subclass that skips applying state for the owner (needs a prefab rebuild).
4. `using Unity.Netcode.Components` (NetworkTransform) at runtime in `Emberdelve.Net` (the Editor builder already does it).
Everything else (NetworkTickSystem.Tick, Rpc + RpcParams, NetworkVariable int / FixedString, OnValueChanged) is the pattern already verified in 4a.

## Risks and notes
- **Server repeat / neutral steps.** If the server's queue is empty at a tick it repeats the last move (4a behaviour); the owner did not predict that extra step, so the next Ack shows one step of error (about 0.17 m at walk speed) and a blend corrects it. Rare on loopback but possible; it would raise `blends` and slightly `meanErr`, never `snaps`. The gate bounds `snaps == 0` and `meanErr <= 0.05`, not `blends`. If it shows up the right fix is a 1-frame prebuffer on the server, not a looser threshold.
- **Server-only colliders** (chests, enemies; other players' controllers are disabled on a client) are real differences between server and owner; walking into one produces genuine corrections until U3B replicates them. The proof scenario has no enemies and clear lanes.
- **Parity of the Update vs Step gate** relies on `CharacterController.velocity` being displacement / render deltaTime. If NetSeams `StepParity` fails by more than 1e-4 after this change, that assumption is the first thing to check (log the two seeds).
- **flood-run** (hostile, 10 flushed frames per tick, only the first predicted): the server pops one frame per tick like the client predicts one per tick, so positions should track, but the Ack's frame is often an unpredicted extra (`missing`). Not asserted; the honest statistics are read before it.
- **Initial vertical state**: a fresh owner starts at vertical velocity 0, the server at rest sits at about -2.6; both are grounded within the skin width and agree after two ticks (error far below 0.10 m).
- **Dash** is not part of the predicted state (offline-only until U3B); `MoveParams` re-publishing covers speed changes but a mid-run change reaches the owner one round trip late (one blend at most).
- **Owner rotation**: the body yaw on the owner comes from the predicted `ApplyAimPose`, not from the transform sync.
- Host process (`HostPlayer`) is unchanged: it still moves with its own `Update`.
- Numbers (0.10 / 1.0 / 100 ms / ack every 2nd tick / ring 128) are the plan's; the ring holds about 4 s of frames, more than any realistic round trip.

## CI regression follow-up (commit 560fef5 on CI)

### 1. EditMode `PredictionReconcilerTests.ServerView_QuantizesLikeTheWire` (166/167): the TEST was wrong
- Input (0.3333, 0.9999) quantizes to 42/127 = 0.33071 and 127/127 = 1.0. That pair has length 1.109 > 1. `InputSanitizer.Submit` (the real server path) divides a quantized pair longer than 1 down to length 1, and `PredictionRules.ServerView` deliberately mirrors that (the test `ServerView_MatchesWhatTheSanitizerHandsTheSimulation` compares the two on 64 axis pairs and passes). 0.33071 / 1.1094 = 0.31398 is exactly the "was" value in CI. The test compared against the un-normalized `Quantized()` value, which is not what the server hands the simulation.
- Production code is right; `NetOwnerPrediction` calls `PredictionRules.ServerView` (NetOwnerPrediction.cs:141), the same quantize + normalize order as the server, so no production change.
- Fix: the test now has two parts: an in-circle input (0.3333, 0.6) must equal the plain wire value, and the original out-of-circle input must equal the NORMALIZED quantized pair. No expectation was loosened.

### 2. EmberdelveNetAdmissionGate failed once in CI (104/108): ROOT CAUSE NOT DETERMINED
Evidence from `Builds/net-admission/20261028-150012/logs` (server tick numbers, 30 Hz):
- B's last frame was accepted at about tick 352 (222 frames since tick 130); the hard kill. The server removed B at tick 472 (120 ticks = the 4000 ms disconnect timeout, as designed).
- A was healthy for those 120 ticks (acc rose 1 per tick up to 418, `depth` 2-3, acks flowing). A's last accepted frame was tick ~471-473, the SAME tick B's timeout was processed (tick 472). After that the server accepted nothing from A: final line at tick 589 (118 ticks = 3.9 s, the same 4000 ms timeout counted from A's last packet) has `acc=418`, `redundant=833` (about 2 per accepted frame, i.e. no batch after 418), `neutral=120`.
- Client A kept running at 30 Hz the whole time (seq 418 -> 538, `predict` lines continue), received B's despawn and the ack for 418, and then never an ack again (`lastAck=418`); the server then closed the connection (`ClosedByRemote`, exit 13).
- D (launched afterwards) never got an approval line on the server at all and timed out after its 60 s connect timeout: so the server received NOTHING from ANY peer after tick ~472, including a brand-new connection, for the rest of the run (more than 60 s).
- The server process was healthy: tick counter advanced, `status` lines every 2 s, UTP timers fired (it disconnected A by timeout), the quit file worked. No exception, no `Error`, no transport-failure line in any log.
- So it is not "A hiccuped" (A and the server both ran normally) and not "the CI machine paused" (both loops alive), and not a flood/fragment/queue symptom of the Ack path: acks to a dead client are only produced when a real frame has been processed (`AckDirty`), so the server was sending B no Acks and no NetworkVariable writes for the whole 4 s before the failure (B's `acks=111` = 222 frames / 2, nothing after the kill). The only traffic toward B's dead port in that window is transport heartbeats, the same in U3A4a.
- What it looks like: the server's UDP receive path died permanently at the moment B's timed-out connection was removed (`NetworkManager` disconnect callback -> `RemoveActor` -> `Despawn(true)`) while the UTP driver kept running its timers. Candidates, none provable from these logs: (a) Windows UDP `WSAECONNRESET` (ICMP port-unreachable from B's closed port surfacing on the server's unconnected UDP socket and killing the receive path; the Unity Transport version in use may not survive it); (b) a UTP/NGO fault when a timed-out connection is disconnected while other connections are active. U3A4b adds ack/params traffic but, by the counting above, none of it goes to a dead peer, so there is no evidence U3A4b caused it; it may simply be that this is rare (it passed 108/0 on an identical rerun) and 4a's single run did not hit it. Not claimed as fixed.

### Mitigations made (all keep offline behaviour identical)
- `NetMovementServer.CanSendTo`: Acks and params writes are sent only if the object is spawned, the owner is in `ConnectedClientsIds`, and the owner delivered a real frame within the last 30 ticks (1 s). Otherwise the Ack is dropped (`acksSuppressed`) and the params write is deferred (`paramsSuppressed`, it goes out when the owner is heard from again; first publish at registration is unaffected). This guarantees the 4b server never feeds a dead or silent endpoint, whatever the cause above is.
- New diagnostic so the next occurrence is explainable: `rx-quiet id=.. client=.. quietTicks=.. others=[id:quietTicks,..] connected=[..] maxGapMs=.. acksSuppressed=.. paramsSuppressed=.. tick=..` is logged when a player has been quiet 30 ticks, then every 90. If ALL players show the same quiet tick while `maxGapMs` is small, the receive path died (not a stalled server). The move final line also carries `acksSuppressed`/`paramsSuppressed` (appended after `shoves=`, the movement gate regex is unaffected).
- Gate: after B's removal the gate now checks that A's ack still advances by at least 30 (`A is still acked by the server after B's removal`). This does not weaken anything; it makes this failure show up as one named check at the right moment instead of four later symptoms. The gate is NOT made to retry or to tolerate a dropped A: a server that stops receiving everyone after a hard-killed client is a real defect, not CI timing (the 4000 ms timeout is the design value and both sides ran normally).

### If it recurs
Read the `rx-quiet` lines and the new gate check. If the receive path dies again right after a timed-out removal, the next step is not more mitigation in game code but (1) checking the Unity Transport version for the Windows connection-reset handling, (2) running the server with a separate `UnityTransport` log level raised, and (3) trying removal by `NetworkManager.DisconnectClient(id)` before the transport timeout (e.g. the server disconnecting a peer that has been quiet for N ticks itself) to see whether the fault is tied to the timeout path.
