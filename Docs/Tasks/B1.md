## 1. Reload swap lock
- D1b rule found: `ClassLoadout.IsActionLocked` = authority swing in progress OR `RangedCombat.IsDrawing` (the crossbow/bow draw already blocks swaps). B1 mirrors it: also `RangedCombat.IsReloading` (ranged component enabled). New `IsReloadLocked`, and `ActionLockMessage` ("Cannot swap weapons while reloading" / "... during an attack"), used by `SwitchToSlot`, `TryReplaceWeaponSlot` and both `Equipment` main-hand weapon refusals. A refusal changes nothing and queues nothing (swap input is read on its frame only; `RangedCombat` ignores a primary press while reloading).
- Forced changes (`ForceSwitchToSlot`, class apply `Equip`) are unlocked. Fix for a latent hole: `RangedCombat.Initialize` returned early for a non-ranged weapon WITHOUT resetting `_reloading`/`_drawing`; a cancelled reload left the flag stale (harmless to ammo, because `Equip` stores the magazine before the weapon leaves and an unfinished reload adds nothing, but it would have kept `IsReloading` true on the disabled component). Both are now cleared. No free ammo: stored magazine/reserve are exactly the pre-reload numbers (gated, also after waiting out the reload time).
- Buffered melee press: `MeleeCombat.Initialize` already cleared `_bufferedUntil`; `OnDisable` now clears it too (a press buffered in a recovery can no longer survive the weapon leaving the hand). A refused swap during the swing neither drops nor redirects the buffered press: it becomes the next swing of the SAME weapon (gated).
- New test seams `EmberdelveInput.ReloadPressedOverride` / `SwapPressedOverride` (internal, same pattern as the primary overrides; file is mixed CRLF/LF, edit kept CRLF).

## 2. Slow merge (`StatusComponent`)
- Old rule (every kind): one entry per kind; reapply = max remaining and, for Slow, min magnitude. So a short strong slow onto a longer weak one became the strong magnitude for the long time.
- New rule for `StatusKind.Slow`: separate entries, each with its own magnitude and remaining time, expiring individually. `SpeedMultiplier` is already the min over slow entries = strongest active at any moment. "Refresh, not stack": after each apply, any slow entry that another slow equals-or-beats in BOTH strength (magnitude <=) and remaining time (>=) is dropped (the older of two equal ones stays). Same slow again = one entry with max duration; a weaker-and-shorter one disappears behind a stronger-and-longer one; hard cap 8 entries (shortest dropped). Non-slow kinds keep the old rule exactly.
- `RemainingOf(Slow)` = longest remaining slow entry (documented; the AttributeSkillGate checks it only on single-entry cases). `RaiseStatusChanged` on expiry reports the kind as ended only if no other entry of the kind is left. `Update` now calls `internal Tick(float)` so a gate can step time exactly.
- CombatFlowGate "once, refresh not stack, strongest wins" checks were read and are unchanged and hold (single entry for repeated sword hits, 0.55/3 s skill slow stays against the 0.9/0.6 s hit, `ActiveCount == 1`).
