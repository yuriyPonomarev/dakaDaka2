# U3B3 - server-authoritative weapon combat over the network (PvP + PvE visibility)

Status: implemented, NOT compiled or run by the author (no Unity available). The local tester must compile and run everything below. Every NGO spelling that was not already used in this repo is listed under "Known limits / risks" with a fallback.

## What changed

Client -> server (reliable, ordered; `NetPlayerRig.CombatIntentRpc(int kind, uint sequence, RpcParams)`, `InvokePermission = Everyone`, compiled in every build)
- Intent kinds (`CombatIntentKind`, NetRules): AttackPress, GuardDown, GuardUp, DrawStart, DrawRelease, SwapWeapon. No aim, charge, target, time, damage or id travels with an intent.
- `Net/NetCombatServer.cs`: identity first (connection -> identity row -> NetworkObject reference equality; nothing of the object is read on a fault, the SENDER is charged), then the connection's `CombatIntentGate` (kind/sequence/rate on the server clock, same verdicts as `SkillIntentGate`; burst 10, 10/s, probation = empty gate), then execution on `row.Rig`.
- Shared abuse accounting: every combat reject is charged to the connection's `SkillRejectLedger` owned by `NetSkillServer` (new internal `DropIfDisconnecting`, `StrikesOf`, `ChargeReject(..., channel)`), so skill and combat rejects add up to ONE disconnect decision ("skill abuse", probation by slot memory). Log tag is `combat reject=...` (the skill gate's `skill reject=` greps are unaffected).
- Execution = the code the offline game runs: `MeleeCombat.TryBeginSwing()` (swept D1 hit detection), `RangedCombat.ServerBeginDraw/ServerReleaseDraw` -> `LocalCombatAuthority` projectile launch (D2 fixed-step ballistics), guard through `PlayerRig.SetGuardHeld` (MeleeCombat keeps the guard flag down during a swing), swap through `ClassLoadout.RequestWeaponSetSwap()`. Hit location, guard reduction, armor, falloff, teams/friendly fire are the authority's. Both players and enemies are targets exactly as offline (`CombatTeams.AreHostile`).
- The CHARGE of a draw is measured by the server: `ServerDrawTimer` (NetRules, pure) starts at DrawStart, the release computes the charge from the server clock; a release below `minChargeToFire` fires nothing; an abandoned draw is cancelled after `draw time + 20 s`.
- `MeleeCombat.RemoteDriven` / `SetRemoteGuard`, `RangedCombat.RemoteDriven`: a server rig has no input device; the network layer supplies presses and the guard level. Set by `NetCombatServer.OnAdmitted` for remote (non-host) players only.

Offline / host unchanged: no listener is attached offline (`LocalCombatAuthority` report events are null-checked), the host's own player never goes through the channel (and is refused with `ClientRole` if it calls it), `HealthComponent` changes only act when `NetRole.IsClientOnly`.

Clients never resolve combat
- `HealthComponent.ApplyDamage` does nothing in a client-only process (counts `ClientBlockedDamage`), no local regeneration there, the only writer is `ApplyReplicatedState` (refused in every other role). `ClassLoadout.Update` no longer swaps locally in a client. Melee/Ranged components stay disabled on client views. The client's final summary prints `clientBlockedDamage=N` (expected 0).
- Client log wording is "server-hit/server-swing/server-shot": a client reports what the server did, never "a hit applied here".

Replication
- `NetworkVariable<CombatVitalsWire> Vitals` (Everyone read, Server write): player health, max and death; published by `NetCombatServer.Tick` at most 10/s and only when the 0.1-quantized value changes. Clients show it through `HealthComponent.ApplyReplicatedState` (log `[client] vitals id=.. health=.. max=.. dead=.. owned=.. applied=..`).
- Owner feedback: `CombatResultRpc` (SendTo.Owner, reliable) per request that passed the gate: accepted/refused + reason code + the charge the server measured. Gate rejects get no answer (amplification).
- Observers: `CombatSwingRpc` (weapon id, pattern id, combo step, windup/active/recovery), `CombatShotRpc` (origin, direction, speed, gravity, max time, range, charge, radius, length: everything D2's integrator needs), `CombatFlightEndRpc`, `CombatHitRpc` (feedback only). All `SendTo.ClientsAndHost`, handlers act only in a client-only process, so the host never double-presents. `NetCombatFx` advances an arrow replica with `ProjectileBallistics.Advance` and retires it where the server says the flight ended.
- Enemies (split, see below): `EnemyPoseRpc` (owner, unreliable, 5 Hz) and `EnemyVitalsRpc` (owner, reliable, resent on any change and once to a new client); `NetEnemyViews` keeps a proxy capsule per enemy (no collider/brain/health), removed on death.

Launch arguments / scripts
- `-ember-net-party-size N` (1..3, server/host): lowers the largest party. With 1 every player is alone in a party, so two networked players are hostile (without it they are party mates and friendly fire is off). Applied once the RunDirector is ready (`RunDirector.SetPartySizeOverride`).
- Scripts `melee-duel` and `ranged-shot` (all builds) and `combat-abuse` (development builds only, like the other hostile probes). Role by server id: lower id = attacker/shooter/victim, higher = defender/target/abuser. Numbers come from the content of `-ember-net-script-start-file` (`CombatScriptParams`: `stop interval presses walk away awayyaw shots hold early pspeed pgrav pitch aimheight`), written by the gate from authored data; nothing is typed into a client. Scripted clients steer the movement stream through `NetInputSender.DriveFromCombatScript` and take no real input.
- Real input (windowed owner): primary press -> AttackPress or DrawStart/DrawRelease, secondary held -> GuardDown/GuardUp, swap key -> SwapWeapon. The client does not know which hand the server wields (class loadout is not initialised on client views): it starts as melee and flips to draw mode when the server answers `WrongWeapon`.

Assemblies: `Emberdelve.Net` now also references `Emberdelve.Rules` (ProjectileBallistics for the arrow replica and the shooter's pitch). Acyclic: Rules has no references.

New files
- NetRules: `CombatNetLimits`, `CombatIntentGate`, `ServerDrawTimer`, `CombatVitalsData`, `CombatScriptParams`.
- Runtime: `Combat/LocalCombatAuthority.Reports.cs` (observer events `HitResolved`, `ProjectileLaunched`, `FlightEnded`, with the damage factors).
- Net: `NetCombatWire`, `NetCombatServer`, `NetCombatSender`, `NetOwnerCombatView`, `NetCombatFx`, `NetEnemyViews`.
- Editor: `EmberdelveNetCombatGate`.
- Tests (EditMode, NetRules): `CombatIntentGateTests`, `ServerDrawTimerTests`, `CombatVitalsDataTests`, `CombatScriptParamsTests`, `CombatNetScriptAndArgsTests`.

## Decisions
1. Intents, not state: the client says what it did, the server's rig does it. Aim is the last sanitized movement frame (log field `inputAgeTicks`); the swing/shot can use an aim up to the input's network delay older than the client's key press. This is a deliberate trade (no lag compensation yet, no rewind).
2. Draw timing is the server's. Network jitter therefore shortens/lengthens a hold by the jitter; a client cannot claim a charge.
3. One abuse budget per connection across skill and combat (shared ledger). A hostile client cannot spend two budgets.
4. Presentation events are broadcast RPCs, never state. Health/death are NetworkVariables so a late joiner is right at once.
5. Enemies are snapshots through each client's own player object, not NetworkObjects: the dungeon's enemy spawner is a scene-authored server system that client processes do not have (NetSceneRoles), and adding a NetworkObject enemy prefab would regenerate committed prefab/catalog assets. Documented split: no animation/hit reactions/server-side enemy arrows for observers; health and death are visible.
6. Gate derivation: data-derivable factors (weapon base, pattern and combo multipliers, hit-location table, guard reduction as reported, armor formula `x*100/(100+R)`, charge lerp, air-time falloff table, projectile speed/gravity, ballistic flight and contact point) are re-computed from assets. The attacker's outgoing multiplier (attributes/passives/status), the flat weapon bonus, the zone multiplier, the armor rating and the guard reduction are READ from the server's own report and only bounded for plausibility (independently re-deriving them needs the full attribute/gear stack; not attempted).

Scenarios
- melee-duel (server `--ember-net-no-enemies -ember-net-party-size 1`): A and B warriors in different parties. A walks to the data-derived stop distance (0.6 x the pattern's reach) and presses every swing time + 0.4 s. B takes the first hit open, guards until a blocked hit is reported, drops the guard and dies. Gate: every `combat-hit` amount equals the data-derived value; first hit open, >=1 blocked with reduction >0; health lost equals the sum of reported amounts and the max health equals `AttributeRules.Derive(...).MaxHealth`; death on the server, in both client logs (`vitals ... dead=True`); B's four post-mortem actions are refused `Dead`; B never swings; clients log every `server-hit`/`server-swing` and no `combat-hit`; `clientBlockedDamage=0`.
- ranged-shot (A archer, B warrior target): the player who spawns in dungeon row 3 walks east (`awayyaw=90`) to a distance from the weapon's air-time falloff window (`speed x mid window`, 8..18 m); the shooter solves the pitch with `ProjectileBallistics.SolveLowPitch` from the weapon's speed/gravity. Two full draws (hold = 1.6 x draw time + 0.8 s) then one deliberately early draw. Gate: launch parameters equal the weapon data; full draws carry charge 1.000 measured by the server; each hit's contact point equals the D2 integration of the logged launch at the logged air time (tolerance one step + 0.6 m), drop > 0; falloff scale equals the weapon table; final damage equals base x charge lerp x outgoing x location -> guard -> armor -> falloff; observers got every launch/flight end; an arrow replica's flight time matches the server's. The early draw must have charge < 1; `TooEarly` is asserted only when the client's 0.12 s send spacing is below the weapon's minimum-charge window (otherwise it is logged, not asserted).
- combat-abuse: B forges 3 intents on A's object, sends 1 valid, 1 replay, 1 malformed kind (99) and 40 guard toggles. Gate: identity=3, invalid=1, replay=1, flood>=1, total = burst + threshold (read from the server's policy line), charged to B, A never touched (no intent processed, no vitals change, no hit/swing), flood logging rate limited, traffic after the decision dropped (`ignored>=1`), B exits with the unexpected-disconnect code and the reason `skill abuse`.
- enemies: server with enemies; the client's `enemy-view summary total` equals the server registry count, poses arrive, health lines are logged. Enemy death display is the same path (`dead` flag) but is not scripted in the gate.

## Known limits / risks
- NGO spellings not verified without a compile: `SendTo.ClientsAndHost` (alternative `SendTo.NotServer` + remove the `NetRole.IsClientOnly` guards would also work), `Delivery = RpcDelivery.Unreliable` with `SendTo.Owner` (already used by `AckRpc`), a `NetworkVariable` of an `INetworkSerializable`+`IEquatable` struct with Everyone read (same pattern as `SkillState`). If `InvokePermission` fails to compile, fall back like U3B2 (`RequireOwnership = false`), and update the gate's static check.
- `Emberdelve.Net.asmdef` gained a reference to `Emberdelve.Rules`; if the tester prefers not to, move the arrow replica's integrator and the pitch solve behind a small helper in Runtime.
- Aim lag: an action uses the aim of the newest processed movement frame. With 50 ms input latency the swing can lag the screen by about that long. No rewind/lag compensation.
- Draw movement penalty (`SetAimingPenalty`) is applied on the server rig but owner prediction does not know it, so a drawing owner can see small reconciliation corrections.
- Reload is not on the wire (no intent kind); ammunition and magazines are the server's. A reload key is a follow-up.
- Real-input weapon mode is learned from the server's WrongWeapon refusal; after a swap the first press can be refused once.
- Enemy arrows/melee are not shown to observers; enemies are proxy capsules with no animation. Enemy death is shown by removal.
- The gate cannot assert the exact attribute multiplier (read from the server's report). The row-3 / east-walk assumption of the ranged scenario comes from the current dungeon layout (spawn cells (4,3) and (2,2)); if the layout changes the scenario fails visibly at its first check.
- Skill projectiles (`SkillProjectile`) hit reports are logged on the server like weapon hits but have no observer launch event (skill visuals remain U3B2's `SkillVisualRpc`).

## FIX1 - gate fixes after the first local run (2026-11-03)

- `EmberdelveRetroVisualGate`: the "presentation only" source scan matched `Destroy(` inside `private void OnDestroy()`. Forbidden calls are now whole-identifier regexes (`(?<![A-Za-z0-9_])Destroy\s*\(`), the scan proves itself (it matches `Destroy(x)` / `Object.Destroy (x)` and not `OnDestroy()`).
- `EmberdelveBladeDefenseGate`: sword-vs-blade guard now holds by authored data (see U3C.md, FIX1). Display numbers use the invariant culture (the tester's PC prints `0,7000`).
- `NetCombatGate` melee amounts: the FAIL now prints every candidate pattern (patternId, damageMultiplier, pre / after-guard / final, tolerance) and the full factor set. On the server, `ApplySwingHit` now reads the outgoing multiplier, the flat bonus and the target's armor ONCE and passes the same values to the resolver and to the hit report (`ReportHit` optional parameters), so the logged factors are the ones the damage was computed with, never a second provider call after the hit's side effects. If the gate still fails on the next run, the new message shows which factor differs.
- `NetCombatFx.OnHit`: the client report prints `src=Melee` / `loc=Arms` (enum names, like the server's `combat-hit`) instead of the raw bytes.
- combat-abuse: the abuser's own valid AttackPress is a real swing. The gate now expects exactly the swings of B's valid intents (count from the shared constant `CombatNetLimits.AbuseProbeValidAttackPresses`, cross-checked with B's script line and the server's accepted intents), zero swings by A, zero `combat-hit`, A's vitals unchanged.
- combat-abuse `ignored>=1`: the combat path already counts drops (`NetSkillServer.DropIfDisconnecting`). Cause of `ignored=0`: `EndConnection` called `NetworkManager.DisconnectClient` inside the receive handler, which despawns the sender's object while the rest of the same batch is still being dispatched, so the post-decision messages never reached the drop path. The DECISION stays immediate (`Disconnecting` set, log line unchanged); the transport disconnect is now carried out by the next `NetSkillServer.Tick`. The gate check is unchanged (`ignored >= 1`).
- `EmberdelveGameConfig.asset` carries the U3C1 `flow` fields (heights, tolerances, pitch thresholds, endurance, `commitSwingAim`); `BuildConfig` now also saves the asset, so a stale asset gets every `CombatFlowTuning` field written by `BuildAll`.
