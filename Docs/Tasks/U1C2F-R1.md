# U1C2F-R1 — ordinary requested speed bounded to the resolved target (code saved, checks pending manager)

Changed file (only one): Assets/Emberdelve/Runtime/Movement/PlayerMovement.cs — one added statement inside the non-dash branch of Move(dt), immediately after the existing `if (Mathf.Abs(currentHorizontal - targetSpeed) > 0.05f) Lerp ... else _horizontalSpeed = targetSpeed;` block and before `IsMoving`/`SpeedMultiplier`/`DesiredMoveIntent`/`controller.Move`: `_horizontalSpeed = Mathf.Clamp(_horizontalSpeed, 0f, targetSpeed);` plus an explanatory comment. No other line in the file was edited.
Behavior implemented: the requested horizontal speed can never exceed the speed the character is currently legally allowed to produce, `targetSpeed = ResolveGroundSpeed(input.SprintHeld, _crouched)` (already folds class walk/sprint/crouch values, stat passives, guard multiplier, aim `SetSpeedPenalty`, `StatusComponent` slow), and never goes below 0. `DesiredMoveIntent = direction * _horizontalSpeed` therefore has magnitude <= the same `ResolveGroundSpeed` value the review bridge samples as maxResolvedSpeed, which is the 34.663 m/s intent against 5.824 m/s resolved sprint in validation/U1C2A-player-20261019-074221/commands/id13.
Why the overshoot existed (source, not speculation): `currentHorizontal` is read from `controller.velocity`, and CharacterController.velocity includes the contact/depenetration displacement of the previous `Move` (wall, enemy body, chest collider). A contact spike is re-injected as the Lerp seed and `speedChangeRate = 11` decays it slowly, so many consecutive frames requested several times the class speed. The clamp removes that feedback from the request only.
Deliberately NOT done, per brief: no transform write, no `controller.velocity` write, no FPS cap, no collision mask/`CollisionFlags` change, no disabling of enemy/prop collisions, no teleport, no change to review bridge, tests, scenes, prefabs, packages or engine. Physical collision response stays the controller's business and may legitimately exceed the target for a frame; the acceptance comparison is intent vs resolved target, not raw velocity vs target.
Preserved: `ConfigureMoveThreshold()` / `controller.minMoveDistance = 0f` from Awake and ApplyClass; the dash's separate early branch (`IsDashing -> MoveDash`, dash speed cap 24 m/s, `CollisionFlags.Sides` early stop, `DashWasBlocked`) — dash intent is intentionally not bounded by the walk/sprint target; gravity/terminal velocity, grounded check, capsule/crouch transition, controller shape (radius 0.34, height/center, skinWidth/slopeLimit/stepOffset untouched), guard/status penalties, `ViewRelativeDirection`, and all class numbers.
Observable side effect worth noting for the manager: because the upper bound equals the target, releasing a key or releasing Shift now drops the request to 0 / to walk speed on the next frame instead of lerping down over a few frames. This strengthens the already-accepted stop evidence (raw 0 -> intent 0 -> displacement 0) and removes no assertion; the acceleration ramp upward is unchanged because `Mathf.Lerp` saturates its t, so the clamp is inert while speeding up.
