# U2B2-R1 — trusted item definition enforced at the shared creation boundary (code saved; all Unity checks pending manager)

- Changed file (only): `Assets/Emberdelve/Runtime/Items/ItemInstance.cs` — `ItemInstance.TryValidateForCreation`, the single validator shared by `TryCreateNew`, `TryCreateWithUid`, `ItemIdentityIssuer.TryCreateInstance`, `TryCopy` and the JSON `TryRestore`/`TryValidateSnapshot` path. No signature, gate, asset, scene, consumer or `ItemInstanceAuthority` change.
- Exact boundary: after null-authority / null-definition / stable-id checks and **before** any quantity, category, equippability or affix claim is read, the supplied id is resolved with `authority.TryResolveItem(...)` and the resolved object must be reference-identical to the supplied one (`ReferenceEquals(trusted, definition)`); every later read (`TryValidateQuantity(trusted,…)`, `authority.TryCategory(trusted,…)`, `trusted.IsEquippable`) uses that trusted object. A refusal returns false + one reason + null instance and mints nothing (validation still precedes `TryMintUid`, so `ItemIdentityIssuer.MintedCount` is untouched).
- Reproduction 1 (`rogue.itemId="unknown_item"`, maxStack 80): refused by `TryResolveItem` — "unknown item id 'unknown_item': it is not in the trusted item catalog". Reproduction 2 (`rogue.itemId="coins"`, maxStack 999, quantity 999): refused by the identity check — "the supplied 'coins' definition is not the definition the trusted catalog owns for that item id…" — the shadow object is never believed for its own 999 cap; only the trusted coins entry (cap 80) is readable.
- Same-ID clones are no longer accepted silently, even with identical fields; an authority built from the same loaded `ItemData` objects still validates and copies because those are the same references. `TryRestore`/`TryValidateSnapshot` are unaffected (they already resolve the definition from the authority, so the identity check passes trivially); no clamping/trimming/reroll/immutability rule was loosened, and no gate check was altered.
- Deliberate consequence: `TryCopy(authority)` and `TryCreateWithUid(suppliedUid,…)` now also refuse when the supplied authority registers a *different* object under that item id — a cross-catalog definition swap is a refusal, not a silent rebind. This is local catalog consistency, not a client/server security claim.
- Actual checks performed here: read/grep/find/ls plus the edit only — no Unity, compile, import, gate, build or runtime run, so nothing is claimed passing. Verified by inspection that no runtime consumer calls these factories (only `EmberdelveItemInstanceGate` does; the smoke test's `Instantiate(ItemData)` probe is an Inventory/Equipment fixture, never an authority entry).
