Observations for Codex (no failing assertion, no change made by me):

- **O1 — `CombatKitState.TryStartReload(float)` is public and does not sanitize its argument.** Today its only
  call site is `LocalCombatAuthority.Kit.cs:107`, which always passes a finite value ≥ `.1`. If a future caller
  (or a future networked authority) passed `0`/`NaN`, `ReloadRemaining` would become `NaN`, `NaN - dt` stays `NaN`,
  `NaN <= 0f` is false and the reload would never finish. A `Mathf.Max(.1f, …)` or a `Finite` guard at that one
  boundary would close it. Not reachable from current code or saved data.
- **O2 — `ReloadDuration` deliberately preserves absurd finite authoring.** `ReloadDuration(float.MaxValue, .5f)`
  returns `float.MaxValue` (the overflow branch falls back to the authored value, which is itself finite). That is
  what the added test asserts, and it is the documented "preserve finite positive authoring" policy, but it means a
  weapon authored near `float.MaxValue` would produce a reload that never ends. Saved data is 1.9 / 2.2, so this is
  a policy note, not a defect.
- **O3 — `RangedCombat.ReloadProgress` returns 0 when `_reloadDuration <= 0` even if `_reloading` is true.** Not
  reachable through `TryStartReload` (always ≥ `.1`), but it would silently hide a desynchronised push rather than
  expose it. Cosmetic.
- **O4 — `ApplyKitView` early-returns on weapon mismatch and leaves `_reloading`/`_reloadTimer`/`_reloadDuration`
  stale.** This is the pre-existing shape for `ReloadRemaining`; D4b2 adds one more field to the same stale set.
  No behavioural change observed in any gate.
