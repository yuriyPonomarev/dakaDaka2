## 7. The failure — exact assertion, reproduction, likely cause (for Codex; nothing changed by me)

**Assertion:** `EmberdelveDrawSpeedGate.cs:215`
`Check(_shots == shots + 1 && rig.CurrentHealth == hp && rig.Mana.CurrentMana == mana, "release has no repeat launch or refill")`
Raw log lines **4227** and **4261** of `E/gatesA-042124/Emberdelve.EditorTools.EmberdelveDrawSpeedGate.Run.log` — the same
label twice, once per `ClassDraw` (Archer+HollowBow, Warrior+EmberCrossbow). Both stack traces point at
`DrawSpeedHarness/<ClassDraw>d__36:MoveNext () (EmberdelveDrawSpeedGate.cs:215)`. No `error CS`, no exception, no other
mismatch anywhere in the 316 418-byte log.

**The whole flow did run.** I hand-counted every reachable `Check`/`Close`
(`E/drawspeed-assertion-handcount.txt`: fixtures 1 + InputSettings-restore 1 + shared-asset immutability 1 +
ClassDraw 47×2 + FrozenRates 22 + CancellationPaths 65 = **184**) and the gate reported **exactly 184**. An early
`yield break` would have produced a smaller number, so all 184 assertions executed and 182 passed — including the 24
real-transform assertions, the boots/DEX anchors, the frozen slow↔fast captures, the too-early real release, and every
cancellation path.

**Which term fails — not `_shots`, not mana: `rig.CurrentHealth`.** Evidence chain:

1. `_shots` cannot change between line 212 and 215: line 212 already proved `_shots == shots + 1`, `_authority.AcceptedCount`
   +1, `Magazine` −1, `Reserve` unchanged; line 213's `Cleared()` proved `!IsDrawing` and `Charge == 0`; `Release()` queues
   `buttons = 0` and no further press edge is queued.
2. Mana **is** protected: `EmberdelveKitFixtures.SpendMana` routes through the authority (`KitEdit.SpendMana` →
   `CombatKitState.TrySpendMana`, which sets `ManaSinceSpend = 0`), the clone carries `manaRegenDelay = 1000`,
   `ManaComponent.Update` returns early when `_viewBound`, and `TickKits()` derives `dt` from the injected clock
   (`LocalCombatAuthority.Kit.cs:126-131`), which only moves inside `NextClock()`.
3. Health is **not** protected. `HealthComponent` has no authority-view gate: it self-ticks on real `Time.deltaTime`
   (`HealthComponent.cs:106-115`). `PlayerRig.ApplyClass` → `health.Configure(maxHealth, healthRegenPerSecond, regenDelay)`
   (`PlayerRig.cs:540`) and `Configure` **pre-arms** `_timeSinceDamage = delay` (`HealthComponent.cs:47`), while the harness
   then calls `rig.Health.SetHealth(40)` — below the ceiling (Archer 80, Warrior 100) — and `SetHealth` does **not** reset
   `_timeSinceDamage`. So `_timeSinceDamage >= regenDelay` is already true and passive regeneration runs every frame from
   the moment the fixture lowers the pool.
4. Saved class data: Archer `healthRegenPerSecond: 2`, `regenDelay: 7`; Warrior `1.5`, `8`. Between the `hp` capture
   (line 209) and the check (line 215) at least the saturated hold elapses (0.9107 s archer / 0.3600 s warrior) plus 2
   release frames + 3 frames → expected gain **≥ 2.02 HP** (archer) and **≥ 0.69 HP** (warrior) — computed in
   `E/health-regen-hypothesis.txt`. `rig.CurrentHealth == hp` therefore cannot hold, in both classes, deterministically.

**Likely cause / concrete fix direction for Codex (I did not apply it):** the new gate neutralises *mana* regeneration
with a clone-only delay but never neutralises the class's authored *passive health* regeneration, so a legitimate class
behaviour is asserted as a "refill". The fixture-side options are, in the harness's own clone: set `healthRegenPerSecond`
to 0 (or `regenDelay` far beyond the fixture window) on the cloned `CharacterClassData` before `ApplyClass`, **or** keep
regen live and compare `rig.CurrentHealth` against an independently computed `hp + healthRegenPerSecond × elapsed`
instead of demanding equality. The assertion's intent (no repeat launch, no free HP/mana from a release) is preserved by
either route; the current form is a wrong fixture expectation, not a runtime defect in `RangedCombat`.

**Log-reading warning for whoever reviews the raw log:** it contains only **one** `[RangedCombat] projectile` line
(`#1 (hollow_bow) charge 1,00, accepted=True`) even though both classes fired. `CombatDiagnostics.Log("ranged-shot", …)`
is throttled to one message per key per real second (`CombatDiagnostics.cs:16-27`), so the warrior's crossbow shot is
suppressed, not missing — its own line-212 acceptance/spend check passed. Do not read the single log line as evidence
that the crossbow never fired.
