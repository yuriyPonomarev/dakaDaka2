# D1b independent review

Verdict: ACCEPT-WITH-FOLLOWUPS. No authority hole that gives a forged client more damage, speed or chain than the data allows. Static read only: no Unity run; I did not re-execute the 346-check gate or the mutation runs, so those numbers are the worker's claims.

## 1. Authority and security
- Combo forging is closed. `TryBeginMeleeSwing` (LocalCombatAuthority.Swings.cs:174-297) validates step and pattern against the weapon chain, then step k>0 against the authority's own ChainState (:366 ChainAllows: same weapon, same instigator object, k == NextStep, Now <= WindowEnd). Chain state is written only after every refusal check (:272-297), so a refused begin changes nothing. Step 0 always restarts the chain; that gives no gain (base multiplier, base timing). Multipliers, zone, hit slow, impact power and stagger come from weapon/pattern data or sweep geometry, never from the intent.
- Chain across swap/death: removed in ForgetDeadChains (:459), FinishSwing for non-Completed (:788), begin-while-dead (:183); ChainAllows needs the same weapon object. Residual (low): swap A->B->A across frames with no FixedUpdate between keeps the chain (reference equality only, no swap stamp). Fix: stamp a swap counter into ChainState.
- Test flags: `AllowLegacyPatternSelection`, `ImpactZonesEnabled`, `AllowLegacyMeleeAttacks`, `AutoStepSwings` are `internal`, defaults false/true/false/true, and no non-Editor code sets them. EmberdelveInput `MoveOverride/SprintHeldOverride/SecondaryHeldOverride` are public nullable properties, default null, no runtime setter anywhere (same pattern as the existing Primary overrides). Acceptable; make them internal if InternalsVisibleTo covers the test assemblies.
- Swap paths: `SwitchWeapon`/`SwitchToSlot` are locked. `ForceSwitchToSlot` has NO runtime caller (gates only), so it is not reachable from player input. The real bypass is **`ClassLoadout.TryReplaceWeaponSlot` (ClassLoadout.cs ~161-187, `if (slot == _activeSlot) Equip(slot)`)**: the inventory "equip weapon item" path replaces the ACTIVE weapon mid-swing or mid-draw with no IsActionLocked check. The authority then ends the swing as WeaponChanged and drops the chain, and the cooldown floor is per instigator, so there is no damage gain, but it violates the stated rule. Medium-low.
- Guard stays client-held (`_guardHeld`), as the doc admits. Stagger is on the authority clock. OK.

## 2. Gameplay
1. (Medium) Wall stop resets the chain (Swings.cs:685 and :788). In 3 m corridors the first slash often touches a side wall, so steps 2 and 3 are hard to reach (worker saw it windowed). DaD-like rule: a wall hit only cuts the swing short with a recoil (a longer recovery) and does not erase the combo. Suggested: keep ChainState on a wall stop, set WindowEnd = stopTime + WallRecoil + comboWindow; if some punishment is wanted, reset only when the stop came before any hit on a step 0, or when it comes early in the active phase.
2. (Low-Med) MeleeCombat.cs ~131: `_bufferedUntil = -1f; TryBeginSwing();` clears the buffered press before knowing the authority accepts. Client `_readyTime = Time.time + max(cooldown, Total)` equals the authority floor `Total`, so a float ulp in `now - last < Total` refuses and the press is silently lost. Fix: clear the buffer only when TryBeginSwing returns true, or add a few ms to the client ready time. Also a press buffered in the finisher recovery starts a fresh chain up to 0.5 s later even if the player stopped pressing; DaD does not queue that long.
3. (Low) `IsActionLocked` uses `IsSwingInProgress` (record stays until the next FixedUpdate finishes it), so a swap is refused up to about 20 ms after the swing really ended. The begin path got the "step to Now" fix; IsSwingInProgress, GetMoveFactor and the stagger reads did not. The lock also does not cover ranged recovery or reload (not requested).
4. (Low) The held factor is applied after `ResolveWalkSpeed`'s 2..8 clamp, so the documented walk floor becomes 1.88 for the warrior. Fixtures were rewritten to rule x 0.94, so this is pinned rather than noticed. Decide: clamp after, or accept.
5. (Low) Hit slow uses the existing StatusComponent merge (strongest magnitude, refreshed duration): a short hit slow onto a stronger skill slow extends that skill slow (worker lists it). Stacking with Slow/dash/guard/swing/held is multiplicative; realistic worst case sprint + active swing + slow = 0.7 x 0.9 x 0.94 = 0.59. Fine.
6. (Low) Ranged weapons got the default `impactPower 10` (bow and crossbow assets), and `DamageResolver.Resolve` passes `weapon.impactPower`. An arrow therefore breaks a sword-only (resist 8) or rapier (5) guard. Set ranged impactPower to 0.
7. Warrior guard speed 0.45 -> 0.65 is a data change with the gate expectation moved to match; consistent with the user decision, but the number is a tuning guess, not a DaD number.
8. Stamina: no gameplay reader remains (only the pool config in PlayerRig, CharacterClassData fields, StaminaComponent). HUD bar off. OK. `_guardBrokenUntil`, `_chains`, `_lastSwingFloor` are never pruned for removed entities (tiny leak).
9. Impact zones: point-blank hits land at t near 0 (0.7x), which explains the 0.56 factor the smoke saw; check that enemy melee spacing feels fair.

## 3. Test integrity
Changed fixtures: SweptMelee (two flags on for the whole gate, move-hook check replaced, step-1 "does not exist" now "no running chain", real-rig second swing is chain step 1, forced swap through ForceSwitchToSlot); smoke combat damage check; AttributeAction (every warrior speed x WarriorHeld computed from data, guard 0.45 -> 0.65); Vitals and NumericAffix (x(1-18/300)); CloakSlot rows 6+3+2+3 -> 6+2+2+3; realcombat matrices wait for the window when the next press would be step 3.
- Weakened: (a) the smoke check "melee damage is weapon base x passive x location x zone" now reads location and zone from the authority's own swing record, so it can no longer catch a wrong zone or location number (the run had failed at 19.6 vs 34.9; the 0.56 explanation is plausible but not independently shown). The follow-up `> base*loc*zone + 1` is relative to the same record. Zones are pinned by the new gate, so coverage moved rather than vanished, but this assertion is now close to tautological. (b) SweptMelee runs entirely with zones off and legacy pattern picks on, so the sweep gate no longer exercises the production configuration end to end (CombatFlow and realcombat do). (c) Speed expectations are `rule x held` with held computed from the same asset values: they prove the factor is applied once, not that 0.94 is right; the CombatFlow gate has the literal numbers.
- Not weakened: stamina data assertions kept, AttributeAction `ResolveWalkSpeed` assertions untouched, CloakSlot is a legitimate row removal, the matrix wait skips only the overhead press the matrix could not pin (RealComboChain covers step 3 with exact damage).
- The 346-check gate is substantive by inventory: forged-step matrix with state-unchanged checks, window edges on an injected clock, exact armour 0/50/100, contact t at six positions, guard equal-power boundary, real-time hit slow ratio 0.900. The mutation claims (22/16/22/21/3/11 failures) are plausible: each mutation hits a rule with many dependent checks, and the stamina mutation failing only 3 matches its narrow section. Not re-run by me.

## 4. Overclaims in D1b.md
- "ForceSwitchToSlot is the forced path (class apply/respawn/tools)": no runtime caller; class apply uses Equip(0) directly. The real unlocked path, TryReplaceWeaponSlot, is not mentioned.
- Chain "forgotten on swap": true except the A->B->A same-gap case.
- "Nothing is skipped or loosened" for the matrix and the smoke damage rewrite: the damage assertion was loosened to the record's own multipliers (3a).
- "All 39 lines PASS" and the mutation counts are log claims I did not re-run.
- Windowed evidence honestly lists what was not reached (step 3, a visible hit, guard break).

## Findings ranked
Nothing blocks the commit. Recommended in the same commit (small): A) lock TryReplaceWeaponSlot on the active slot (or document the exemption); B) do not clear the press buffer before the authority accepts (2); C) ranged impactPower = 0 (6).
Later: wall-stop chain rule (1, tune before playtest), stale IsSwingInProgress tick (3), A->B->A chain stamp, held factor vs walk clamp (4), tighten the smoke damage assertion with literal location/zone expectations, prune per-entity dictionaries, make the EmberdelveInput overrides internal.
