### 4.3 Likely cause (reported, not fixed)

The refusal happens **before the authority is ever reached**:

- the log contains **8** `[CombatAuthority] Rejected …` lines in total and **none of them is for
  `warrior_dash`** — so `authority.TryBeginSkillCast` was not called and did not refuse;
- therefore `SkillCaster.CanCastSlot` returned false. Its branches in order: slot ✓, skill ✓,
  rig ✓, `rig.IsDead` false, `_cooldownRemaining[0] == 0` (proved by line 291), `mana != null` ✓,
  `mana.HasAmount(24)` ✓ (75 − 24 = 51 ≥ 24 even if `ApplyClass` did not refill; the harness also sets
  `manaRegenDelay = 10000`), `behavior != null` ✓, `authority != null` ✓, Dash has no weapon
  requirement ⇒ the only remaining branch is `DashBehavior.CanCast`
  (`Assets/Emberdelve/Runtime/Skills/Behaviors/DashBehavior.cs:26-28`):

  ```csharp
  if (context.Rig.Movement.IsDashing) { reason = "already dashing"; return false; }
  ```

  with `PlayerMovement.IsDashing => _dashTimeRemaining > 0f`
  (`Assets/Emberdelve/Runtime/Movement/PlayerMovement.cs:74`) and
  `CanDash => controller != null && _class != null` (line 281, true — so the earlier
  "no movement component" branch is ruled out).

**Classification: harness/fixture sequencing, not an authority cooldown defect.** The game rule
"you cannot start a second dash while the first is still running" is existing intended behaviour and
is *not* what this case is meant to test. The fixture re-casts a Dash on the same instant, while the
first Dash's movement is still physically in progress. `SkillCaster.Reject()` only raises
`SkillRejected`/`Toast` events (no log), which is why the reason is invisible in the raw log — worth
considering for diagnosability. Suggested directions for Codex (not applied by me): yield frames until
`rig.Movement.IsDashing` is false, or `rig.Movement.CancelDash()` before the epoch re-cast, or run the
epoch case with a non-movement skill (e.g. `warrior_battle_cry`) so the movement rule cannot interfere.
I did **not** weaken, skip or reorder any check.
