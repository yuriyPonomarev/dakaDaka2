Reviewer: independent, clean context, read-only (no edits apart from this file, no git writes, no Unity runs).
Reviewed: `git diff HEAD` (Inventory.cs, Equipment.cs, ItemInstance.cs, ItemSnapshot.cs) plus the untracked StrictJson.cs, ContainerSnapshot.cs, ContainerSnapshotValidator.cs, ItemUidRegistry.cs, LoadoutSnapshot.cs and Editor/EmberdelveContainerSnapshotGate.cs. ## Verdict: ACCEPT-WITH-FOLLOWUPS (commit only after M1 and M2)

The structure is sound:
- validation is split from commit (validate, then a commit step that is meant not to fail);
- item rules are reused from `ItemInstance`, not copied;
- the JSON reader is strict and its depth is bounded;
- the checksum is described honestly as tamper evidence, not security;
- the gate is real. I checked the logs: `Logs/r9final_ContainerSnapshot.log` reports `PASS checks=762 failures=0` and was written after the last source edit (source 11:36:08, log 11:36:43). `Logs/r9_mut.log` really fails 21 checks, all of them checksum or ledger checks. All 34 regression lines in `r9final_exit.txt` show PASS, exit 0 and no `error CS`. No existing gate or fixture was changed (diff confirmed).

One real validation hole must be closed before commit (M1), and three statements in the docs are wrong (M2).

## Must fix before commit

### M1. Integer overflow lets an entry sit outside the grid and skip the overlap check (High)
`ContainerSnapshotValidator.cs:266` checks `entry.x + size.x > snapshot.width` (and the same for y) in unchecked int arithmetic. The loops at `:272-274` use `xx < entry.x + size.x`. The project has no `-checked` flag and no .rsp/asmdef override.

Malicious input:
- Take any bag entry and set `"x":2147483647` (or `"y":2147483647`). `TryInt` accepts it because it is within int range.
- For a 1x1 relic, `2147483647 + 1` wraps to `int.MinValue`, which is not `> 10`, so the bounds check passes.
- The occupancy loop runs zero times, so no cell is marked and no overlap is found.
- The entry is accepted with `Origin = (2147483647, y)`.

What follows:
- `Inventory.Recompute` (`Inventory.cs:1447-1451`) also loops zero times, so the stack takes no cells. `UsedCells` and `FreeCells` ignore it, but `TotalUnits` and `CarriedValue` count it.
- The UI places it off-grid. `ToContainerSnapshot` writes it back out forever.
- Gear entries with different uids can all share `x = int.MaxValue` (the canonical order then compares by uid). One 10x4 bag can therefore carry up to 512 items, and up to 4 more for each extra footprint width (`x = int.MaxValue - k`).

Gate status: the gate tests `x == width`, `-1`, `y == height` and the corner overhang, but not the overflow.

Fix: `entry.x > snapshot.width - size.x || entry.y > snapshot.height - size.y`. Width is at most 64 and size at least 1, so this cannot overflow. Add gate cases for `x = int.MaxValue`, `y = int.MaxValue` and `x = int.MaxValue - 1` with a 2-wide item.

Side note: the same pattern exists in `Inventory.cs:865` (`origin.x + width > gridWidth`). That code predates R9 and its origins come from UI and moves, but the same fix applies.

### M2. Three claims in the docs are wrong (fix the text, or the code)
1. **"an accepted file has exactly one byte form"** (`Docs/Tasks/R9.md:22`, and `ContainerSnapshotValidator.cs:292` "one container, one byte representation"). This is false at the byte level. The checksum is computed over the *re-serialized model* (`ContainerSnapshot.ComputeChecksum` -> `BuildBody`), not over the stored bytes. All of these parse to the same model and pass the same checksum:
   - insignificant whitespace;
   - `bag` escapes;
   - JSON members in any order (`TryExpectObject` builds a dictionary);
   - `0.090`, `9e-2` or `0.0900000001` for `0.09`;
   - `-0` for an int.

   The gate itself asserts that whitespace and `\u` escapes are accepted (`Gate:776-781`). What is unique is the *entry order*, i.e. a canonical model. Either reword the docs, or make it true by refusing a document whose `ToJson()` is not ordinal-equal to the input. That check is cheap and also covers N4 below.
2. **"Adding v2 means adding `case 1:` ... older files then keep loading"** (`R9.md:28`, `ContainerSchema` doc at `ContainerSnapshot.cs:427-433`). This does not work with the checksum as designed:
   - `TryReadVersionAndUpgrade` rewrites the tree *before* the checksum is verified. The checksum is then recomputed from the v2-shaped model, so it no longer equals the stored v1 checksum, and every migrated v1 file is refused with "checksum does not match".
   - For a loadout, the outer checksum covers the inner container JSON, so that breaks as well.
   - A migration must verify the checksum against the v1 canonical form first, then rewrite `schemaVersion` and re-seal.

   State this in the docs now, so that v2 is not designed around a hook that cannot work.
3. **"a float is written as the shortest text"** (`R9.md:37`, `StrictJson.cs:31, 412`). `"R"` is the shortest form only on runtimes with .NET Core 3.0+ semantics. On .NET Framework-style runtimes it is G7, falling back to G9. The round trip is bit-exact either way, and the gate proves that for 4017 values through real text on this runtime. But the *spelling* can differ between runtimes (see L1). Say "round-trip text (runtime-dependent spelling)".

## Should fix soon (same task or the next one)

### S1. The loadout commit raises events between the two halves (Medium)
`LoadoutSnapshot.cs:185-186` calls `equipment.CommitRestore(...)` and then `bag.CommitRestore(...)`. `Equipment.CommitRestore` does the following before the bag is committed:
- it runs `RefreshStats()` (`Equipment.cs:556`), which goes into `PlayerRig.RefreshEquipmentStats`, pool `SetMax` and their events;
- it raises `GameEvents.RaiseInventoryChanged/RaiseEquipmentChanged` (`Equipment.cs:558-561`).

`GameEvents` invokes the delegates directly (`GameEvents.cs:41-42`) with no try/catch.

Two problems follow:
- (a) Subscribers (`InventoryScreenController.cs:191-192`, `HudController.cs:126`) see a state that is half restored. Concrete case: the live bag holds boots X and the snapshot wears X. Between the two commits, X is both worn and carried, which breaks the very "one uid is one item" rule the restore enforces.
- (b) If any subscriber throws, the equipment is replaced and the bag is not. That is exactly the partial application the task forbids, and it contradicts the claim that the commit "cannot fail".

Fix: split each commit into an apply step with no events and a notify step, and notify only after both containers are applied.

Minor in the same place: no `EquipmentChanged(item, false)` is raised for items the restore removed. The equip/unequip paths do raise it.

### S2. Restores never write the ledger, and a full-profile ledger refuses legal loadouts (Medium, design)
- `Inventory/Equipment/LoadoutSnapshot.TryRestore(..., others, ...)` only *reads* `ItemUidRegistry.CanHold`. Nothing calls `TryReplaceOwner` after a commit, so the ledger and the live containers drift apart, and the caller has to register in a separate step.
- `ItemUidRegistry`'s doc says U4C keeps *one registry per profile* holding bag, equipment and stash. If that ledger is passed to `LoadoutSnapshot.TryRestore`, any loadout in which a uid moved between bag and equipment since the ledger was filled is refused. Example: X is registered to `"bag"`, and the snapshot wears X, so `CanHold("equipment",[X])` fails with "already held by container 'bag'". The gate only uses an empty or stash-only ledger (`Gate:858-862, 926`), so this never shows.
- Needed: a loadout-level operation that treats both owners as being replaced. That means validating against the ledger minus `{bag, equipment}`, then calling `TryReplaceOwner` atomically for both. Alternatively, document that `others` must exclude every container being restored.

### S3. Test gaps worth closing
- No check runs on the real production grid or the real starting kit. The gate wipes the rig (`Gate:298-300`) and reconfigures it to 10x6, so the state `ClassLoadout.Apply` actually produces (config grid, issuer-minted Common kit) is never captured and restored. Add a capture -> JSON -> wipe -> restore -> byte-equality check *before* `Clear()`. Using 10x6 for the rich fixture is acceptable, because the code is grid-agnostic.
- About 35 `RefuseJson` cases each count a "touched nothing" check. Parsing cannot touch the target, so those checks are vacuous and pad the count (762 overstates the number of independent assertions by about 35). The parse-refusal assertions themselves are meaningful.
- The gate has no M1 overflow case, no BOM case (a BOM is refused as "unexpected character", which is fine but untested) and no `-0` int case.

## Later (U4C / U3 / design notes)

### L1. The checksum depends on how the runtime spells floats
Verification re-serializes and re-hashes. A server on CoreCLR (.NET 8 dedicated server) and a Unity Mono or IL2CPP writer can spell some floats differently: shortest form versus the G7/G9 fallback. Values with an 8-9 digit shortest form are at risk. The affix tolerance (L5) admits off-grid bit patterns near each step, and those can have long spellings. A file written by one runtime family would then fail its checksum on the other. The 4017-value gate proves round-trip stability on *one* runtime only. U4C options: hash the stored canonical bytes, or enforce M2.1 and treat a different spelling as a refusal rather than a mismatch.

### L2. Restore requires the snapshot grid to equal the live grid
This was a deliberate choice (`Inventory.cs:785`). If the class config ever changes the bag size, every saved bag is refused and the profile cannot be loaded. U4C/v2 needs a policy: migrate, relocate, or keep the grid in the profile.

### L3. The entry cap does not fit a large stash
`MaxEntries = 512` but `MaxGridDimension = 64`. A legal 64x64 stash can hold up to 4096 1x1 stacks, which cannot be represented. Size the cap for the stash in U4C.

### L4. The ledger is per process and per profile only, with no thread safety
- No cross-profile uid index exists. Copying one profile's items into another profile file (with a recomputed checksum) is not detected.
- There is no record of issued uids, so a fabricated Rare item with valid rolls and a fresh uid is accepted wherever the file is writable.

Both are acceptable *only* because the store is server-owned, and the docs say so honestly. U3/U4 need a global uid ownership index, locking, and issuance tracking.

### L5. Float exactness
- Exact original values are never refused. Rolls are validated on the same bits, and the JSON round trip is bit-exact (proven).
- Tampered near-values are accepted. `AffixBandRules.TryGridIndex` allows a residual of about 1e-6 relative. For move_speed 0.09 (band 0.03-0.12, step 0.01) that is about 1.8e-7 absolute, roughly ±24 float ULPs. A value like `0.0900001` is therefore accepted and stored verbatim.
- This tolerance predates R9 and is gameplay-irrelevant, but it means the bits of a "valid roll" are not unique, and it feeds L1.

### L6. Other notes
- **Run state:** run statistics (`LifetimeCollected`, `RecoveredValue`) are not restored, and restore ignores whether the rig is alive. Both are documented as deliberate. U4C/U3 callers must enforce "only in the lobby or at raid start".
- **`kind: "stash"`:** it validates like a bag but nothing consumes it, and `Inventory` refuses it.
- **`ItemSnapshot.ToJson/TryFromJson` (JsonUtility):** grep shows no production persistence use; only the single-item DTO remains. However, `ContainerSnapshot` and `LoadoutSnapshot` are `[Serializable]` with public fields, so `JsonUtility.ToJson(containerSnapshot)` would compile and silently bypass the strict format. Consider dropping `[Serializable]`, or say so in the doc.
- **Weak "validated" type:** `ValidatedContainer` and `ValidatedEntry` are public, with public constructors and mutable fields, and there is no asmdef split. `internal CommitRestore` therefore accepts a hand-built "validated" container from any runtime code. Make the constructors internal and the fields readonly.
- **"Validation touches nothing" is not quite true:** `Inventory.TryPrepareRestore` calls `EnsureGrid()` (`Inventory.cs:770`), which can resize `_cells` and clamp the grid, and `EquipmentPartner()` caches `_equipment`. Both are benign, but the docs say validation touches nothing.
- **Shared version number:** the loadout and container schema versions share one constant, so a container-only change forces a loadout version bump.
- **Slot names are persisted as text:** they come from `EquipmentSlot.ToString()`, so renaming an enum member breaks saves. Assets store the int and saves store the name, so both must stay frozen.
- **DoS:** `StrictJson` builds the whole tree before any per-array cap applies. A 2 MiB `[0,0,0,...]` document allocates about 1M nodes before it is refused. Recursion depth is safely bounded at 12. This is irrelevant while the store is server-written, and matters if clients ever upload.

### What U4C must add (minimum)
1. An atomic file replace (temp file, flush, rename), a backup of the previous version, crash recovery, and per-profile safe fixed file names (UNITY_DESIGN "Raid results and persistence").
2. Validate before writing: parse and `TryValidate` the exact text about to be written. Capture does not self-validate, so an unrestorable capture would otherwise be saved silently.
3. One ledger per profile, plus a loadout and stash commit that updates it atomically (S2), plus locking.
4. A stash container class consuming kind `stash`, with an entry cap sized for its grid (L3).
5. A grid-change policy (L2) and a working migration design (M2.2) before any v2.
6. A decision on checksum versus raw bytes across runtimes (L1). Read with an encoding that strips the BOM.
7. Server authentication and account binding (signing). The checksum is not that.
8. Extraction and death integration: what is banked, exactly once, and alive/range/time validation, which stays with the caller.

## Checklist answers (short)
1. **Atomicity.**
   - For every refusal path, validation completes before any mutation, and the gate asserts the full `State()` (cells, float bits, counters, stats, pools, hands) is unchanged after each refusal. That comparison is as strong as a canonical-serialization comparison.
   - The catalog, authority and issuer are not mutated during validation (apart from the authority's lazy cache, which predates R9).
   - `RefreshStats` runs once per restore and replaces the stat source wholesale, so six repeated restores do not accumulate or heal (tested).
   - Gap: the commit is not event-free in the loadout path (S1).
2. **Validation completeness.**
   - Everything in ITEM_AFFIXES.md is covered through `ItemInstance` and the container rules, and tested.
   - Hole: out-of-grid placement through int overflow (M1).
   - Near-value tolerance predates R9 (L5).
   - The JSON edge cases listed in the task are covered: NaN/Infinity literals, overflow, huge ints, fractional or exponent ints, duplicate/unknown/missing keys, depth, size, control characters and bad escapes. A BOM is refused but untested, and a `-0` int is accepted (harmless).
3. **StrictJson.**
   - Correct and RFC-strict, with depth bounded at 12.
   - Every format/parse call uses the invariant culture. Thread culture is proven to be in effect for ru-RU and de-DE.
   - The float test really goes through text (`AppendFloat` -> string -> `TryParse` -> `TryFloat`), and the full loadout bytes round-trip under three cultures.
   - Risks: spelling across runtimes (L1) and allocation before caps apply (L6).
4. **Checksum.**
   - It covers schemaVersion, kind, containerId, width, height and entries (everything except the checksum field). The loadout checksum covers both containers including their own checksums.
   - An empty container is hashed normally.
   - It can be recomputed by design, and the docs say so honestly.
   - Comparison timing is irrelevant.
   - Problems: incompatible with the migration hook (M2.2), and spelling-dependent (L1).
5. **Tests.**
   - Meaningful, and the mutation proof is genuine (log checked).
   - Gaps: no production grid or starting kit check (S3), the vacuous JSON "touched nothing" checks, and no overflow case.
6. **Design for what follows.** See L1-L6 and the U4C list.
7. **Compile and API.**
   - It compiles: 0 `error CS` across all 34 logs, and the Editor gate reaches the internals through the existing `InternalsVisibleTo("Assembly-CSharp-Editor")`.
   - `TryValidateQuantity` was changed from private to internal with no logic change.
   - `Equipment.BagPartner` is new and internal.
   - No dead code of note.
   - Overclaims: see M2 and S1.
