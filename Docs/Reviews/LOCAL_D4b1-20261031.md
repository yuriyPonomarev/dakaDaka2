## 6. Source-review findings (read-only)

Confirmed behaviour:

1. `ActionSpeedRules.Resolve` is called **exactly once** at authority swing begin
   (`LocalCombatAuthority.Swings.cs:260-262`) from the authored pattern/`ComboTiming` values; the result is frozen into
   `SwingRecord.Timing/RepeatInterval/ActionSpeedFactor/ContactWindow` and re-published through
   `MeleeSwingStatus.RepeatInterval/ActionSpeedFactor`. `SanitizeFactor` maps NaN/±Infinity/≤0 to 1; a finite positive
   factor whose duration arithmetic is nonfinite falls back to a single neutral recomputation.
2. `repeat = max(max(.1f, cooldown/factor) * cooldownGrace, windup+active+recovery)` — the existing `.1s` cooldown floor
   and the existing `.8` authority grace are preserved, and the total-dominant branch is what makes the sword's `.84`
   and the 2 s-cooldown case `1.6`. `Active` keeps the `.02s` authority floor; it is the only remaining active floor.
3. No double scaling: `MeleeCombat` consumes `accepted.Timing` and `accepted.RepeatInterval` only; the old
   `authority-failure → _weapon.ComboTiming(...)` fallback is replaced by a hard refusal plus
   `Debug.LogError("[MeleeCombat] Accepted swing has no authority timing/status: …")`. Client-only `.02` windup/active/
   recovery and `.05` wall-recoil extensions were removed; `WeaponVisualRig` recoil duration floor is now `1e-5f`
   (division epsilon only).
4. Neutral cadence change is real and matches the documented policy: local input floor
   `max(.1, weapon.cooldown, timing.Total)` → `Time.time + max(0, accepted.RepeatInterval - accepted.Elapsed)`.
   Sword `.92 → .84` (−8.7 %); cooldown-dominant `2 → 1.6` (−20 %). Authority/enemy policy untouched.
5. The frozen prior interval is shared by melee begin, legacy `SubmitAttack`, the projectile rate check and
   `WeaponCooldownRemaining` through one `FrozenRepeatInterval(combatId, lastAttack, fallback)` helper keyed on the
   last accepted attack stamp, so a different accepted attack retires it. Verified in source and by the gate's
   melee→fast-ranged case (`.75` remaining for a `.1s` crossbow, then its own `.08`).
6. Sampling/contact: `SampleCount` keeps its legacy 3-arg overload (authored `pattern.activeTime`) and adds a duration
   overload using accepted active seconds; accumulation is `double` and returns `MaxSamples` **before** `int`
   conversion (`MinSamples=8`, `MaxSamples=400`). Contact window is frozen as
   `acceptedActive * clamp01(authoredContactWindow / authoredActive)` and consumed with `acceptedActive / K`,
   `windowSamples` now clamped to `[0, SampleCount]`.
7. No action factor enters any intent or network path: `IActionSpeedSource` is implemented only by `PlayerRig` and the
   gate's private `RatedActor`; a project-wide grep found no `ActionSpeed`/`IActionSpeedSource` reference under
   `Assets/Emberdelve/Runtime/Net`. Six attribute names, class scores, both mana pools, immutable profile captures and
   exact item identities are unchanged; the gate asserts no shared weapon/class/profile/item mutation and no
   HP/mana/ammo refill, and those checks passed.

Observations worth Codex attention (none is a current test failure):

- **A. `WeaponCooldownRemaining` can now exceed the held weapon's own cooldown.** After a melee→fast-ranged switch the
  gate asserts `.75s` remaining for a weapon whose `cooldown` is `.1s`. Any HUD-style assertion of the form
  `CooldownRemaining <= weapon.cooldown` is only safe while the accepted interval ≤ that weapon's own cooldown.
- **B. Low-DEX melee HUD readout exceeds the authored weapon cooldown.** `EmberdelveSweptMeleeGate.cs:1660` asserts
  `melee.CooldownRemaining <= _sword.cooldown + 1e-3f`. It passes because that fixture runs at factor 1.0
  (`.84 ≤ .92`). At the authored low end the accepted interval is larger than the weapon's cooldown: DEX 1 → factor
  `.82` → sword accepted repeat `max(max(.1,.92/.82)*.8, (.24+.30+.30)/.82) = max(.8976, 1.0244) = 1.0244 s > .92 s`.
  No executed assertion currently covers a real sub-1.0 action rate on a live rig. Recommend Codex either state this
  as intended or add a fixture; I did not change any tolerance.
- **C. Client ready-time mixes two clocks.** `_readyTime = Time.time + max(0, accepted.RepeatInterval - accepted.Elapsed)`
  subtracts an authority-clock quantity from `Time.time`. It is exact while the authority clock is `Time.time`
  (the default `Now`), and gates inject `SetClock(...)`, where `accepted.Elapsed ≈ 0` at read time so the offset is
  unexercised. This becomes load-bearing for U3B when the authority clock is a server tick.
- **D. `ContactWindow` divides by `authoredTiming.Active` with no epsilon guard.** If an authored pattern ever had
  `activeTime == 0` the ratio is `+Infinity`, `Clamp01` yields 1 and the window silently becomes the whole active
  phase. The previous code guarded `sampleDt` with `1e-5f`. Safe outcome today, undocumented.
- **E. `EmberdelveAssetLibrary.BuildDataOnly()` now calls `EditorUtility.SetDirty(profile)` unconditionally** on the
  shared `AttributeCurve_Default` asset, and every interactive gate invokes `BuildDataOnly()`. In my runs the committed
  content of that asset did not change beyond the intended 13-line action table, but any gate run can leave the shared
  profile dirty so a later save persists builder-side re-serialization. See §7 for the drift already visible in the
  working tree.
