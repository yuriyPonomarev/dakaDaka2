# Review R4+R5: seeded loot pipeline, per-raid seed, project RNG

Independent reviewer with a clean context. Read only: no edits except this file, no git writes, no Unity runs.
Scope: `git diff HEAD` (HEAD c112e97d) plus the untracked `Runtime/Core/DeterministicRng.cs`, `Runtime/Items/RaidSession.cs`, `Editor/EmberdelveLootPipelineGate.cs` and `Data/Loot_Enemy_*.asset`. Checked against Docs/Tasks/R4R5.md, CODEBASE_HEALTH F5/F7/R4/R5, R3 H2, ITEM_AFFIXES and AGENTS.md.

## Verdict: ACCEPT-WITH-FOLLOWUPS

The core is correct.
- The RNG is a correct SplitMix64. The integer paths are unbiased and the float path is exact.
- The seed derivation is sound and domain-separated.
- The raid owns one issuer, and the chest, enemy drop, bag and pickup paths all use it.
- Gear dropped by enemies keeps the same instance from the ground to the bag to equipment.

I recomputed every known-answer vector in the gate with my own Python implementation, written from the algorithm itself. All of them match. The SplitMix64 vectors for seeds 0 and 1234567 also match the published reference values.

The final-tree logs agree with the worker's claims: `Logs/r4r5_final_exit.txt` shows 37 lines, all exit 0 and `failures=0`. LootPipeline passed 3941/3941 with an entropy seed (0xFD0AF9951A0BA3DA) and 3941/3941 with `EMBERDELVE_RAID_SEED=777` (0x309).

Nothing here is a correctness blocker. Fix the must-fix items below before committing. They are documentation accuracy, one overclaiming comment in the gate, and commit hygiene. The Warden re-baseline is an undocumented balance change and needs an explicit decision.

## Must fix before commit

### M1. The Warden drop re-baseline is described wrongly, and it is a real balance change
- `Editor/EmberdelveAssetLibrary.cs:1376-1383` (doc comment) and `Docs/Tasks/R4R5.md` ("Legacy rule ... re-baselined to 'equal weights, up to 2 copies'", "Warden 90%") both say the table uses equal item weights and that each item can drop up to twice. That is true for the Servitor only.
- The Warden table is actually Relic w9 with maxCopies 1, Coin w8/2, Draught w6/2 and Boots w4/1 (Uncommon), with `nothingWeight` 3 and 3 rolls.
- The miss weight is fixed, but the item weights shrink as copy caps are reached (`LootTable.cs:528-556`). So 90% is the drop chance on the first roll only. After a Relic or Boots drop it is 18/21, about 86%.
- Expected drops per kill, computed exactly by enumerating every outcome:

  | Item | Old rule (3 rolls, 0.9 each, uniform, with replacement) | New table |
  |---|---|---|
  | Relic | 0.90 | 0.68 (-24%; at most 1 instead of up to 3) |
  | Draught | 0.90 | 0.68 |
  | Coin | 0.90 | 0.90 |
  | Footpad Boots (Uncommon) | 0 | 0.39 |
  | Total items | 2.70 | 2.65 |

- The Servitor is exactly equivalent to the old rule: 24/(24+6) = 0.8, uniform over three items, and the cap of 2 copies never binds with 2 rolls. Expected drops are 1.6 total, 0.533 per item, under both rules.
- Why it matters: the Relic is the sealed-chest unlock currency (`SealedUnlockValue`). Value earned from Wardens drops, and a new gear drop is added. AGENTS.md requires the report to describe actual behaviour.
- Fix:
  - Correct both texts to the real weights and caps and state the expected-value change.
  - Either confirm the change as a design decision, or make the Warden table equal weight with maxCopies ≥ rolls to keep parity, and add Boots as a separate decision.
  - Also say in the `nothingWeight` tooltip (`LootTable.cs:240-243`) that the miss chance is relative to the weight still available, so it is not a constant per-roll chance once caps bind.

### M2. Stale determinism comments in LootTable now say the opposite of the truth

- `LootTable.cs:353` still says "the shape loop, consuming exactly what the legacy loop consumed".

### M3. The gate states a check that does not exist

- Fix: add the check (end the run, try the pickup, assert the instance is kept) or delete the comment. AGENTS.md: do not claim unexecuted checks.

## Should fix now (cheap) or soon

### S1. The enemy drop key depends on the machine's culture
- `AI/EnemyAgent.cs:97` builds the key with `$"{data.enemyId}@{RoundToInt(x*4)},{RoundToInt(z*4)}"`. Int formatting through string interpolation uses the current culture's `NegativeSign`. Some cultures, for example sv-SE under ICU, use U+2212 instead of '-'.
- Failure scenario: an enemy at negative x or z. A client and a server, or two developers, with different locales get different drop keys, so different drop seeds for the same raid seed. That breaks "(raid seed, key) fixes the drop".
- Latent today: the layout origin is (0,0,0), so every position is positive. The gate's own known answer uses "hollow_servitor@10,-8".
- Fix: `string.Format(CultureInfo.InvariantCulture, ...)` or `FormattableString.Invariant`. The chest id (`ChestSpawner`, `Chest_{variant}_{x}_{y}_{i}`) only formats non-negative values, so it is safe, but make it invariant as well.

### S2. Enemy drop key collisions and predictability (the worker already lists this)
- Two enemies with the same `enemyId` whose spawn points round to the same quarter-metre cell get identical drop contents in a raid. UIDs still differ, so this is not identity duplication. It is the same items twice.
- An enemy that dies before its `Start` runs keeps the default key "enemy" (`EnemyAgent.cs:50`), which every such enemy shares.
- A future respawn or wave system at fixed points would re-drop identical contents in every raid.
- Today's layout has 6 distinct cells, so nothing collides now.
- Fix with explicit spawn ids in the layout, as planned. For respawns, add a per-spawn kill counter to the key.

### S3. The raid seed is logged in every build
- `RunDirector.cs:64` calls `Debug.Log($"[Emberdelve][Raid] {Session}")` unconditionally, so release Player.log files contain the seed.
- Offline this does not matter, because the client holds the seed anyway. It contradicts the R4R5.md note that a server must keep the seed secret.
- Fix: guard it with `UNITY_EDITOR || DEVELOPMENT_BUILD`, or log a hash or prefix only.

### S4. Seeded UIDs are not version-4 UUIDs, despite the comment
- `ItemInstance.cs:312` sets the version nibble on `bytes[6]`. `new Guid(byte[])` reads bytes 6-7 as little-endian Data3, so the version is the high nibble of `bytes[7]`.
- Evidence: the gate's own known answer `7e2cbb32-9625-f843-931b-...` shows 'f' where a v4 UUID has '4'. The variant bits on `bytes[8]` are placed correctly.
- Cosmetic only: `ItemIdentityRules` checks length, not version, and the seeded mode is only for tests and replay. Fix the byte index (7) or the comment at `:256`. Changing the byte invalidates the gate's UID known answer.

### S5. One-issuer invariant: public ways around the issuer remain (R3 H2 is only partly closed)
- `ItemInstance.TryCreateNew` (`ItemInstance.cs:456`) mints through `ItemIdentityRules.TryMintUid` with no issuer and no ledger. Today it has no runtime caller, only editor gates, but it is public.
- The gate's source scan checks `CreateLocalTrusted(` but not `TryCreateNew(` or `ItemIdentityRules.TryMintUid(` under Runtime.
- The bag is still a minting entry point (legacy gear `TryAdd`, `Inventory.cs:684` falls back lazily to a private issuer). It now mints from the raid issuer in a run, which closes the "issuer per bag" half of H2. "Move minting out of the bag" (H2/R4) is still open and is not claimed.
- `RunDirector.UseSessionForTest` (`:405`) is `internal`, so any Assembly-CSharp code can swap the raid session mid-run. That splits the ledger.
- Fix:
  - Extend the scan to `TryCreateNew(` and `ItemIdentityRules.TryMintUid(` in Runtime, allowlisting `ItemInstance.cs` only.
  - Later, make `TryCreateNew` internal or editor-only and guard `UseSessionForTest` with `UNITY_EDITOR || DEVELOPMENT_BUILD`.

### S6. The source scan is a plain-text heuristic
- Things it misses: `new Unity.Mathematics.Random(...)` (its `\bnew\s+Random` needs the bare name), `System.Security.Cryptography.RandomNumberGenerator`, `Environment.TickCount`, and `DateTime.Now` used as a seed or outcome.
- It strips only whole-line `//` comments, so block comments and trailing comments can give false positives (the safe direction).
- The allowlist is per file, so new random calls added to `EnemyBrain.cs` or `TorchFlicker.cs` would pass unseen.
- It is enough as a tripwire, not as proof. Add the patterns above and count matches per allowlisted file, for example exactly one in `EnemyBrain.cs`.

### S7. The EnemyBrain allowlist entry is mislabelled
- `EnemyBrain.cs:87` uses `Random.value` to jitter the patrol waypoint angles. The gate and R4R5.md call it "strafe jitter".
- It changes where enemies walk, and so indirectly who meets whom. It is not loot or identity, and when AI becomes server-simulated it runs only on the server.
- Acceptable as a follow-up. Correct the label, then seed it from `(raidSeed, spawnKey)` when AI becomes authoritative.

### S8. Smaller items
- **Misleading coverage message.** `RunDirector.cs:115` now adds `LootTable.Validate()` problems (chest and drop tables) to a list that is logged as "Items not in the item catalog" (`:163`). The extra validation is good, but the message is wrong. Give it its own message.
- **Two catalog sources.** Enemy drops use `config.itemCatalog` (`RunDirector.cs:422`) and chests use `_host.Inventory.Catalog`. These differ when a test swaps the bag catalog. Pick one, matching R3 M3 "pass the run catalog explicitly".
- **Interfaces not merged.** R4 in the health doc asked to merge the loot-host interfaces. This change adds two more (`IEnemyDropHost`, `IRaidSessionHost`). This is a deviation from the spec, and R4R5.md lists it as a follow-up.
- **Small allocations per roll.** Each roll allocates `Encoding.UTF8.GetBytes` per `HashString` (`H("chest")`/`H("enemy-drop")`/`H("uid")` are recomputed on every call; make them `static readonly`), about 5 `DeterministicRng` objects, `new byte[16]` per seeded UID, and the lists. Rolls are rare events, so this does not matter now.
- **Shared asset mutated during the gate.** The gate sets the shared `EnemyData` asset's `dropTable` at runtime (`LootPipelineGate.cs:801-808`) and restores it after one frame. If an exception is thrown in between, the in-memory asset stays modified for the rest of that editor session. Batch runs exit, so this is harmless there. Prefer an `EnemyData` clone.
- **Not thread-safe.** `ItemIdentityIssuer` (a HashSet ledger and a counter) is not thread-safe. That is fine on Unity's main thread. Note it for a server.

## The questions, checked

### 1. RNG (`Runtime/Core/DeterministicRng.cs`)
- **SplitMix64.** The increment `0x9E3779B97F4A7C15`, the finalizer `(z^z>>30)*0xBF58476D1CE4E5B9`, `(z^z>>27)*0x94D049BB133111EB` and `z^z>>31` are all correct. Everything uses `ulong` inside `unchecked`, so there are no sign or overflow bugs.
- **Conversions.** `FromInt` zero-extends through `(uint)`, as documented, so negative ints map to distinct seeds.
- **`Next(int)`.** It rejects draws below `(0-range)%range` = 2^64 mod range, which is the standard unbiased method, and then takes the modulo. `range` is at most 2^31, so the rejection probability is below 2^-33. Correct.
- **`Next(min,max)`.** The span is computed in `long`, at most 2^32-1, and the result is cast back after the add in `long`. Correct for `int.MinValue..int.MaxValue`, which the gate exercises.
- **`NextDouble`.** `(x>>11)*2^-53` lies in [0, 1-2^-53] and is exact IEEE. `NextUInt32` is the high half.
- **`Fork`.** It derives from the original seed, so a fork never depends on how much its parent consumed.
- **`Combine(a,b)` = `Fin(Fin(a^G)+b+G)`.** For a fixed `a` it is a bijection in `b`, and for a fixed `b` a bijection in `a`.
  - Two different chests collide only if FNV-64 collides on the ids, or if the related-key condition `Fin(h1^G)-Fin(h2^G) = salt2-salt1` holds. Both are about 2^-64 events.
  - Order dependence is intended. Domains ("chest", "enemy-drop", "uid") are separated as the first step.
  - The stream ids 1, 2 (table) and 3 (scatter) never alias a salt-derived seed, because they are applied to a different parent.
- **FNV-1a 64.** The offset and prime are correct, applied over explicit UTF-8, so it does not depend on culture or on UTF-16. Null and "" hash alike (documented; neither can occur for a GameObject name).
- **Platform stability.** The shape and integer paths have no float. The affix roller uses `NextDouble()*double(sum of float weights)`, which is deterministic IEEE double. The scatter uses `Math.Cos`/`Sin`, but only for the item's position on the ground.
- **Known answers.** I recomputed every vector in `RngKnownAnswers`, `SeedDerivation`, `TableKnownAnswers` (including the `nothingWeight` cases) and the seeded UID `7e2cbb329625f843931bbf7f100ebb3d` with my own Python implementation (scratch only, not in the repo). All match.
  - The gate really compares them: exact `==` on ulong, double and string. The only `||`-weakened checks are "different chest id/salt changes the contents" (`:595-596`), which is acceptable.
  - Caveat: my oracle follows the same algorithm spec, so it confirms the C# implements that spec. Only the seed-0 and 1234567 SplitMix64 vectors come from an external reference.

### 2. Seed and issuer semantics
- **Session lifetime.**
  - `RunDirector.Awake` builds a new `RaidSession` (new seed, new issuer) for each scene load, and a retry reloads the scene.
  - Statics: `_hasPendingRaidSeed` is consumed once, and `_entropyCounter` is harmless. Domain reload is on (`m_EnterPlayModeOptionsEnabled: 0`), so a seed left pending cannot leak into the next play session.
  - In the editor an `EMBERDELVE_RAID_SEED` environment variable pins every raid of that editor process. That is intended for debugging, and it is logged with source "environment".
- **Seed resolution order.**
  1. Explicit `SetNextRaidSeed` (consumed once).
  2. Inside `#if UNITY_EDITOR || DEVELOPMENT_BUILD` (`RunContext.cs:117-134`), the `-emberdelveRaidSeed` argument, then the environment variable. These are the correct symbols, so the override is compiled out of release players.
  3. `DefaultRaidSeed`.
- **Entropy.** `Guid.NewGuid` is a CSPRNG-backed v4 on Windows, Mono and IL2CPP, mixed with UTC ticks and an interlocked counter. Most of the entropy comes from the GUID, not from time. The secrecy follow-up (server-owned seed) is noted.
- **Default UIDs.** These are `Guid.NewGuid` (122 random bits) through `ItemIdentityRules.TryMintUid`, then checked against the issuer's ledger and redrawn if seen. Collision probability is negligible (about n²/2^123).
  - The ledger only covers this issuer's own mints. Restored stash items are protected by the bag's duplicate-UID refusal and `ItemUidRegistry`, not by the issuer.
  - Main thread only (S8).
  - "Mints nothing rather than reuse" holds: after 8 repeated draws it returns false with `Guid.Empty` and does not increment the count. The gate tests this with a constant stream.

### 3. Loot flows
- **Chest without a session refuses.** `ChestInteractable` logs, shows a toast and returns false. No scene or prefab places a chest: the only RunDirector, EnemyAgent and LootPickup users are in `Emberdelve_Level01.unity`, and chests come from `ChestSpawner` with the RunDirector as host. Of the existing gates, only ChestInstance and ChestPartial configure chests with `director`, which is a session host. The gate's `BareHost` covers the refusal path.
- **Smoke "items" with an entropy raid seed.** The real-chest assertions do not depend on the seed: the ember chest guarantees a non-stackable cuirass, so it always leaves something behind with a full bag; the supply chest guarantees a draught; the sealed chest guarantees a relic. Low flake risk.
- **Enemy drop key.** See S1 and S2. Kill order does not affect contents, because each drop is a pure function of (raid, key) and the issuer only adds UIDs.
- **`nothingWeight` = 0 leaves tables unchanged.** `ticket = Next(total + 0)`, and the old -1 path is unchanged. Verified: chest assets have no `nothingWeight` field and deserialize to 0.
- **Re-baseline.** See M1. The Servitor is equivalent. The Warden changed: fewer relics, the copy cap binds, and it now drops boots.
- **Pickup instance lifecycle.**
  - `Configure(ItemInstance)` holds the reference without serializing it. Scene pickups stay definition pickups.
  - On success the pickup is destroyed. On refusal (full bag, duplicate UID, host refusal) the same object and the same instance stay, and the gate proves this.
  - A second interact in the same frame before `Destroy` completes is caught by the bag's duplicate-UID refusal.
  - Ground instances are not persisted. They are lost at scene end, which is correct for raid ground loot.
  - Corpse loot (U4B) can reuse `SpawnLootInstance`.

### 5. Test integrity
- **Modified gates.**
  - `EmberdelveLootRollerGate`: `FixedRandom` now implements `ILootRng` with the same scripted `NextDouble`/`Next(max)` values. `new System.Random(seed)` is replaced by `DeterministicRng.FromInt(seed)`. No assertion text or logic changed. The new methods `Next(a,b)` and `NextUInt*` count calls, but the roller never uses them.
  - `EmberdelveItemCatalogGate`: `System.Random(5)` is replaced by `DeterministicRng.FromInt(5)`, and the coverage check now includes `dropTable` items and affixes (stronger).
  - No other gate file changed.
- **Moved counts.** CloakSlot 10110 → 10157 and AffixProfile 13344 → 13336 are honest. Both loop over 300-400 int seeds and run one `Check` per rolled cloak, gear unit or affix record. Their expectations are structural (rarity matches the entry, affix count, category allowlist, determinism, at least one of each kind) and are not hard-coded outputs. A different generator gives different contents and so a different count. Nothing was silently re-baselined.
- **The 3941 checks are real, but most of them are trivial.**
  - About 2000 of them are "shape roll succeeded" calls inside the `nothingWeight` 2000-seed loop, because `RollShape` calls `Check`.
  - About 1800 are per-iteration roll successes in `UniqueIdentity` and `SessionDeterminism`.
  - The substantive assertions are roughly 100. They are good: known answers, uniqueness across more than 1000 instances in random and seeded mode, the ledger, the live kill → pickup → bag → equipment path with exact snapshots, refusal and retry, duplicate refusal, a real chest compared with the pure roll, and the source scan.
- **Passing under both entropy and a fixed seed.** True according to the logs, but only `RunStartWiring` (the seed source label) actually depends on the run seed. Every content assertion uses fixed seeds through `RaidSession.Begin` or `UseSessionForTest`.
- **Flakiness.**
  - The only assertions that depend on chance are the distinctness ones: 1000 default seeds distinct, `b != 12345`, random-UID signatures differ, different-session UIDs disjoint. Each fails with probability about 2^-64 or less.
  - The uniformity and `nothingWeight` 850-1150 checks use fixed seeds, so they are deterministic.
  - The starting-kit check covers 0 instances today, because the kits hold carried goods only (the worker says so). The legacy-mint check covers the bag-to-issuer wiring instead.

### 6. Compile, API, overclaims
- `UseSessionForTest` is internal. It compiles for the editor assembly through the existing `InternalsVisibleTo("Assembly-CSharp-Editor")` (`LocalCombatAuthority.cs:7`).
- `RaidSession` (namespace Items) depends on Data (`LootTable`, `EnemyData`), which deepens the Data↔Items namespace cycle that R8 has to break. `DeterministicRng` in Core has no dependencies, which is good.

- Overclaims found: M1, M2, M3, S4 ("version-4") and S7 ("strafe"). Everything else in R4R5.md matches the code and the logs.
