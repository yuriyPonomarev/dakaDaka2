# R0 independent review: extraction loot rule + stale AttributeSkill fixture id

Reviewer: independent, clean context, read only. Scope: `git diff HEAD` (6 files) and `Docs/Tasks/R0.md`, checked against `AGENTS.md` and `CODEBASE_HEALTH_20261020.md` F3. I did not run Unity. Where I quote results, they come from the worker's `Logs/r0_*.log`, which I read.

## Verdict: ACCEPT-WITH-FOLLOWUPS (one small must-fix in the test before commit)

The runtime fix is correct and closes F3.
- The only producer of `Complete(RunState.Extracted)` is `RunDirector.BeginExtraction` (`RunDirector.cs:178-188`). It now re-runs `ExtractionAllowed`, which covers both the loot rule and the "state must be Running" check.
- The grep found no other callers of `BeginExtraction`, no other `IExtractionSink` implementers, and nothing in UI/Review/result-screen code that calls `OnHoldComplete`/`BeginExtraction`.
- The result screen and retry only read `RunState.Extracted` (`ResultScreenController.cs:31`, `FeedbackDirector.cs:168`). They cannot cause an extraction.
- The signature change from `void` to `bool BeginExtraction(out string)` breaks no other code.
- Double extraction cannot happen: `ExtractionAllowed` refuses once state is no longer Running, and `Complete` keeps its own `_state != Running` guard. Everything runs on the main thread, so there is no race.

One new assertion is tautological (F-1). It should be fixed before commit because it is exactly the kind of fake coverage F3 was about.

## Findings (ranked)

### F-1 Medium (test is tautological): the "refusal reason surfaced" check passes from an earlier toast
`Editor/EmberdelveRuntimeSmokeTest.cs:1005-1010, 1021, 1028, 1036`
- `onToast` is subscribed before step (4). Step (4) calls `_director.BeginExtraction` directly, and that raises the toast "Recover at least one relic first". The toast contains "relic", so `relicToast = true` is already set before the Interactor hold starts.
- Line 1028 resets only `lastToast`, not `relicToast`.
- `Check(relicToast, "refusal reason surfaced to the player")` at :1036 therefore passes even if the Interactor/ExtractionPoint hold path never raised a toast.

**Failure scenario:** someone deletes the `RaiseToast` in `Interactor.cs:95`. The player holds E for 3 s with no loot, the bar fills and silently empties with no message, and the smoke still reports `ok`.

In the actual log, `lastToast` was "Recover at least one relic first" (`r0_extraction.log:1027`), so today's behaviour is fine. The assertion just doesn't prove it.

**Fix:** add `relicToast = false;` next to `lastToast = null;` at :1028, or assert on `lastToast` instead.

### F-2 Low-Medium (test fragility / coupling): step (3) starts from leftover progress from step (1)
`EmberdelveRuntimeSmokeTest.cs:1002, 1030-1049`
- Step (1) holds for `HoldDuration + 1` s. It completes once at 3 s, then refills to about 1/H (0.33 at H=3).
- Three release frames barely decay it (`r0_extraction.log:1040` shows 0,33).
- Step (3) then holds another H/2 s, so "before" is 0.33 + 0.5 = 0.83 (`log:1546`). The upper bound in the check is 0.9.

The step-(1) check "hold progress was reset after the refused hold (< 0.5)" is also met by the refill value 0.33, not by a reset.

**Failure scenario:** `extractionHoldDuration` is tuned to 2 s. Leftover 0.5 plus 0.5 means the hold completes, and the run extracts during the "half-way" wait. Steps (3) and (2) then fail confusingly. At any H below about 2.5 s, the `before < 0.9` check fails.

**Fix:** after step (1), wait until `interactor.HoldProgress == 0` (it decays at 1.6/s), or step off the gate, before starting step (3).

### F-3 Low (design / robustness): the damage interrupt infers damage from a per-frame health drop
`Runtime/Interaction/Interactor.cs:51-58`

What is fine:
- First-frame init (`_lastHealth = -1` sentinel) is correct.
- Respawn/`Configure` raises health, so it can't false-trigger.
- While dead, the method returns before sampling, and the next sample after a revive is higher.
- Regen and `Heal` only raise health, so they can't false-trigger.

Gaps:
- **False positive:** `HealthComponent.SetMax` clamps current health down when the ceiling shrinks (`HealthComponent.cs:65`, called from `PlayerRig.RefreshEquipmentStats` via `Equipment.cs:385`). Unequipping CON or max-HP gear mid-hold would read as damage. Today equipping happens with the satchel open, which disables gameplay input, so the impact is only a decaying bar snapping to 0. Any future HP-cost skill or `SetHealth` call will also interrupt.
- **False negative:** damage and a heal in the same frame (potion via `Inventory.cs:1177`, future lifesteal) that net to zero or more does not interrupt.
- **Shield blocks:** a fully blocked hit (0 net) does not interrupt. That may or may not be the intended design.

**Better:** subscribe to `HealthComponent.Damaged` (it already exists and fires on every `ApplyDamage`) and reset on any damage event. The current test would still cover it.

### F-4 Low (test seam): `InteractHeldOverride` is safe for shipping, but it bypasses input gating, so the tests skip that gate
`Runtime/Input/EmberdelveInput.cs:54-60`

Why it is safe:
- It is an instance property on a scene MonoBehaviour, not static, so a scene reload destroys it. ResultLoop's retry gets a fresh rig.
- It defaults to null, and nothing in Runtime sets it.

The catch:
- When set, it overrides `_playerMap.Disable()`. With the override on, the hold keeps filling after extraction, during pause (time scale 0 stops it anyway) and with the satchel open.
- So the new tests do not verify that disabled input blocks the hold. That gating is still covered only by the real Input System path.
- In step (2) the override stays true after the run ends. A later completion is blocked by `CanInteract`, but only because the run is no longer Running.

Optional follow-ups:
- Wrap the setter in `#if UNITY_EDITOR || DEVELOPMENT_BUILD`, or have the override respect the action-map enabled state: `_playerMap.enabled && (override ?? IsPressed)`.
- The test's cleanup (`RunEnded`/`ToastRaised` unsubscribe, override reset) is not in a `try/finally`. An exception mid-coroutine would leak static `GameEvents` handlers. Low risk, because `Check` does not throw.

### F-5 Low (test strength): "extraction fired exactly once" cannot fail on either old or new code
`EmberdelveRuntimeSmokeTest.cs:1062-1065`
- After the damage reset, the hold lasts H+1 s. Only one completion fits in that window, and `Complete` was already idempotent before this change.
- It is a valid sanity check, not a double-extraction regression test. To make it real: keep holding for more than 2H after extraction, or call `gate.OnHoldComplete()` and `_director.BeginExtraction` again after extraction, and assert `endedCount` is still 1 and `BeginExtraction` returns false with a reason.

### F-6 Low (UX, acknowledged by worker): a blocked hold still fills the bar
`Interactor.cs:77-97`. With zero loot, the bar fills for 3 s and then toasts. This repeats every 3 s while E is held. The prompt already shows the blocked reason (`BuildPrompt`). It would be better not to accumulate progress while `CanInteract` is false.

Also not done, from F3's "also missing": progress still **decays** on release (`:99-103`) instead of resetting, and moving within range does not interrupt. R0's scope did not include these, but U4B still requires them.

### F-7 Info: behaviour change for chests (acceptable)
The completion re-check in `Interactor.cs:89` now applies to every hold interactable. `ChestInteractable.CanInteract` (`:150-172`) refuses only when there is no table, the chest is empty, or a sealed chest lacks the value. In all of these, opening was not legitimate anyway, so this is an improvement, not a regression. Chest smokes passed (`r0_chestinst` 21/0, `r0_chestpartial` 17/0).

### F-8 Info: redundant layered checks
The Interactor, `ExtractionPoint.OnHoldComplete` and `BeginExtraction` each validate. On the real hold path only the first refusal toasts, so there are no double toasts. A direct `ExtractionPoint.OnHoldComplete()` call (no current caller) also toasts only once. This is fine as defence in depth.

Pre-existing issues, not introduced by R0:
- `ExtractionAllowed` skips the loot rule when `config == null` (`RunDirector.cs:164`).
- It reports "Run already finished" while Paused.

### F-9 Info: AttributeSkill change is clean
`EmberdelveAttributeSkillGate.cs:921, 1304-1308`
- The id is renamed to satisfy `ItemIdentityRules.IsStableItemId`, as diagnosed in `P2-baseline.md:52`. Grep finds no other dashed fixture ids in Editor.
- The `TryAdd` check keeps the same boolean condition. Only the label gained the reason, and an extra `LogError` fires only on refusal. Nothing was weakened.
- Log: `PASS checks=885 failures=0` (previously 884 checks with 11 failures). The one extra check is from the now-reachable downstream path.

## Removed or weakened assertions: none
I diffed `ExtractionFlow` line by line:
- The old auto-pickup fallback (`if LootValue <= 0, pick up loot`) is replaced by a stricter check: `startedEmpty`.
- "loot requirement satisfied before extraction" and "gate accepts interaction" are kept. They moved inside `if (interactor != null && _rig.Input != null)`. If that guard is false, extraction never happens and the unchanged final `State == Extracted` check (:1075) fails, so nothing silently passes.
- The direct `gate.OnHoldComplete()` shortcut was replaced by the real Interactor hold.

Would the tests fail on old code? (1) yes: the old Interactor plus the old `BeginExtraction` would extract, so the "state Running / endedCount 0" check fails. (3) yes: with no reset, "after" stays at or above "before". (4) would not compile against the old signature. F-1 and F-5 are the exceptions noted above.

## Parked-enemy fixture
`SetActive(false)` on all `EnemyAgent`s (:1015-1016) is justified: live hits would correctly interrupt the hold. The run then deliberately injects damage. It does not hide a defect. The cost is that the smoke no longer exercises the gate with live enemies nearby. Enemies are never re-enabled, which is harmless: extract mode ends after this, and ResultLoop reloads the scene.
