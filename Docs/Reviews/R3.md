# R3 independent review: one runtime ItemCatalog (F5)

Reviewer: independent, clean context, read only (no edits, no git writes, no Unity runs). Date: 2026-10-21.
Scope: `git diff HEAD` (18 modified files) plus the untracked files `Runtime/Items/ItemCatalog.cs`, `Editor/EmberdelveItemCatalogGate.cs`, `Editor/EmberdelveTestCatalog.cs` and `Data/EmberdelveItemCatalog.asset(+.meta)`. I checked the claims in `Docs/Tasks/R3.md` against the source and against `Logs/r3*_*.log`.

## Verdict: ACCEPT-WITH-FOLLOWUPS

The main F5 hole is closed. `Inventory.TryAdd/TryAddAt` and `LootTable.TryRoll` no longer build a catalog out of the definition they are given. `LocalCatalogFor` and `TryBuildAuthority` are deleted. Gear UIDs are minted only for an object that the single `ItemCatalog` asset owns. That asset is complete for the current data (10 `ItemData`, 13 affixes). It is wired consistently: `GameConfig` -> catalog GUID `f3859776…` matches the `.meta` file, the `m_Script` GUID `1b75052…` matches `ItemCatalog.cs.meta`, and both shipping scenes reference the config. Seeded roll streams are unchanged by construction. No fixture assertion was weakened, and check counts only went up. Two small items should land before commit (M1, M2). Everything else is follow-up work.

The `combat` flake is **not caused by R3**, and it is **not an authority race**. It is a defect in the test environment (diagnosis below).

## Must fix before commit

### M1. The test seam is public in the runtime assembly, and the gate does not watch it
- Location: `Runtime/Items/ItemCatalog.cs:386` (`public static CreateForTest`), `:403/:436` (`public RegisterForTest`). `Inventory.SetCatalog` (`Inventory.cs:133`) is public too.
- Problem: `RegisterForTest` correctly refuses on an asset catalog. But nothing stops runtime code from calling `bag.SetCatalog(ItemCatalog.CreateForTest(new[]{anyItemData}, null))`, and that brings back exactly the "any ItemData becomes gear" behaviour. A test catalog also drops the production rule that gear needs affixes (`TryGetAuthority`, `!_testOnly`, line 140).
- The source scan in the gate (`EmberdelveItemCatalogGate.cs:505-517`) only looks for `ItemInstanceAuthority.TryCreate(` and `LocalCatalogFor`. It never looks for `CreateForTest` or `RegisterForTest`.
- Fix (small): make both seam methods `internal`. This is the same precedent as `LocalCombatAuthority.SetClock`, and `[assembly: InternalsVisibleTo("Assembly-CSharp-Editor")]` already exists in `LocalCombatAuthority.cs:7`. Also add `CreateForTest(` and `RegisterForTest(` to the Runtime source scan. Without an asmdef split, `internal` does not stop Assembly-CSharp code from calling them, so the scan is what actually enforces this. Say so in the doc comment, as `SetClock` does.

### M2. `TryAddInstance` checks the definition but not the rolls
- Location: `Inventory.cs:565`. A catalogued bag runs only `_catalog.Contains(definition)`.
- Scenario: any code builds its own authority with `ItemInstanceAuthority.TryCreate` (still public). For example, real `Item_FootpadBoots` plus an ad-hoc `AffixDefinition` "x_str" with range 0..999. It mints Rare boots with value 999 through `ItemInstance.TryCreateNew` or an issuer, then calls `RunDirector.TryCollectLootInstance` or `bag.TryAddInstance`. The bag accepts it because the definition is the catalog's own object. The affix id, band and step were never checked against the catalog's affix set.
- R3's stated goal is that instances are "validated against the one authority" (`ItemCatalog.cs:17-18`). This path is the one gap left in it.
- Fix (one call): when `_catalog != null`, run `ItemInstance.TryValidateSnapshot(instance.ToSnapshot(), _catalog.Authority, out reason)` before placing. The API already exists at `ItemInstance.cs:465`. Add one gate check with a foreign-affix instance of a catalog definition.
- Impact on fixtures: GearInstance, ArmorAffix, ChestInstance and CloakSlot build their test catalogs from the same item and affix objects as their authorities, so they should still pass. This needs a rerun of those four gates plus `items`.

## Findings (ranked)

### H1. Silent "empty chest" when an item is missing from the catalog; completeness is guaranteed only by the builder and the gate
- `LootTable.TryRoll` refuses the **whole** roll if any gear entry is not a catalog member (`LootTable.cs:331`, `TryDeriveAuthority` ~`:438-480`). In a run, `ChestInteractable.Open` (`ChestInteractable.cs:207-215`) then logs an error, shows the toast "Chest contents are invalid", and stays unrolled. So every open retries and fails, and the player sees a chest that never gives anything. Enemy drops of such an item are refused at pickup with a technical toast (`Inventory.cs:294-298`).
- Completeness comes from the asset set, not from a hand-written list. That part is good: `BuildItemCatalog` gathers every `t:ItemData` under `Data`, recursively and sorted ordinally (`EmberdelveAssetLibrary.cs:1033-1058`). But it only happens when someone runs `BuildAll/BuildDataOnly`. A hand-created ItemData asset that is put into a loot table without a rebuild is caught only by the R3 gate's coverage check (`ItemCatalogGate.cs:224-259`). Nothing catches it in the editor or at run start: `RunDirector.Awake` (`RunDirector.cs:55-65`) checks that the catalog is internally valid, not that it covers anything.
- Follow-up: at run start, or in `ChestSpawner.Ensure`, check that every gear entry in the layout's loot tables, every class starting item and every `EnemyData.lootTable` item is a catalog member, and log one aggregated error. Optionally add an `AssetPostprocessor` or validation menu that flags ItemData assets the catalog does not list.

### H2. Spec deviation from CODEBASE_HEALTH R3 (narrower than written; the R3.md report does not claim more)
- The health doc's R3 row says gear enters "only through `TryAddInstance`", the starting kit is "created by the run or server through the issuer", and there is one authority "per run". What was implemented:
  - the bag is still a minting door, with its own issuer per bag (`Inventory.cs:639-657`);
  - the starting kit is minted by the bag (`GiveStartingItems`);
  - every loot roll builds a fresh derived `ItemInstanceAuthority` and a fresh local issuer (`LootTable.cs:216`, `ItemCatalog.cs:317`).
- This meets the brief given to the worker ("stop minting gear for arbitrary ItemData"), and R3.md lists the per-run issuer under R4. Still, the coordinator should record that the bag is still a mint point until R4 or U3 moves minting to the run or server.

### H3. A bag with no catalog still admits ready-made instances (documented follow-up; fails open)
- `Inventory.cs:565` skips the definition check when `_catalog == null`. Production ordering is safe:
  - `RunDirector.Start` -> `PlayerRig.ApplyClass` -> `ClassLoadout.Apply` sets the catalog (`ClassLoadout.cs:82`) before `_inventory` is captured, before chests are spawned, and before the run is Running;
  - `TryCollectLootInstance` refuses unless the run is Running;
  - Lobby and `EmberdelveReviewBridge` have no item paths (grep confirmed).
- But if `GameConfig.itemCatalog` were ever null (a data error), minting would fail closed while instance admission fails open. Recommend making instance admission fail closed in R9, as R3.md itself suggests.

### M3. The chest gets the run catalog through the player's bag
- `ChestInteractable.cs:208` uses `_host.Inventory.Catalog`, not `config.itemCatalog`. Determinism is not affected, because the catalog only gates membership and does not change the RNG streams. The cost is that the chest's validity depends on whichever catalog a fixture last put on the bag, and that is how the ChestInstance gate works today. Better: pass the run's catalog explicitly through `ILootHost` or `ChestSpawner.Ensure(layout, config, …)`, which already has the config.

### M4. `ClassLoadout` keeps a stale catalog when config has none
- `ClassLoadout.cs:82-84`: a config with a null catalog keeps whatever the bag already has, so a fixture's test catalog carries over silently. This exists only to help tests. Prefer always assigning `config.itemCatalog` and logging when it is null. Fixtures already re-adopt their catalog through `EmberdelveTestCatalog.Adopt`.

### L1. Gate brittleness and gameability
- The source scan is a plain substring match. It is defeated by `using static`, an alias, a reflection call, or a different file name. It is acceptable as a tripwire, and M1 widens it. The real protection is behavioural: the bag, table and restore refusals, which the gate does cover well, including "state string identical before and after".
- The gate runs `BuildDataOnly` twice, so it writes to the data tree. The "drift from start" check (`:150-159`) makes that visible, but running the gate on a dirty tree can rewrite data assets. That is the same F8 concern as smoke calling `BuildAll`.
- About 108 checks are meaningful. The negative paths assert no mint (`issuer.MintedCount == 0`, `MintedInstanceCount`) and no partial state. Gaps:
  - no check for the M2 forged-affix case;
  - no check that a chest with a non-catalog gear entry shows "invalid" and stays unrolled;
  - no check that `TryAddInstanceAt` refuses non-catalog definitions (only `TryAddInstance` is tested; both share `TryAddInstanceInternal`, so the risk is low).

### L2. Fixture hygiene
- `EmberdelveTestCatalog.Release` destroys the test catalog but leaves the bag pointing at a destroyed object. Unity's `==` then reports "no catalog", so the bag would refuse gear if the scene kept running. All three Attribute gates release only at teardown, so this is harmless today. Better: restore the production catalog in `Release`, or pass the bag in.
- `EmberdelveRuntimeSmokeTest.cs:2900-2901`: `productionCatalog.Items` throws a NullReferenceException if the rig's bag has no catalog. Load the asset by path instead, as `:3847` does.
- `ManagerInventoryGeometryProbe` is not part of the regression list, and its fix (unique ids, test catalog) was not run in the r3final sweep.

### L3. Minor API notes
- `ItemCatalog.Items/Affixes` return the live serialized arrays as `IReadOnlyList`. A caller can cast back to `ItemData[]` and mutate the asset's list, and the cached authority would then be stale. Return a copy, or document it.
- The cached `_evaluated` authority is not invalidated when an `ItemData.itemId` is edited in the inspector during Play. Editor-only, low impact.
- `ItemCatalog.Validate` with `requireAffixesForGear` refuses a catalog that lists gear with no affixes. That is correct for production, but adding the first gear item to a fresh project then requires an affix catalog too. That is intended; just note it in the doc.

### Verified (no finding)
- **Bypass sweep.** In Runtime, the only callers of `ItemInstanceAuthority.TryCreate` are `ItemCatalog.cs:103,317`.
  - `ItemInstance.TryCreateNew/TryCreateWithUid` are still public but have no runtime callers.
  - `Equipment` only receives instances from the bag (`TryEquipFromInventory/TryEquipItem` -> internal `TryEquipTransfer/TryUnequipTransfer`), so nothing enters equipment from outside.
  - `LootPickup` and enemy drops are definition-only and go through `CollectLootCounted` -> `TryAdd`, which is now catalog-gated. All current enemy drops and class kits are catalog members (asset GUIDs checked).
  - Snapshot restore goes only through `ItemCatalog.TryRestore/TryRestoreAll` -> `ItemInstance.TryRestore(snapshot, authority)`. The batch is atomic, with duplicate UID and unknown id refused (gate `:451-503`).
- **Partial acceptance.** The catalog pre-check (`Inventory.cs:294`, `:393`) runs before any state change. The counted path (`accepted`) is unchanged for carried stacks, and the gear rollback (`RollbackCreatedStacks`) is kept for mint failures that happen later. Coins and potions never touch the catalog.
- **Determinism.** The order of the derived authority's affixes is still the table's own `affixCatalog` order, deduplicated (`LootTable.cs` ~`:458-472`). `LootRoller` reads `authority.AffixDefinitions` (`LootRoller.cs:290`). The shape, item and amount streams do not consult the authority. Item order in the authority only affects lookup. So seeded output is unchanged by construction. One loosening: carried entries are no longer put into the authority, so a carried entry with an invalid id no longer refuses a gear table. That is harmless.
- **Fixtures.** No assertion was removed or loosened, and no expected value changed. The diffs only add catalog wiring, `TryRoll(..., catalog, ...)` arguments, and registration checks. Counts against earlier logs:
  - unchanged: GearInstance 62, ArmorAffix 44, ChestInstance 21, AffixProfile 13344, combat 227;
  - increased: items 403->404, AttributeAction 231->242, Vitals 200->205, Skill 891->918, CloakSlot 10109->10110.
- **AttributeSkill `EquipCharm` serial suffix** (`AttributeSkillGate.cs:1299`): fine. The label is kept in every message. No check compares the charm's `itemId` to the label. One id naming one definition is the rule the gate is meant to respect.
- **Logs.** Every `r3final` gate shows PASS with failures=0, and there are no catalog refusal lines ("could not give", "not an entry of", "contents refused", "has no itemCatalog") in any r3final log.

## Flake diagnosis: `combat` "off-axis windup -45 deg"

### Evidence
- The test is `EmberdelveRuntimeSmokeTest.cs:766-838` (`OffAxisWindupFlow`). It runs +45, then -45, then outside-the-wedge, against one enemy that `PickAliveEnemy` chooses, in the live Level01 scene.
- Failure in `r3a_combat.log:10015/10028`: **0 damage**, and the "accepted exactly one, rejected none" check fails.
- Failure in `r3b_combat.log:7587/7600`: **30 damage** (two 15-damage claw hits) and the same count check fails. This means **two** attacks were accepted in one window.
- In neither failing window is there any `[CombatAuthority] Rejected attack` line. `logRejections` is on, and the first rejection for each reason is always logged (`LocalCombatAuthority.cs` `Reject`). The only rejection lines in these logs come from the deliberate forgery tests near line 3100.

### What this rules out
- **Not the authority's 1.5 m hit-point rule, and not cooldown, reach or authority line of sight.** Any of those would have logged a rejection. The geometry also has a large margin. Since R1a the enemy submits the target's own centre as the hit point (`EnemyAgent.cs:377`), so the hit-point distance is 0 against a tolerance of 1.5. The authority's 3D distance is about 1.8 m against reach 2.65 + 0.8.
- **Not a brain/authority cooldown mismatch.** The brain's cooldown is 2.0 s (`Enemy_HollowServitor.attackCooldown`), and it only counts down while the agent is enabled. The authority's is 2.0 × 0.8 = 1.6 s of wall time, so the brain is always the slower of the two.
- **Not two strikes from the observed enemy.** That would need the windup (0.6 s) plus the brain cooldown (2 s) to fit inside a window that ends 2 frames after the strike. Frame dt is capped at 0.1 s (`TimeManager` Maximum Allowed Timestep).

### Root cause: the test does not control its environment (a test defect, not a runtime defect)
1. **Other enemies are still live.** `OffAxisWindupFlow` (like `DefenseFlow` before it) toggles only the chosen enemy. Every other `EnemyAgent` in Level01 keeps running its brain, with sight 14-18 m and hearing range. The flow spends many seconds near the spawn: up to 9 s waiting for each windup, a 2 s brain cooldown each iteration, and the guard sequence before it. A second enemy can walk into range and hit the player during the window. That explains r3b exactly: two accepted hits, no rejections. It also makes the global `AcceptedCount/RejectedCount` delta the wrong thing to assert on.
2. **The strafe position is never validated, and the player's body is still simulated.** Line 803 teleports the player to `enemy.position + rotate(±45°, warned) * 1.8` without checking walkability, clearance or line of sight. `enemyHome` and the committed telegraph direction come from the real brain's earlier chase, which depends on frame timing, and patrol points are seeded with unseeded `Random.value` (`EnemyBrain.BuildPatrolPoints`). So the -45 spot sometimes lands against or inside level geometry, or overlaps another enemy's body. When that happens, either:
   - the brain loses sight or range and drops the windup with no attack: `TickAttack` with `!visible || distance > range*1.35` goes to Chase with `_windingUp = false`. This shows up as 0 damage, no submission and no rejection, which is exactly r3a; or
   - the player's `CharacterController` is pushed out of the overlap on its next move, so at strike time the player is out of the wedge or out of range, and `EnemyAgent.SubmitAttack:353` records a whiff. This also gives 0 damage and no rejection.

   Either way, this matches r3a.
- The +45 versus -45 asymmetry comes from geometry: the enemy is placed on the dominant axis next to the spawn, and walls or corners are on one side.

### Is there a real gameplay race?
No. Dropping the windup when line of sight or range is lost, and whiffing outside the wedge, are the intended R1a behaviour. The authority accepted every attack that reached it. One real design note, not a defect: brain timers tick only while `EnemyAgent.enabled` is true and are kept across disable and enable. Only tests toggle `enabled` today.

### Deterministic fix (test only)
1. Isolate the scenario. For the whole `DefenseFlow` and `OffAxisWindupFlow`, park every other `EnemyAgent` with `SetActive(false)` and restore them afterwards. `ExtractionFlow` already does this at `:1261`.
2. Use a known-clear arena. Before the loop, choose an anchor and enemy spot whose three strafe positions (+45, -45, outside) are all nav-walkable (`INavigationProvider.IsWalkableWorld`), clear of colliders (`Physics.CheckCapsule` with the player's radius and height, ignoring the player), and have line of sight to the enemy's eye. Use `HitScanner.HasLineOfSight` with the same mask and radius the brain uses. If no such spot exists, fail with a clear diagnostic rather than trusting luck.
3. Freeze the player's body during the strafe. Disable `PlayerMovement`, or move the player with `CharacterController.enabled = false` then set the transform and `Physics.SyncTransforms()`, and zero any velocity, so depenetration and gravity cannot move it before the strike.
4. Assert on this enemy only. Compare `_localAuthority.LastSequenceFor(enemy.CombatId)` and `LastAttackTimeFor(enemy.CombatId)` before and after, plus a damage capture filtered by instigator, instead of the global counters. Assert `!enemy.LastAttackWhiffed` in the inside-wedge cases.
5. Make a failure explain itself. On failure, log the brain state, distance, angle to the warned direction, line of sight, `LastAttackRejectReason`, the player's position before and after the strike, and any other live enemies within 8 m.

Optionally, drive the brain with a fixed `dt` instead of real frames. With steps 1-3 in place the outcome no longer depends on timing, because the authority's own clock already gives margin.

## Summary of follow-ups (after commit)
- H1: check catalog coverage at run start or chest spawn; add an editor hint for ItemData assets that are not in the catalog.
- H2 / R4: move minting out of the bag; use one issuer and authority per run; starting kit through the run.
- H3 / R9: a bag with no catalog refuses instances; snapshot restore of containers through `TryRestoreAll`.
- M3/M4: pass the run catalog explicitly to chests; `ClassLoadout` always assigns the config's catalog.
- L1-L3: widen the gate (forged affix, chest-invalid path, `TryAddInstanceAt`); `Release` restores the production catalog; load the catalog in smoke by path; `Items/Affixes` return copies.
- Flake: apply the five test fixes above. Do not treat it as a runtime bug.
