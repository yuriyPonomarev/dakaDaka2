# Review U2B11: Back/cloak slot, cloak data, rarity and fixed/rolled tooltips, character pane

Reviewer: independent, clean context, read only (no edits, no git writes, no Unity runs). Scope: `git diff HEAD` plus the untracked `ItemTooltip.cs`, `EmberdelveCloakSlotGate.cs`, `Item_AshenCloak.asset`, `Item_EmberthreadMantle.asset` (and metas), checked against `Docs/Tasks/U2B11.md`, `Docs/Design/ITEM_AFFIXES.md`, `ATTRIBUTES.md` and `AGENTS.md`. I read the `Logs/u2b11_*` summary lines and file timestamps but did not re-run anything.

## Verdict: ACCEPT-WITH-FOLLOWUPS

The core change is sound. The slot is appended (`Back = 6`, existing integers untouched). Every slot loop in `Equipment` goes through a derived `SlotCount`. Back maps to the Cloak category, so cloaks cannot roll weapon-only affixes. Equip, unequip and swap use the existing atomic paths, and stats are rebuilt with no accumulation and no free refill. Only two existing fixtures changed, both legitimately. Logs agree with the report: CloakSlot `PASS checks=10107`, inventoryui2 `PASS 202`, AffixProfile `PASS 13344`, AttributeSkill `PASS 891`. All runtime sources were older than the batch (00:55 to 00:58, batch from about 01:16). The only file changed after the batch is `EmberdelveInventoryUiChecks.cs` (01:30:15), and it was re-run as `inventoryui2`, as stated.

Two things need fixing before commit: a small layout regression the report says is fine, and some report statements that are inaccurate or leave out a gameplay consequence. The visual side (tooltip panel, 54 px slots, rarity colours, character pane) still has no screenshot, so a windowed review is required before the task is accepted.

## Must fix before commit

### M1. The character pane overflows by 6 px after adding the Armour row. The report says it fits.
- `Runtime/UI/CharacterStatsView.cs:35` (`GuardRowCount = 2`), `:39-45` (`PreferredHeight` = 4x21 + 14x18 = **336**), `:159` (new row).
- `Runtime/UI/InventoryScreenController.cs:1383-1394`: the pane height is `gridHeight + 10 + 74 + 10 + 56` = **340** for the 10x4 grid. The rows group is placed at `paneTop - PanePadding` (10 px inset), so the rows end at 346 px below `paneTop`.
- Result: the last row ("Skill power") ends 6 px below the bottom of the `StatsPane` background, with no bottom padding. Before U2B11 it was 13 rows: 318 + 10 = 328, which fit. The report's sentence "14 rows x 18 px + 4 section lines still fit the existing 340 px pane (336 px)" leaves out the 10 px top inset. `PreferredHeight` claims "The host sizes its pane from this", but nothing reads it.
- It is still inside the satchel panel, so it is not off-screen. It is a visible edge defect, and the arithmetic in the report is wrong.
- Fix (one line): size the pane from `PreferredHeight + 2*PanePadding`, or set `RowHeight` to 17 (14x17 + 84 = 322, plus 10 = 332). Add a rect check that the last `StatValue` row sits inside `StatsPane`.

### M2. Corrections to `Docs/Tasks/U2B11.md`: overclaims and an undisclosed gameplay consequence
1. **Every Sealed chest now always drops a Rare Emberthread Mantle.** `Loot_SealedChest` has 4 entries, each `maxCopies 1`, with `guaranteeFirstEntry` and `maxRolls 3`. `LootTable.TryRoll` (`Runtime/Data/LootTable.cs:339-354`) takes entry 0 and then rolls 3 times without replacement over the 3 remaining entries, so every entry drops every time. The "weight 2" in the report has no effect. The gate log confirms it: `rare=400` out of 400 seeds. Ember drops the mantle about 73% of the time (292/400) and Supply drops the cloak about 31% (123/400). Each of these is a 2x3 item, which adds bag pressure. This is a balance and design decision that the architect or user has to make knowingly. Either state it in the report, or change it (for example, raise Sealed `maxRolls` headroom by adding an entry, or lower its rolls).
2. "3 tables x 400 seeds (determinism per seed)": the CloakSlot gate only compares `drops.Count == again.Count` (`Editor/EmberdelveCloakSlotGate.cs:524`). It does not compare items, rarity or rolls. Item, amount and roll determinism is really covered by the existing AffixProfile gate (`EmberdelveAffixProfileGate.cs:121-148`), which also loops over the cloak drops. The report should say that.
3. "10107 checks": about 9,900 of these (roughly 98%) come from the 1200-seed loot loop, at 4 checks per cloak drop plus 5 per affix. Each check is real, but the gate contains only about 190 distinct behavioural assertions. Report the composition so the number is not read as breadth.
4. The pane-fit sentence (see M1).

## Findings, ranked (later / follow-up)

1. **Medium: the tooltip panel does not come back after a tab round-trip.** `InventoryScreenController.cs:603` hides `_tipPanel` when switching to the character tab, but nothing re-shows it when switching back. `ShowTooltipAt` (`:643-675`) only re-applies on a hover change, and `PositionTooltipPanel` (`:787`) returns early while the panel is inactive. Scenario: hover a cloak, press the Character tab, press the Bag tab with the pointer still on the cloak. The strip line is back, but the floating tooltip stays hidden until the pointer moves to a different item. Fix: in `ApplyTabVisibility`, when `!_showCharacter && _currentTooltip != null`, call `ApplyTooltip(_hoverInstance, _hoverDefinition)`.
2. **Medium: no negative test for the category restriction on a cloak.** The gate proves that loot-rolled cloak affixes are all allowlisted for Cloak, which comes from the catalog the roller itself uses, plus a hard-coded check for no melee or projectile damage. It never asks the authority to mint a Back item carrying `affix_melee_damage` and expects a refusal with nothing minted. `AffixDefinition.cs:408` enforces this, but ITEM_AFFIXES.md requires "disallowed category ... rejected atomically" to be tested. Add one refusal check in the CloakSlot gate.
3. **Low-Med: the tooltip height ignores wrapped lines.** `:779` sizes the panel as `lines x 16 + 16`, but `_tipBody` wraps at 234 px with `VerticalWrapMode.Overflow` (`:1083`). Any wrapped line, such as an `unknown(<id>)` record or a long display name in bold, spills below the dark background. Use `_tipBody.preferredHeight` after setting the text.
4. **Low: a weak assertion in the new gate.** `EmberdelveCloakSlotGate.cs:400` uses `MaxMana >= base + 15`. The mantle also grants +1 INT, which changes derived mana, so `>=` would pass even if the INT bonus double-applied. Assert the exact value: base, plus the INT-derived delta for +1, plus 15.
5. **Low: a permissive OR check.** `EmberdelveInventoryUiChecks.cs:791` accepts `SelectedItem == null || == ashen` after a right click on the worn slot. One deterministic outcome should be asserted. The following line (793) does pin the final state, so this is not a coverage hole.
6. **Low: tooltip text quality (player-facing).**
   - Rolled lines show raw keys (`+9 max_health`, `+0.07 move_speed`, mana_regen without "/s"), while fixed lines say "Armour +2" and the rolled line says "+4 armor".
   - `DescribeModifier` (`ItemTooltip.cs:207-212`) would print "+-0.1" for a negative Flat modifier and "Block reduction +0.08" rather than a percentage.
   - The short uid appears in the player strip (`Headline`).
   - None of this is wrong data. It needs a localisation and format pass.
7. **Low: the tooltip falls back to the selection when the pointer is over nothing** (`:666`). The floating panel then follows the pointer showing the *selected* item next to the carry ghost. This is existing strip behaviour, now with a large panel. Consider showing the floating panel only for a real hover.
8. **Low: `EnsureEntry` puts back a cloak entry a designer deleted on purpose** (`EmberdelveAssetLibrary.cs:895-911`). It is idempotent in the sense claimed (it keys on item reference, appends at the end and never touches other fields). A hand-edited weight is kept, but removing the cloak from a table is undone by the next build. Document this as "builder-owned entry".
9. **Low: the Supply table was re-serialized.** The diff adds `affixRarity: 0` to its four original entries and `affixCatalog: []`. These fields existed in the schema but were never written, because U2B10 never dirtied this asset. It is benign, with no value change, but the report should mention it so a reviewer does not treat it as a data change.
10. **Low: `SlotOrder()` and `SlotCount` are derived from the highest enum value** (`InventoryScreenController.cs:972`, `Equipment.cs:55-65`). If a future enum value leaves a gap, the screen draws a row for a slot that does not exist. A guard or a comment is enough.
11. **Note: pre-existing, unchanged.** `Equipment.Clear()` (`Equipment.cs:341-347`) calls `RestoreClassHand` for *every* filled slot, including Chest, Legs and now Back. This resets the main hand to the class primary even when only a cloak was worn. U2B11 did not introduce it and it is harmless today.
12. **Note: naming debt.** `EquipmentSlot.Legs` is still the boots slot. It shows to players as the empty-slot label "Legs", the toast "does not fit the Legs slot" and the tooltip "Slot: Legs". This is a note only, as the task asks.

## Checklist results

### 1. Enum and slot correctness
- No remaining 5-slot assumption. I grepped for `SlotCount`, `(EquipmentSlot)`, `EquipmentSlot.Legs` loops and `switch` on the slot.
- `Equipment` sizes and indexes its arrays by enum value through `SlotCount` (7). `SlotIndex` rejects None and out-of-range values.
- `ItemCategoryRules` has a `Back` case. The `SlotLabel` switch has a Back case and defaults to the enum name.
- Nothing else in Runtime switches on the slot. HUD and `InventoryScreenController` use `FilledCount`, which is not a hard-coded 5.
- Serialized assets: only the item assets store `equipSlot` as an int (new cloaks: 6). Scenes and prefabs hold no slot values. `ItemInstance` snapshots do not encode the slot, and equipment is not persisted.
- Back items can never be `GrantsWeapon` (`ItemData.cs:136`), so the hand, two-handed and shield logic is untouched. `Equipment` has no two-handed code; that lives in weapon and defense data.
- Stat recompute: the same replaced source, verified exact in the gate. It covers round trips, a doubled `RefreshStats`, no heal, no mana payout, armour through the real `LocalCombatAuthority`, and a refused full-bag swap and unequip that leave counters unchanged. This is meaningful coverage.

### 2. Loot tables
- Entries are appended at the end, and the original entries are still asserted by index and rarity (`EmberdelveAffixProfileGate.cs:101-106`).
- No other fixture was re-baselined: the diff touches only the two gates listed. The existing assertions that depend on seeds are loose:
  - the AffixProfile explicit-seed block only needs at least one gear drop;
  - the RuntimeSmoke `otherSeedDiffers` check depends on the data, but passed.
- So determinism coverage is preserved, not weakened. Builder idempotence is plausible from the code and was demonstrated by a SHA1 comparison over every `Data/*.asset` and `*.meta` after a second `BuildDataOnly`. That only shows the build is stable once the entry exists; the first append is covered by the entry-count checks.
- See M2.1 for the Sealed 100% drop.

### 3. UI
- The model is correct and keyed on the instance:
  - two instances of one base give different text, with identical fixed lines;
  - Common has no rolled header;
  - rarity names and colours are distinct;
  - the hover reads `Slots[i].Instance` or `EquippedInstance`;
  - `Rebuild` re-validates by uid (`HoldsUid` / `HoldsInstanceUid`), so a consumed or moved instance cannot leave a stale tooltip. Gear never stacks; stacks fall back to `ForDefinition`.
- Steady-state hover allocates nothing. Strings are built only when the hover changes or on `Rebuild`.
- Null instance and definition hide the panel. The clamp keeps the panel inside the satchel in root space, and the math is correct for a panel with a (0,1) pivot.
- Visual risks are under R1, findings 1, 3 and 7.

### 4. Changed existing assertions (complete list)
- `EmberdelveAffixProfileGate.cs:97`: `entries.Length 4/4/3` changed to `5/5/4`. Justified, since a cloak entry was appended to each table. Three new checks (`:98-100`) pin the appended item and rarity. Coverage is extended, not weakened.
- `EmberdelveAttributeSkillGate.cs:1323`: the `UnequipAll` upper bound changed from `Legs` to `Back`. This is not an assertion; it widens a cleanup helper, so it is stronger. `Equipment.SlotCount - 1` would be more robust.
- No other test file has modified lines. The inventoryui change is a new scenario only: the existing scenarios are untouched and one `yield return` was added.
- Counts are stable: there is no randomness without a seed in any counted loop.

### 5. Compile and API fragility, dead code
- Removed members (`UpdateTooltip`, `_hoverItem`, `DescribeAttributeBonuses`, the old `IsCarriedOrWorn(ItemData)`) have no remaining references.
- `Equipment.SlotCount` changed from `private const` to `public static readonly`. Array field initializers still work, because the static is initialized first, and no `const` context uses it.
- No dead code was found. `ItemTooltipModel.Rarity` is set but not read, which is harmless.
- Overclaims are listed in M2 and M1.

## Summary
ACCEPT-WITH-FOLLOWUPS. Slot, category, equip and stat logic are correct, well tested, and do not weaken existing tests. Before commit:
- **M1:** fix the 6 px character-pane overflow added by the Armour row.
- **M2:** correct the report. Every Sealed chest now guarantees a Rare mantle; the "determinism per seed" claim is count-only; most of the 10107 checks come from one seed loop; the pane arithmetic is wrong.

Before acceptance: a windowed 720p/1080p screenshot review (R1). Later: the tab round-trip tooltip bug, a negative category-mint test, tooltip height for wrapped lines, exact mana assertion, and text and format polish.
